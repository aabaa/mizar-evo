### 0.2 Mizar の実装史: 初期処理系から Mizar-rs、Evo へ（0:30）

1973年の出発点は、数学の文書を計算機で扱う構想でした。1975年の Mizar-PC は命題論理の版です。この PC は propositional calculus の略で、後年のパソコン版 PC-Mizar とは別です。初期実装は ODRA 上の Algol、1977年の量化を扱う QC では CDC 上の Pascal が使われました。〔歴史論文〕
1980年代前半には、小言語として整理した MSE や、数学的記法と暗黙の引数を拡充した HPF などの実験がありました。表は主要な節目で、一本道の後継関係ではありません。
1986年の Mizar-4 は、限られたメモリで処理するために複数のパスをファイルでつなぎ、同年末に PC へ移植されました。1988年の PC-Mizar と、翌年の MML 開始によって、article を相互参照し、数学を積み上げる環境になっていきます。〔歴史論文〕
可読な記述もライブラリ再利用も、こうした試行と再設計の中で育ちました。

PC-Mizar の段階的な処理系を受け、Mario Carneiro 氏の Mizar-rs は、健全性に関わる analyzer と checker を Rust で再実装しました。〔Carneiro 2023〕
成果は三つあります。第一に、checker を差し替えて当時の MML 全体を検査したこと。第二に、論文の8スレッドの実時間比較で、検査を約5〜6倍高速化したこと。第三に、既存実装の健全性バグ4件を発見し報告したことです。MML 内で偽の証明に使われていたという意味ではありません。〔文献、Table 1・§5〕
再実装は高速化と既存系の改善に貢献しました。一方、小さな信頼基盤への証明出力は将来課題です。この成果と課題を背景に、Mizar Evo では言語仕様から設計し直し、Rust で処理系を構築します。〔文献／Evo の方針〕

### 0.4 設計の深化と AI Agentによる実装（6:30）

template には当初から generics の構想がありました。そこから、従来の scheme 相当を template 内の theorem として書く形に統一しました。さらに、たとえば環の加法と乗法で同じ定理を使えるようにするため、型パラメータの制約や構造 view を具体化し、型引数推論も整えました。単なる型の差し替えから、定義と証明を共通に扱う設計へ広がったのです。〔仕様18／Git履歴〕

AI coding agents の進歩により、当初考えていた実装協力を待たず、2026年5月から Rust 実装を本格化できました。これは私の定性的な経験で、速度の倍率を測定した報告ではありません。
6月から7月には、crate の開発と自律開発の手順、SAT を使う検査、健全性監査を整えました。実装とテストで仕様の曖昧さが見え、設計へ戻る循環です。〔Git履歴／経験〕

## Part 1. Logical Foundation（9–11分）

### 1.1 Keep The Foundation, Rebuild The Tools（9:00）

数学の層は保存する。その下と周りの基盤は作り直す。これが Mizar Evo の方針です。
証明の基盤として、一階論理と Tarski–Grothendieck 集合論を保ちます。soft type、mode、attribute、registration、structure、宣言的証明も保ちます。
証明探索と検査を分離し、受理を小規模な kernel に集約します。論理の継承と、小さな信頼基盤を両立する設計です。検査の具体的な仕組みは §6 で説明します。
数学的な記述は §2、汎用化は §3、計算は §4、開発基盤は §5 で扱います。〔仕様〕

### 1.2 集合から位相空間まで（10:00）

継承したい数学の書き方を二つ示します。ここでは前提と結論に注目してください。
一つ目は Cantor の定理です。集合 X より冪集合の方が濃度が大きい。集合、冪集合、基数を、同じ一階の集合論の対象として扱います。ここでは基数を順序数で表すため、inが大小を表しています。
二つ目は、コンパクト空間から Hausdorff 空間への連続全単射が同相写像になる定理です。TopSpaceという構造に compactやT_2という属性を付け、写像の条件と結論を記述しています。
このような数学的な記述を継承し、それを支える探索・検査の処理系を再設計します。〔CARD_1:14／COMPTS_1:17〕

## Part 2. Readable Mathematics（11–16分）

### 2.1 type・registration・overload の追跡（11:00）

ここでは type、registration、overload の順に、暗黙の判断を追います。
対象をどの型として使えるか、必要な属性がどの規則から得られたか、どの定義やビューを選んだか。自然な記述と自動処理を保ちながら、その根拠を説明できるようにします。まず構造の宣言と継承から見ます。〔仕様〕

### 2.2 type: field と property を宣言する（11:30）

LoopStr と、その加法版 AddLoopStr の宣言です。carrier と演算は格納する field で、構成子に渡すデータです。
unit と zero は property として名前と型だけを宣言します。ここでは値は決めません。まず、この二つの構造の対応を継承で宣言し、その後で property を実装します。〔仕様〕

### 2.3 type: 継承関係を後から宣言する（12:15）

構造の宣言後に inherit を書けます。型の定義と関係の実装を分ける点で、Rust の trait 実装に近い構成です。
親の binop を子の add、親の property unit を子の property zero に対応付けます。親ごとに一つの inherit 宣言です。型が同じなら証明は不要で、型を狭める場合は coherence を証明します。
この対応を使い、次に親側の unit を実装します。〔仕様〕

### 2.4 type: Unital の unit を実装し、zero に引き継ぐ（13:00）

has_unit は、両側単位元が存在するという属性です。unit 自体は参照しません。この条件を満たす LoopStr を mode Unital と定義し、その unit を means で実装します。存在は mode の前提から、一意性は二つの単位元を演算して証明できます。
AddLoopStr の LoopStr ビューが Unital なら、先ほどの zero from unit の対応を通じ、同じ実装を zero として使えます。零元を別に実装する必要はありません。〔仕様に基づくスケッチ・証明省略〕

### 2.5 registration: 自動連鎖で見えにくくなる依存（13:45）

次に registration です。empty な集合 S と宣言するだけで、finite、さらに countable まで自動的に得られます。利用箇所で、働いた規則を by に書く必要はありません。
便利な反面、登録が連鎖すると、countable という事実がどの規則から得られたか、その箇所のソースだけでは追いにくくなります。ここがトレーサビリティの課題です。
新仕様では、自動適用を保ちながら各登録にラベルを必須にし、EmptyImpliesFinite から FiniteImpliesCountable へ、という適用経路を記録します。最終的な属性だけでなく、そこに至る依存の連鎖を説明できるようにします。〔仕様〕

### 2.6 overload: 同じ環の単位元を使い分ける（14:45）

最後に overload です。先ほど扱った単位元を、環の加法と乗法で使ってみます。
加法の単位元は零、乗法の単位元は一です。どちらも演算の単位元ですが、値は違います。
仕様にある id. M は、unital Magma の単位元を返す functor です。ここで id. R とだけ書くと、加法と乗法のどちらの Magma として使うかが曖昧になります。
R qua AddMagma を指定すれば R.zero、R qua MulMagma を指定すれば R.one が得られます。それぞれのビューに単位元がある事実を前提に使います。
同じ環でも、選ぶビューによって零と一を使い分けます。型や属性で定義の適合性を判断し、どの演算のビューを使ったかを明示することが重要です。〔仕様に基づくスケッチ〕

## Part 3. Generic Mathematics（16–19分）

### 3.1 現行 MML: 型ごとに増える再定義・登録（16:00）

次は template です。関数の和は、各点で値を足すだけです。現行 MML でも、その本体は一度定義されています。
ところが、結果の型を保つには、複素数、実数だけでなく、有理数、整数、自然数についても、結果型の再定義と登録を個別に用意します。それぞれ整合性の証明も必要です。
同じ和なのに、対応する型が増えるほど周辺の記述と証明が増える。この負担を template で一元化したい、というのが次の例です。〔VALUED_1〕

### 3.2 template: 本体と結果型を一元化する（16:45）

加法構造 T と共通の非空定義域 I をパラメータにし、関数の和の本体と結果型を一つの定義にまとめます。
実数から自然数まで、それぞれの加法構造を T に指定して同じ Add を使えます。型固有の閉性や登録は必要ですが、和の定義と結果型の記述を繰り返す必要はありません。
synonym で + 表記を与えます。ここでは宣言型から T と I が一意に決まるため、型引数を省いて f+g や u+v と書けます。曖昧な継承経路には qua が必要です。
現行 MML は異なる定義域の共通部分も扱います。この例は共通の非空定義域に限定しています。〔仕様に基づくスケッチ・証明省略〕

### 3.3 Schemes Become Ordinary Templates [deep dive]（17:45）

従来の scheme も theorem に統合します。帰納法を例にすると、`let P be pred(Nat);` を持つ定理 `NatInduction[P]` になります。述語パラメータは、代入する述語ごとに一階の定理の族を生成します。
適用は `defpred` の後に `by NatInduction[P], Base, Step` と明示します。関数子パラメータは schema レベルの記号として扱い、一階論理を維持します。

### 3.4 template: 構造と属性もパラメータ化する（18:25）

上は体 K 上のベクトル空間、下は空間 M における稠密性の例です。
馴染みのある of や属性の接頭表記も、template の syntax sugar として扱います。Vector of K は Vector[K]、M-dense は dense[M] に対応します。構造の例でも VectorSpace over K と書けます。
構造・属性・mode などを、共通のパラメータ化で扱います。〔仕様に基づくスケッチ〕

## Part 4. Verified Computation（19–24分）

### 4.1 Computation: Verified Algorithms（19:00）

Hoare 論理では、事前条件 P から文を実行し、戻れば事後条件 Q が成り立つことを検査します。
代入は Q の x を代入式 e で置き換えます。if は条件 B とその否定で枝を分けます。while は、入口で不変条件 I が成り立つこと、本体が I を保つこと、終了時に I と条件の否定から Q が導けることを示します。
規則を本体に再帰的に適用して、一階の証明義務に分解します。停止性は後の terminating で扱います。〔仕様の基本規則〕

### 4.2 Algorithms: Contracts, Proofs, Computation（19:45）

ユークリッドの互除法です。requires と ensures で契約を記述し、ループに invariant と decreasing を付けます。Gcd は数学側の関数子です。
EuclidGcdDef は定義ラベル、euclid_gcd は呼び出す名前です。terminating は、requires を満たすすべての入力で停止するという主張で、不変条件と測度から生成する証明義務を検査します。
検証後は数学的な functor として論理式や証明の中で使えます。〔仕様〕

### 4.3 互除法: コードと証明義務（21:00）

先ほどの本体を再掲しました。コードと表の番号を対応させて見ます。
(1)で x=a、y=b と初期化するので、事前条件から不変条件が成立します。(2)の不変条件は、r=x mod y として x,y を旧 y,r に更新した後も保つ必要があります。Gcd(x,y)=Gcd(y,r) という補題を使います。
(3)の測度は y です。ループに入る時点で y は正で、剰余は0以上、旧 y 未満なので厳密に減少します。(4)で返す時は y=0 です。不変条件と Gcd(x,0)=x から、返却値が入力の GCD だと分かります。
こうした各箇所の義務をライブラリの補題とともに検査します。〔仕様に基づく説明〕

### 4.4 Termination And Functor Promotion（22:15）

既定は部分正当性です。terminating を検証すると、requires の下で全域性が得られ、functor として使えます。
上の例は、一般の正の自然数 a,b について、by EuclidGcdDef で検証済みの契約を引用します。
下の by computation は、検証済み algorithm を具体的な入力で MVM、仮想機械により実行し、その結果を証明に使う機能です。ここでは12と8を入力し、結果が4になることを確かめます。MVM 実行は未実装で、この例は仕様に基づくものです。〔仕様／実装状況〕

### 4.5 式変形を検証する: lambda と微分（23:15）

lambda は関数を直接書く記法です。u |-> (sin u)*u で、実数 u を sin(u) 掛ける u に送る関数を表します。
expr、構文木として渡すと、algorithm が積や sin の形と変数束縛を保って処理できます。differentiate の契約を微分則で検証し、変換結果を微分の証明に使います。表示した結論には意味変換と簡約の補題も用います。
関数の記述、式の変換、その正しさの証明をつなげられる点が利点です。これは仕様上の利用例で、MVM 実行は今後の課題です。〔仕様に基づくスケッチ〕

## Part 5. Development Infrastructure（24–27分）

### 5.1 Environment: What Must An Author Import?（24:00）

環境部には、表に示した10種類の指令があります。上のコードは ALGSTR_0 の一部を抜粋したものです。同じ STRUCT_0 でも、記号・記法・構成子・登録など、必要な資源を役割ごとに選びます。
特に難しいのが notations と definitions です。重なる記法や再定義には上書きの優先関係があり、article の列挙順によって採用される記法・定義が切り替わります。追加や並べ替えが、既存の記述や証明に影響することがあります。
何を取り込むかに加え、この優先関係まで著者が管理します。上書きと順序依存の管理が、Mizar アーティクル執筆の最大の難所です。〔現行環境の説明〕

### 5.2 Imports And Dependency Tracking（25:00）

新仕様では冒頭の import でモジュールの公開項目を取り込みます。例の function と algebra.structure.sorted は、仕様の例に基づくモジュールです。元の完全修飾名と、登録の解決トレースで、どの項目が実際に使われたか追跡する方針です。
依存指紋で検証済みの成果を再利用し、package と lock file でバージョンを固定します。IDE からは解決した名前やトレースを確認する設計です。
旧環境部の各一覧を一対一で置換する翻訳例ではありません。数学的な記述を継承しながら、依存と暗黙の処理を説明できる開発基盤へ進む、という設計です。〔仕様〕

### 5.3 The Whole Picture [deep dive]（26:00）

全体像を一枚で。
上に豊かな数学。structure、template、algorithm、module。下に小さな一階の基盤。周りに現代的な基盤、ATP 層、kernel、成果物、バージョン管理されたライブラリ、IDE、AI、出版。
数学の層は保存し、核は小さく保ち、基盤は作り直す。この話の内容はすべて、この三つの層のどれかです。〔仕様〕

## Part 6. Checking And Automation（27–32分）

### 6.1 自動化: 補題を探索し、証明を提案する（27:00）

Isabelle の Sledgehammer は補題を探し、証明案を提示します。Mizar Evo でも同様の native hammer を処理系・IDE に統合する計画です。
下の by は最終出力です。ゴール Q(a) と局所仮定 P(a) から、ライブラリの補題 AllPQ を候補に選び、ATP で試して引用案を提案します。採用した引用をソースに反映し、再検証します。
探索や提案を自動化して執筆を支援し、受理は論理式と置換の evidence を kernel で検査して決めます。〔仕様・計画に基づく説明〕

### 6.2 Using ATPs: Search, Check, And Reuse（28:00）

ATP をどこで活用するか、流れ図で示します。
ゴールと利用できる前提を ATP に渡して探索し、得られた候補 evidence を kernel で検査します。受理した成果をライブラリに保存し、再利用します。
未解決の場合は、補題や方針を修正して再探索します。LLM はこの提案や修復を支援できます。この図は設計意図であり、反復の費用対効果を示した実験結果ではありません。
通常の検証で使う前提は、ソースの引用と局所仮定です。支援段階で探索した補題も引用へ反映し、再検証します。受理の根拠である evidence の検査を、次のページで具体的に見ます。〔仕様／設計意図〕

### 6.3 Resolution Tree And Extracted Substitutions（28:45）

前提 F1 は P なら Q、F2 は Q なら R、H は P(a)、ゴールは R(a) です。ゴールの否定を加えて反駁します。
左の木では、まず Q(x) と Q(y) を単一化し、x:=y として、not P(y) または R(y) を得ます。次に P(y) と P(a) を単一化し、y:=a として R(a) を得ます。not R(a) と合わせると空節です。
右側に示すように、途中の x:=y を枝に沿って y:=a と合成します。元の F1 に x:=a、F2 に y:=a を回収し、出所と対象に結び付けます。
これは外部ログを使う非信頼の候補生成案です。現行の独立した instance finder も、同じ形の evidence を生成できます。ログの各推論を kernel に再生させるわけではありません。〔設計スケッチ〕

### 6.4 Saved Evidence To Concrete SAT Clauses（30:15）

図の上段は、保存する evidence、kernel の照合、インスタンス化です。元の式と合成した置換を出所・対象・束縛文脈と照合し、capture avoidance を検査します。その後、二つの含意を a でインスタンス化し、P(a) とゴールの否定を加えます。
P(a)、Q(a)、R(a) を命題変数1、2、3にします。二つの含意を表す補助変数4、5を導入し、これらが真という単位節を加えます。こうした Tseitin 符号化は現行エンコーダと同じ構成です。
下段の青い二つの箱は、補助変数 s と t の定義と、定義の3節と、その含意を真とする単位節1つをそれぞれ示しています。上の単位節 p と not r を加えると、5変数・10節になります。緑の帯のように、p と二つの含意は r を強制し、not r と矛盾します。
small kernel は外部の Resolution の各ステップを replay しません。検査済み evidence から自分で生成した節について、信頼する SAT 検査器で UNSAT を確認します。ここで示した節列は符号化の具体例で、実装の実行ダンプではありません。〔アーキテクチャ仕様に基づく設計スケッチ〕

## Part 7. Status And Roadmap（32–38分）

### 7.1 実装状況と規模（32:00）

ここまでの設計と、いま動く範囲を分けます。表は08861708という固定コミットで、実装規模は2026年10月15日に計測しました。〔固定版の状況〕
単位は千行です。テスト・空行・コメントを除く Rust 製品コードは、現在約27.1万行です。名前解決と型検査が約12.3万行、Core と VC の周辺が約5万行を占めます。これは存在するコードの量であって、機能の完成率ではありません。〔計測〕
右隣は、現在の実装を含む完成時の総量を、残機能から仮置きした見積です。全体で約36万から54万行。正式な計画値ではなく、特に未着手の MVM・抽出は実装方式によって変わります。MML 本体の移植量は別です。〔暫定見積〕
字句・構文解析は Driver から動き、意味解析と検証義務生成には限定した経路があります。ATP・kernel・成果物保存などの部品もありますが、全体の接続が残ります。LSP の意味情報接続、MVM 実行・抽出・文書生成も今後の開発です。〔限定実装／計画〕

### 7.2 ソースから成果物までの境界（33:30）

Driver の実接続はソース読込から Frontend までで、ModuleResolver 以降のサービスは未接続です。一方、テストハーネスには、限定した source を意味解析、Core、VC へ渡す経路があります。〔限定実装〕
一般の証明を外部 ATP に送り、kernel で受理し、検証済み artifact にする全経路とは区別します。SAT kernel があっても、式・文脈・置換・来歴を正しく生成し、受理結果を witness と成果物へ渡す必要があります。〔計画〕
Algorithm も、契約・停止性の義務を作ることと、MVM で計算することは別です。抽出と by computation の実行には別途実装が必要です。互除法の例は、現在の処理系で最後まで動かしたデモではありません。〔仕様と実装の境界〕

### 7.3 ロードマップ（35:00）

最優先は、この接続を完成へ進めることです。ソースから意味を取り出し、VC を生成し、evidence を作り、kernel で受理し、artifact と build へ渡す。この順に、動く範囲を広げます。未対応の入力を受理しない境界を保つことも必要です。Algorithm の意味論と検証義務の整合も続けます。〔計画〕
2027年度には、代表的な MML article を移植して互換性と記述の利便性を評価し、native hammer のベースラインと top-level theorem 単位の評価、論文化につなげたいと考えています。これは目標です。処理系が完成しても、MML 全体の移植は別の研究・整備課題です。科研費の延長も検討中で、承認済みではありません。〔予定・目標〕
MVM runtime とコード抽出は別途進める開発です。その先には学習的な前提選択、LLM による修復、暗号や量子アルゴリズムへの展開も考えていますが、これらは期日付きの完成予定ではありません。〔長期構想〕

35分版では長期構想の個別例を読み上げず、1分30秒に短縮する。

### 7.4 Closing（37:00）

Keep the foundation small. Keep the mathematics readable. Modernize everything else.
基盤を小さく保ち、数学的記述の可読性を維持し、周辺基盤を現代化する。
Mizar の一階論理と集合論、数学を読み書きする力を継承します。その上で Template、Algorithm、開発基盤を再設計し、ATP の探索と信頼できる検査を分離します。

## 想定問答（Backup の使いどころ）

- **「58.4% と 68.8% は結局どちらが強いのか」** → 評価単位・前提・予算・成功判定が異なるため、設計の優劣を判定できない。Backup 1–2, 11–12。
- **「一階の方が ATP に有利なのか」** → 本講演はその優位性を根拠にしない。符号化と再構成は接続の仕組みとして説明し、性能は別に評価する。Backup 13–17。
- **「template は本当に一階のままか」** → 仕様 18 章：述語・関数子パラメータは schema レベル、インスタンス化ごとに一階義務。Backup 4。
- **「algorithm は結局 tactic 言語ではないのか」** → 契約付きで検証対象になる点が違う。tactic 的用途も含むが、それ自体が仕様化・検証される。MVM・抽出は未実装。
- **「kernel は何を信頼しているのか」** → 本編 6.4。evidence の対応と代入を検査し、kernel が生成した SAT 問題の UNSAT を確認する。詳細は Backup 5。
- **「どこまで動くのか」** → 7.1–7.2 の限定経路の通り。一般の source-to-artifact と外部 prover の実証結果は未主張。講演日に固定 SHA と `doc/design/todo.md`、ソースを再確認。
