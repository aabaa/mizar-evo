## Part 0. Opening

### 0.1 Title（0:00）

Mizar は、一階述語論理と集合論の上に、人間が読める数学の言葉で証明を書き、機械で検査する処理系です。ライブラリ MML は50年の蓄積があります。
Mizar Evolution、略して Mizar Evo は、その言語と開発基盤を設計し直すプロジェクトです。
今日は機能を並べません。自動定理証明器をめぐる一つの「謎」から始めて、なぜ論理を一階のままにするのかを説明します。
話す内容はすべて、事実・研究仮説・将来構想のどれかにラベルを付けて区別します。

### 0.2 How To Read The Claims [deep dive]（0:45）

無印は事実、「research hypothesis」は Mizar Evo が検証しようとしている主張、「future direction」は日程も設計も確定していない目標です。
コード例には Białystok の資料と同じく、MML の正確な引用・仕様例・スケッチのラベルが付いています。
仕様と実装は別物です。終盤に一枚、その境界を示します。

## Part 1. Two Hammers, Two Numbers（0–6分）

### 1.1 Two Numbers That Look Alike（1:00）

二つのハンマーがあります。Mizar 側の MizAR と、Isabelle/HOL の Sledgehammer です。
MizAR 60（ITP 2023）は 58.4% を自動証明したと報告しています。Sledgehammer を AFP で評価した 2015 年の研究は 60.7% です。
数字はほとんど同じに見えます。しかし、この二つを一つのベンチマークとして比較してはいけません。
数えている単位、前提の与え方、時間予算が全部違います。MizAR は MML 1147 の top-level theorem と lemma 57,897 件を、ライブラリ全体から機械的に前提を選んで、420 CPU 秒のポートフォリオで証明します。AFP 側は 128 theory からサンプルした 6,934 個の proof goal を、各 prover 30 秒で解き、union を oracle として信じた値が 60.7% です。一行証明に再構成できたのは prover ごとに約 50% です。〔事実〕

### 1.2 What Each Number Counts（2:30）

図で見ると違いがはっきりします。
MizAR が数えるのは、木の根、つまり定理の主張そのものです。「ライブラリからこの定理を丸ごと、人の助けなしに証明できるか」という問いです。
AFP の研究が数えるのは葉、つまり開発の途中に現れる goal です。多くは人間がすでに構造化証明を書いた内側にあります。「この goal を、現れた場所で閉じられるか」という問いです。
どちらも正当な問いです。しかし同じ問いではありません。〔事実〕

### 1.3 Two Paths To A First-Order Prover（3:30）

では、それぞれの経路を見ます。
Sledgehammer は高階の goal を、前提選択のあと、一階論理あるいは SMT の問題に翻訳し、外部 prover を呼び、成功したら証明を Isabelle の内側に再構成します。オレンジの箱、翻訳と再構成が、論理のギャップを埋める層です。
MizAR は、最初から一階・集合論で書かれた top-level theorem を、前提選択のあとそのまま一階 ATP に渡します。使われた前提を Mizar の `by` ステップに戻し、Mizar checker が可能な範囲で再検査します。論理の翻訳層はありません。
どちらも既存システムについての事実です。違うのは、ギャップの代金をどこで払うかです。〔事実〕

### 1.4 The Question（4:45）

そこで問いです。ベンチマークの違いなのか、アーキテクチャの帰結なのか。
研究仮説として、こう置きます。一階のライブラリでは、処理系自身の意味表現と ATP に渡す問題の距離が短い。高階の処理系では、その距離を翻訳と再構成で埋める必要があり、それには代償がある。〔仮説〕
強く言ってよいことがあります。Sledgehammer は、高階の処理系が一階 ATP を非常にうまく使えることを示しました。これは事実です。
まだ言えないこともあります。高階経由が ATP を使う最良のアーキテクチャかどうかは決着していません。比較対象になる現代的な一階 ITP が、ほぼ存在しないからです。その空白が研究機会です。〔仮説〕
Mizar Evo は、現代的な処理系・ライブラリ・prover でこの仮説を試すために作っています。

## Part 2. Where Complexity Lives（6–14分）

### 2.1 Functions In Higher-Order Logic（6:00）

直感をつかむために、関数を例にします。
HOL では関数型と関数適用が論理そのものに組み込まれています。関数を引数に取る、関数を返す、部分適用、ラムダ抽象。すべて直接書けます。
書く人間にとって、これは非常に便利です。
しかし E や Vampire は一階の prover です。高階の構造は、prover に見せる前に符号化しなければなりません。〔事実〕

### 2.2 The Cost Appears At The ATP Boundary（7:00）

請求書は ATP との境界で届きます。
変数の関数適用は明示的な `app` 記号になります。ラムダは lambda lifting か combinator に変換されます。多相型は guard や tag として符号化されます。
そして prover が成功したら、証明を戻さなければなりません。`metis` の呼び出し、`smt` の replay、あるいは生成した Isar テキストです。
これは大きな工学的達成です。同時に、一階の処理系には不要な層でもあります。
HOL は便利さを先に受け取り、ATP の境界で支払います。〔事実、符号化の詳細はスケッチ〕

### 2.3 Functions In Set Theory: Mizar's Foundation（8:15）

今度は Mizar の基礎、集合論側です。MML からの正確な引用を二つ見せます。
一つ目、FUNCT_1。関数適用 `f.x` は、「x が dom f に入っていれば [x, it] が f に属する」という、定義された集合論的関係です。
二つ目、FUNCT_2。`Function of X,Y` は、部分関数の上に `quasi_total` という属性を付けた soft type です。
ここでは関数は普通の一階の対象、つまり対の集合です。適用は論理に組み込まれているのではなく、定義されています。証明の基盤を高階にする必要はどこにもありません。
代償もあります。素朴に集合論を書けば、定義域・グラフ・関数性・所属関係が全部表に出てきます。〔事実〕

### 2.4 Mizar's Fifty-Year Answer: Hide The Details In The Language（9:45）

Mizar の50年の答えは、この配管を言語の中に隠すことでした。
著者が実際に書くのは、`let f be Function of X, Y;`、`let x be Element of X;`、そして `f.x` です。同じ集合論的な関数ですが、対や定義域は書きません。
soft type、mode、attribute、registration、scheme、宣言的証明。これらは単なる糖衣構文ではありません。一階の集合論を、人間が数学として読み書きできる層へ持ち上げるための言語設計です。
Mizar はこの方向に50年歩いてきました。Mizar Evo はこの道を歩き続けます。〔事実と解釈〕

### 2.5 Where You Pay（11:00）

一枚にまとめます。
HOL は ATP の境界で払う。FOL はキーボードの前で払う。そして Mizar の言語層が、その支払いを吸収する。
HOL と FOL は複雑さを消しているのではありません。別の層に置いているのです。
Mizar Evo の選択はこうです。証明の基盤は一階のまま保つ。人間に向いた複雑さは言語層で吸収する。〔解釈〕

### 2.6 The Trade-Off In One Table [deep dive]（12:30）

表にすると、記述、関数の扱い、ATP 接続、再構成、言語層の責務、それぞれで代償の場所が入れ替わっています。
この表は解釈であって、測定ではありません。測定は、Mizar Evo が 2027 年に出さなければならないものです。〔解釈〕

## Part 3. Modernizing Mizar's Answer（14–24分）

### 3.1 Keep The Logic, Modernize The Language（14:00）

数学の層は保存する。その下と周りの基盤は作り直す。これが Mizar Evo の方針です。
証明の基盤として、一階論理と Tarski–Grothendieck 集合論を保ちます。soft type、mode、attribute、registration、structure、宣言的証明も保ちます。
その上で、暗黙の選択を明示し、generic な仕組みを統一し、自動化を追跡可能にし、全体を現代的なコンパイラ構成に載せ直します。
続く数枚で「層を現代化する」の中身を示します。template、algorithm、信頼境界、そして基盤です。〔仕様〕

### 3.2 Templates（15:00）

template は、パラメータ付きの definition ブロックです。例は `let T be type;` で始まる `MagmaStr[T]` です。
パラメータは型、値、述語、関数子を取れます。古典的な Mizar の scheme は、述語パラメータ付きの定理として同じ仕組みに入ります。
重要なのは、template が論理に無制限の二階量化を追加しないことです。インスタンス化はそれぞれ検査され、一階の証明義務に落ちます。
generic な数学は表層言語に住み、証明の基盤には住みません。〔仕様〕

### 3.3 Schemes Become Ordinary Templates [deep dive]（16:15）

帰納法を例にすると、`let P be pred(Nat);` を持つ定理 `NatInduction[P]` になります。述語パラメータは、代入する述語ごとに一階の定理の族を生成します。
適用は `defpred` の後に `by NatInduction[P], Base, Step` と明示します。関数子パラメータは schema レベルの記号であって集合ではないので、論理は一階のままです。
`PermProduct[T]` や `qua` によるビュー選択は Białystok の資料と Backup 4 にあります。〔仕様〕

### 3.4 Algorithms Are A Second Pillar（17:00）

ここで話題を切り替えます。algorithm は「FOL では関数が書きにくいから入れた HOL の代替」ではありません。別の必要、アルゴリズム的推論と検証可能な計算に答えるものです。
歴史的な傾向として、必然ではなく、こう言えます。一階論理には完全な推論系があり、その周りに resolution から superposition、saturation へと自動探索の文化が育ちました。LCF と HOL の系統には、tactic と tactical というプログラム可能な証明構成の文化が育ちました。〔歴史的傾向としての解釈〕
Mizar は宣言的証明と処理系が提供する自動化に依拠し、ユーザがプログラムできる tactic 言語は持ちませんでした。〔事実〕
Mizar Evo の algorithm は tactic 言語を後付けしたものではありません。契約を持ち、処理系が検証する手続きです。

### 3.5 Algorithms: Contracts, Proofs, Computation（18:15）

仕様の例、ユークリッドの互除法です。`requires`、`ensures`、ループの `invariant` と `decreasing` があり、`Gcd` は数学側の関数子なので循環はありません。
契約、不変条件、停止性の測度は一階の検証条件になり、定理と同じ ATP と kernel の境界を通ります。
役割は二重です。仕様化され検証された自動化手続きであること。そして Mizar Virtual Machine、MVM ができれば `by computation` で実行できる、検証済みの計算であること。
現状をはっきり言います。言語は仕様化されています。MVM の実行とコード抽出は後回しの作業です。〔仕様／実装状況〕

### 3.6 Future Targets For Algorithms [deep dive]（19:30）

将来構想として、整数論・組合せ論のアルゴリズム、記号計算、最適化手続き、さらに先には暗号アルゴリズムとプロトコル、量子アルゴリズムやハイブリッドなアルゴリズムを同じ枠組みで扱いたいと考えています。手続きを書き、契約を述べ、不変条件と停止性を与え、検証条件を生成し、ATP で証明して kernel で検査し、具体入力で実行し、将来はコードを抽出する、という一本の流れです。
algorithm は tactic と応用アルゴリズムの境界を狭めます。ただし、ここに挙げた対象はすべて将来構想です。〔構想〕

### 3.7 Search Outside, Trust Inside（20:15）

一階 ATP は強力な探索器ですが、信頼できる検査器ではありません。
Mizar 側の処理が名前、型、cluster、オーバーロードを担当します。prover は探索を担当します。kernel は受理を担当し、渡された論理式と代入を、小さく信頼できる SAT 検査で確認します。
prover の終了コードは証明ではありません。だからこそ、一階の自動化を設計原理にしても、信頼基盤は大きくなりません。〔アーキテクチャ仕様〕

### 3.8 And Mizar Itself Is Fifty Years Old（21:30）

そして Mizar 自身も50年分、古くなっています。
Mizar の数学的な考え方を保存することと、1970年代由来のソフトウェア構成を保存することは別のことです。
表の左は50年の MML 運用で見えてきた課題、右は Mizar Evo の答えです。article 単位の依存から明示的 import を持つモジュールへ。グローバルな名前管理から namespace と完全修飾名へ。配布とバージョン管理の弱さから package、SemVer、lock file へ。フルビルドから依存指紋による差分ビルドへ。外付けの ATP から kernel evidence を伴う第一級の ATP パイプラインへ。弱い IDE 連携から LSP、構造化診断、エージェント向けインタフェースへ。
これは批判ではなく、50年前には一般的でなかったソフトウェア工学を形式数学の環境に持ち込む、という話です。詳細は Białystok の資料にあります。ここでは一枚で十分です。〔仕様〕

## Part 4. The AI Era（24–28分）

### 4.1 The Whole Picture（24:00）

全体像を一枚で。
上に豊かな数学。structure、template、algorithm、module。下に小さな一階の基盤。周りに現代的な基盤、ATP 層、kernel、成果物、バージョン管理されたライブラリ、IDE、AI、出版。
数学の層は保存し、核は小さく保ち、基盤は作り直す。この話の内容はすべて、この三つの層のどれかです。〔仕様〕

### 4.2 LLM Thinks, ATP Proves, Mizar Evo Remembers And Verifies（25:00）

AI 時代にこの設計がどう効くか。
LLM は理論構築、定義の設計、証明方針、補題の発明、失敗からの回復が得意です。ATP は安価で反復可能な一階の探索が得意です。Mizar Evo は数学的表現、検証済みのライブラリ状態、信頼できる検査、来歴を提供します。
研究仮説として、大量生成の時代には、安価に検証する ATP の価値はむしろ上がると考えています。ただし、このカスケードの費用対効果は未検証です。〔仮説〕
現在の仕様では、ATP に渡るのは `by` で引用された前提と局所仮定だけです。ライブラリ全体から前提を選ぶ native hammer は 2027 年の研究項目です。〔仕様／計画〕

### 4.3 Where The Project Stands（26:30）

仕様と実装を分けておきます。2026年10月時点です。
仕様は24章と付録。英語が正典です。
main branch に実装済みなのは、Rust のフロントエンド、alpha コーパス上の名前解決と型検査、検証条件生成と決定的な discharge、ATP 問題の符号化と候補 evidence、SAT に基づく kernel の evidence 検査、キャッシュ・指紋・ビルドスケジューリングの各マイルストーンです。
進行中は、ソースから検証済み成果物までの end-to-end 統合、LSP サーバ、ドキュメント生成です。
後回しは、MVM の実行、コード抽出、ライブラリ全体の前提選択、MML の移行です。
外部 prover を使った end-to-end の結果は、この講演では主張しません。〔実装状況、講演日に再確認〕

## Part 5. Roadmap And Closing（28–30分）

### 5.1 Roadmap（28:00）

2026年は仕様を仕上げ、kernel までの Rust パイプライン、template 処理、alpha の end-to-end 実行を完成させます。
2027年は代表的な MML article を移行し、native hammer のベースラインを作り、MizAR と同じ単位、top-level theorem でベンチマークします。
2028年以降は移行の拡大、学習ベースの前提選択、LLM による失敗回復、MVM と抽出です。暗号と量子は将来構想のままです。〔計画／構想〕

### 5.2 Back To The Two Paths（29:00）

最初の二つの経路に戻ります。
問いは、高階の処理系が一階 ATP を使えるか、ではありません。明らかに使えます。
問いは、一階の自動推論を最初から設計原理にしたとき、何が可能になるか、です。
Mizar Evo の答えは六つ。一階論理と集合論を基盤として残す。Mizar の言語設計で一階の配管を隠す。template で generic な数学を広げる。algorithm で検証可能な計算を統合する。50年分のソフトウェア基盤を作り直す。LLM と ATP を適材適所で組み合わせる。

### 5.3 Closing（29:40）

Keep the foundation small. Keep the mathematics readable. Modernize everything else.
基盤は小さく、数学は読めるように、それ以外はすべて現代化する。
ありがとうございました。特に、2027年のベンチマークを「同じものを同じ単位で比べる」設計にするにはどうすべきか、ご意見をいただければ幸いです。

## 想定問答（Backup の使いどころ）

- **「58.4% と 60.7% は結局どちらが強いのか」** → 比較できない、が答え。Backup 1–2 で条件を並べる。MizAR の 75%（前提をライブラリから人または機械が選んだ条件）も同時に示し、premise regime で結果が大きく動くことを強調する。
- **「翻訳のコストは実測されているのか」** → Sledgehammer 側の reconstruction 失敗率（one-line 約50% に対し oracle union 60.7%）が一つの手がかりだが、架橋コストの直接測定は Mizar Evo 側の 2027 年ベンチマークの課題。〔仮説〕
- **「template は本当に一階のままか」** → 仕様 18 章：述語・関数子パラメータは schema レベル、インスタンス化ごとに一階義務。Backup 4。
- **「algorithm は結局 tactic 言語ではないのか」** → 契約付きで検証対象になる点が違う。tactic 的用途も含むが、それ自体が仕様化・検証される。MVM・抽出は未実装。
- **「kernel は何を信頼しているのか」** → 論理式と代入の evidence を検査し、SAT 検査で UNSAT を確認する。prover の出力は診断のみ。Backup 5。
- **「どこまで動くのか」** → 4.3 の通り。end-to-end と外部 prover の結果は未主張。講演日に `doc/design/todo.md` で再確認。
