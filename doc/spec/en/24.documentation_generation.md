The documentation generator (`mizar doc`) extracts structured documentation from source files and produces browsable, cross-referenced HTML output. The source of documentation is the Mizar source itself: item labels, type signatures, theorem statements, and `:::` documentation comments (§2.9.1). No separate documentation language is required.

The generator reads the `exports` array from `*.mizir.json` artifacts (§23.5.1) to determine which items are publicly visible, and uses the `@latex` annotations (§21.3) and resolved types from the same artifacts to render mathematical notation.

## 24.1 Documentation Comments Syntax

A **documentation comment** is a contiguous block of `:::` line comments immediately preceding a named item (definition, theorem, registration, or algorithm). No blank line may appear between the comment block and the item it documents; a blank line ends the association.

```mizar
::: Computes the greatest common divisor of two positive integers
::: using the Euclidean algorithm.
:::
::: The result satisfies `result divides a`, `result divides b`, and
::: for any `d` dividing both `a` and `b`, `d divides result`.
terminating algorithm euclid_gcd(a, b) -> Nat
  requires a > 0 & b > 0
  ensures result = Gcd(a, b)
  ...
```

The body of a documentation comment is interpreted as **Markdown**, CommonMark 0.31.2, with the following Mizar-specific extensions. The parser baseline is `pulldown-cmark =0.13.6`, `default-features = false`, `Options::empty()`: tables, footnotes, task lists, strikethrough, smart punctuation, heading attributes, metadata blocks and native math are disabled. The complete CommonMark surface remains required, including headings, thematic breaks, containers, code, reference definitions, links/images/autolinks, escapes/entities and raw HTML. The pinned CommonMark examples and Mizar interaction cases must pass before parser implementation acceptance; discrepancies return to the owner rather than narrowing the language. Raw HTML parsing does not decide later sanitization/output policy.

- Inline code enclosed in backticks (`` `code` ``) is rendered with Mizar syntax highlighting. It is linked only when the contents are an exact label or FQN reference (§24.2).
- Display math delimited by `$$` is rendered as a mathematical formula (§24.3).
- Cross-reference links of the form `[text](ref)` are resolved as described in §24.2.

**Block structure.** A documentation comment may contain multiple paragraphs separated by blank `:::` lines. Lists, code blocks, and block-quote admonitions are supported using standard Markdown syntax within `:::` lines.

```mizar
::: Computes `n!` (n factorial) for a natural number `n`.
:::
::: ## Examples
:::
::: ```mizar
::: factorial(0) = 1
::: factorial(5) = 120
::: ```
:::
::: ## Mathematical definition
:::
::: $$n! = \prod_{k=1}^{n} k$$
:::
::: The algorithm terminates because `n` decreases at each recursive call.
terminating algorithm factorial(n) -> Nat
  ensures result = Factorial(n)
  decreasing n
  ...
```

**Structured tags.** The following tags may appear as the first token of a paragraph within a documentation comment:

| Tag | Usage |
|---|---|
| `@param name` | Documents the parameter named `name`. One tag per parameter. |
| `@returns` | Documents the return value; the identifier `result` refers to the return value. |
| `@requires` | Prose description of the precondition (supplements the formal `requires` clause). |
| `@ensures` | Prose description of the postcondition (supplements the formal `ensures` clause). |
| `@see ref` | Adds a "See also" cross-reference link (§24.2). |
| `@since version` | Records the version in which the item was introduced. |
| `@deprecated version` | Marks the item as deprecated since `version`; the deprecation message follows. |

**Raw field model.** Remove `:::` and at most one following ASCII space per line; preserve the remainder and raw/reverse mappings without global trim/deindent or a second source normalization. `W` is ASCII space, tab, CR or LF. Only the first inline source position of a CommonMark paragraph can start a tag, including structural paragraphs in quotes and tight/loose list items even when event wrappers are omitted. Strip only container/paragraph indentation for recognition, retaining its map. Headings, code, HTML and reference definitions do not introduce tags. A marker is literal `@` plus a maximal non-W token; only exact lowercase known names match. Escapes/entities, code/emphasis/link wrappers, uppercase names and `@param,` cannot manufacture a known tag. Unknown tags remain verbatim.
After the marker skip W in the same paragraph. For `@param`, `@see`, `@since` and `@deprecated`, consume the next maximal non-W source token as name/ref/version, without decoding markup, special quoting or imposing token/version/reference grammar. A missing slot is never borrowed from another paragraph. The body is the remaining source suffix after separator W (or after marker-separator W for slotless tags), excluding separator W from its semantic boundaries but retaining the full raw payload. Soft/hard breaks continue the current field; the next paragraph/block ends it. Thus the consecutive `@param a`, `@param b`, `@returns`, `@requires`, `@see` lines in the example below form ONE `@param` field; blank paragraphs are needed to introduce separate fields. Later blocks remain ordinary documentation.
Extract fields from the logical paragraph stream after display recognition and before inline math; slots remain opaque to math. Map each segment through container removal, comment extraction and Artifact/loading maps to real source without fabricating contiguous bridges. Duplicate comparison uses the original extracted slice including continuation-line container prefixes, ending before the final contributing line terminator; internal line endings and trailing spaces/tabs remain significant. `@param` compares exact raw name tokens; `@returns`, `@since`, `@deprecated` are singletons regardless of payload; repeatable `@requires`, `@ensures`, `@see` compare exact tag name plus the entire post-marker payload including separator/trailing W. Compare across all separate source-ordered blocks on the same full-provenance target, warning on each later match without merging/overwriting; no Unicode/whitespace/entity/markup/reference normalization.
Require a non-W source character in bodies for `@returns`, `@requires`, `@ensures` and after `@deprecated version`; markup-only spelling counts. `@param` explanation is optional; `@see`/`@since` need only their slot. Missing slots/bodies, approved duplicates and established metadata mismatches retain text and warn under §22.6.9. Compare raw parameter names only against authoritative metadata for the same target: a complete list can establish absence, a partial/unavailable list cannot. Warn about `@returns` only when authoritative metadata establishes no return value. No warning for undocumented parameters, unavailable metadata or unresolved refs; never infer signatures or compare prose with formal formulas. These tags are neither statement annotations nor formal contracts.

```mizar
::: Divides `a` by `b` and returns the quotient.
:::
::: @param a  the dividend
::: @param b  the divisor; must be non-zero
::: @returns  the real number `a / b`
::: @requires `b <> 0`
::: @see mml.real.Real_div_mul
definition
  let a, b be Real;

  algorithm divide(a, b) -> Real
    requires b <> 0
    ensures result * b = a
  do
    return a / b;
  end;
end;
```

**Module-level documentation.** A documentation comment at the top of a source file, before any `import` or definition statement, documents the module as a whole. It appears on the module's index page in the generated output.

## 24.2 Cross-Referencing and Hyperlinks

The documentation generator resolves cross-references among labelled items across the entire package and its dependencies. References are label-based rather than expression-based so that documentation links are stable even when an item has overloaded notation or multiple surface syntaxes.

**Inline code links.** When the contents of a backtick span are an exact item label or FQN, the generator links it to the documentation page for that item:

```
::: The result equals `Gcd` as defined in `mml.nat.Gcd`.
```

**Occurrence and comparison.** Retain each occurrence's form (code, explicit link or `@see`), raw spelling, interpreted destination when available, mapped source segments, attached module/item identity and publication provenance. Compare the interpreted destination supplied by §24.1 exactly: no further trimming, case folding, Unicode normalization or expression parsing. Raw text remains available for diagnostics. Backtick spans that are expressions, theorem fragments or overloaded notation remain code; never split one expression into reference attempts. Missing or unsupported destination classification is an unresolved handoff, not a guessed symbol.

**Lookup and completeness.** Targets retain full original package/version/lock/module/edition identity, publication hash, export origin, FQN, actual label and visibility; reexports preserve stored identity. Apply the selected documentation visibility policy without granting verification authority. Collapse only identical complete target identities reached through multiple routes. For an unqualified label, one current-module exported target resolves definitively, multiple distinct targets are ambiguous, and only zero targets permits searching imports. Traverse all imports in authoritative semantic order; two distinct matching targets are ambiguous even at different positions. No first-enumerated target wins. Without a definitive current-module result, unavailable or incomplete import metadata prevents successful resolution. Distinguish unavailable, incomplete and explicitly complete-empty ordered import vectors; storage order is not semantic import order.

FQN lookup searches only the explicitly bound finite package/dependency documentation closure. Distinct full identities with the same FQN remain ambiguous across packages or versions; no new disambiguating syntax or version selection is implied. A unique target is linkable only when the queried namespace and its page/anchor are complete; zero matches is unresolved only after a complete search. Missing inputs never mean a negative result or an empty graph. Each dependency reference supplies its package tuple, publication hash and index location. The index consumer authenticates schema, publication and complete target identities against validated inputs before use. Paths or canonical sorting cannot authenticate edges. Cycles do not cause recursive source or dependency discovery; no network lookup is performed.

**Explicit links.** The standard Markdown link syntax `[display text](ref)` accepts three forms for `ref`:

| Form | Example | Resolves to |
|---|---|---|
| Label or FQN | `(Gcd)`, `(mml.nat.Gcd)` | Documentation page for the labelled item |
| Section reference | `(§20.5.1)` | Section anchor in the generated specification |
| URL | `(https://...)` | External URL (passed through unchanged) |

```mizar
::: This algorithm implements the approach described in [§20.5.1](§20.5.1).
::: The result type is documented under [Element of R](algebra.struct.Element).
```

**Automatic back-references.** For each theorem `T`, "Used by" lists every theorem directly citing `T` in a `by` clause, without requiring an annotation. The Artifact owner must supply authoritative publication-bound direct-citation records identifying citing/cited theorem export identities, occurrence provenance and completeness scope, including which theorem bodies/proofs were covered. Existing `exports` and `used_axioms` alone do not establish this graph; no existing artifact field or new schema is implied. A missing producer or unmapped endpoint is unavailable/incomplete, never zero citations. Consumers must not reconstruct citations from source, names or accepted proof evidence.

Reverse only direct mapped theorem-to-theorem edges. Display each citing theorem once per target, including authoritatively recorded self-citations; cross-package edges require bound endpoints. Retain repeated occurrence provenance/order separately. Sort displayed citing identities by existing full module identity order, exact FQN, origin, then publication hash. `@see`, Markdown links, transitive dependencies and `used_axioms`-only entries are not direct-by evidence. Incomplete coverage is visibly unavailable, never an exhaustive empty list.

**`@see` links.** The `@see ref` tag in a documentation comment adds an entry to the "See also" list at the bottom of the item's page. `ref` follows the same three forms as explicit links.

**Pages and anchor naming.** A separate allocation table keyed by full module/publication identity supplies module-page paths relative to the selected output root, distinguishing packages/versions and rejecting path collisions before href construction. This rule does not choose directory spelling. Every documented item has its exact authoritative FQN as the full DOM id, derived from its exported label, without notation slugs, normalization, suffixes or renaming. An unavailable authoritative label blocks item-anchor readiness; distinct items requiring the same full id on one page block that page's link readiness. Item references target the allocated module page plus full FQN fragment. Thus `algebra.ring.AddAssoc` has logical anchor `#algebra.ring.AddAssoc`.

A short alias such as `#AddAssoc` may be emitted only for one distinct documented target with that label on the page and only if it collides with no full id, section id or other alias. Full ids take priority; suppressing an alias never changes them. Section headings use `#sec-20-5-1`; section references require an explicit generated-specification index binding specification version, section id and page destination. Absent/unknown sections remain unresolved, never local module anchors.

**Href encoding.** Construct relative hrefs from allocated paths by percent-encoding UTF-8 bytes outside ASCII letters/digits and `-._~` in each path segment, retaining `/` only as path separators. Encode the full logical fragment by the same byte rule. DOM ids retain the exact FQN spelling, escaped for HTML attributes. For example, allocated path `p/é%#.html` and logical fragment `m.é%#` yield `p/%C3%A9%25%23.html#m.%C3%A9%25%23`; the DOM id remains `m.é%#`. No filesystem layout or source-link routing is selected here.

**Degradation and implementation gates.** Unresolved or ambiguous eligible references render as safe unlinked text with deterministic Documentation warnings. Incomplete link or UsedBy inputs are exposed as unavailable with a completeness warning, not silently treated as unresolved or complete-empty. Lower-reader integrity/schema/binding refusals remain refusals. Doc10 remains gated on authenticated ordered import/dependency inputs and the Artifact direct-by producer, validated page/anchor/specification-section allocations, and adoption of exact shared diagnostic descriptors, detail/location, deduplication and ordering rules. This link-model adoption implements none of those producers, allocations or diagnostics.

Labels are part of the public documentation interface. For definitions, the definition label is used. For theorems and registrations, the theorem or registration label is used. For algorithms, the algorithm identifier is the documentation label; if a future syntax introduces a separate algorithm label, the documentation generator will use that label instead.

## 24.3 Mathematical Formula Rendering

Mathematical notation in generated documentation comes from two sources: `@latex` annotations on symbol definitions (§21.3) and LaTeX expressions embedded in documentation comments.

**`@latex` annotations.** When a functor, predicate, mode, or attribute definition carries a `@latex` annotation, the generator substitutes the given LaTeX string wherever the symbol appears in rendered output — in theorem statements, type signatures, and formula displays. If no `@latex` annotation is present, the symbol name is rendered in a monospace typeface.

```mizar
@latex("n!")
func Factorial(n) -> Nat;

@latex("\gcd(a, b)")
func Gcd(a, b) -> Nat;
```

A theorem whose statement involves both symbols is rendered as:

> **Theorem** `gcd_factorial_coprime`: for all $n \geq 2$, $\gcd(n!, n+1) = 1$.

**Inline formulas** in documentation comments use standard LaTeX delimiters:

- Inline: `$formula$` — rendered inline with the surrounding text.
- Display: `$$formula$$` on its own line — rendered as a centred display equation.

**Delimiter boundaries.** Identify CommonMark fenced/indented code, HTML blocks and reference definitions first, then display math; none contains structured tags. On remaining paragraphs derive fields, then recognize code spans, inline HTML and link/image/autolink structure before inline math, protecting their non-label contents. Backtick contents pass intact to later highlighting/exact label-or-FQN checking, never expression resolution. Preserve standard links outside display math and pass destinations/`@see` raw text and ranges to later resolution. In remaining paragraph text an unescaped single `$`, without adjacent `$`, pairs with the next such `$` in the same paragraph with nonempty interior. Backslash parity determines escaping, with no currency heuristic. Math precedes emphasis but cannot cross code/HTML or whole link/image/autolink boundaries; within a link label it pairs only inside that label. `$[text](ref)$` therefore retains the link and unmatched literal dollars (warning), while `[$x$](ref)` retains label math.
A display delimiter line, after container markers and up to three indentation spaces, contains only optional surrounding spaces/tabs and either `$$nonempty content$$` or `$$`. The latter searches for a later `$$`-only line in the identical container stack/list item, stopping at protected code/HTML/reference-definition blocks or container end; delimiter lines must be outside protected blocks. An interrupted opener is unmatched and consumes no intervening text: preserve its CommonMark parse. Accepted display blocks precede paragraph/inline processing; their interior contains a non-W character and is opaque with raw text/newlines/maps retained for later rendering. Other dollar runs are literal. Single-line candidates use the outermost pair only and allow no internal unescaped `$$`; otherwise the line stays literal. Paired W-only display candidates retain the entire literal spelling without a math node and warn.
CommonMark literal/recovery forms alone never warn, including unmatched emphasis/backticks or unclosed fences. Only eligible unmatched math openers, W-only display interiors, inherited tag conditions, or actual conversion/map failures warn on this surface (§22.6.9). Extension failures preserve text without a math node; actual conversion/map failure preserves the affected raw block and continues the default documentation build. Lower-reader refusals never become presentation success; absent maps never acquire fabricated ranges. Accepted math remains opaque.

The generator does not validate LaTeX syntax during the build; invalid LaTeX is passed through to the rendering engine and may produce a rendering error in the output.

**Automatic formula generation.** For items without a `@latex` annotation, the generator produces a default mathematical rendering by translating the Mizar surface syntax to LaTeX using the following rules:

| Mizar syntax | Default LaTeX output |
|---|---|
| `a + b` | `a + b` |
| `a * b` | `a \cdot b` |
| `a / b` | `\frac{a}{b}` |
| `a |^ n` | `a^{n}` |
| `a mod b` | `a \bmod b` |
| `a <= b` | `a \leq b` |
| `a <> b` | `a \neq b` |
| `a in S` | `a \in S` |
| `S c= T` | `S \subseteq T` |
| `for x being T holds P` | `\forall x \in T,\; P` |
| `ex x being T st P` | `\exists x \in T,\; P` |

The automatic translation is applied only when no `@latex` annotation overrides it. Authors are encouraged to supply `@latex` annotations for non-standard or domain-specific notation.

**Formula numbering.** Display equations in theorem statements are numbered automatically in the HTML output. The numbering is `(chapter.section.item)`, where `item` is the sequential index of the display equation within the item's documentation page. Formula numbers are hyperlinked and can be referenced with `$$\text{see }(24.3.1)$$` syntax in documentation comments.

## 24.4 HTML Output

The documentation generator writes a static HTML site to the directory specified by `doc_dir` in the package manifest (default: `docs/`).

The HTML output is a static site suitable for hosting on any web server or GitHub Pages. It uses **KaTeX** for client-side mathematical formula rendering, requiring no server-side processing.

Directory structure of the HTML output:

```
docs/
├── index.html           ← package overview and module list
├── search.json          ← full-text search index
├── algebra/
│   ├── index.html       ← module index for `algebra`
│   ├── groups/
│   │   ├── basic.html   ← documentation for `algebra.groups.basic`
│   │   └── ...
│   └── ...
└── assets/
    ├── katex/           ← KaTeX library files
    ├── style.css
    └── search.js
```

**Module index page.** Each module's index page lists all exported items with their type signatures (rendered using `@latex` annotations where available), a one-line summary extracted from the first paragraph of the documentation comment, and links to the full item page.

**Item page.** Each named item has a dedicated page containing:
- The full type signature or theorem statement, rendered mathematically.
- The complete documentation comment, rendered as HTML.
- The `requires` and `ensures` clauses (for algorithms and functions), rendered mathematically.
- The `@param` and `@returns` tags formatted as a parameter table.
- An automatically generated "Used by" section (§24.2).
- The "See also" list from `@see` tags.
- A "Source" link to the relevant line in the source file (using the `source_range` from `*.mizir.json`).

**Search.** The generator produces a `search.json` index containing the FQN, item kind, one-line summary, and type signature for every exported item. The search UI (`search.js`) performs client-side full-text search over this index without requiring a backend.

**Versioned documentation.** When the package manifest includes a `version` field (§23.1), the generator embeds the version string in the page header and in `search.json`. Hosting infrastructure may use this to serve multiple versions concurrently; the standard layout places version-specific output under `docs/v2.3.1/`.
