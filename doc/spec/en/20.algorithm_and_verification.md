Mizar Evolution integrates **executable algorithms** with the formal proof system. An `algorithm` block defines a computation that can be:

- **Run** by the Mizar Virtual Machine (MVM) during verification (`by computation`).
- **Reasoned about** using Hoare-logic contracts (`requires`, `ensures`, `invariant`).
- **Promoted** to a mathematical functor (`func`) when total correctness is established (via `terminating`).

The design follows the principle of **partial correctness by default**: an algorithm is permitted to diverge unless an explicit termination argument is given. This avoids demanding termination proofs for algorithms that are only ever used on concrete inputs or in bounded contexts.

## 20.1 Algorithm Syntax

### 20.1.1 Algorithm Definition Block

An algorithm must be declared **inside a `definition` block**. The surrounding `let` declarations bind the type context; the algorithm's parameter list selects which of those bindings become formal parameters.

As a `definitional_item` (§12.5), an algorithm obeys the usual `public` / `private` visibility rules; omitting the modifier means `public`. A public algorithm exposes its signature and `requires` / `ensures` contracts and, when computable, is available for cross-package MVM evaluation through a verified runtime artifact (§20.9.1). No separate computational-export modifier is required. Visibility alone proves neither computability nor termination. Implementation compatibility follows §23.2.

```ebnf
algorithm_def ::= ( "terminating" "algorithm" [ label_identifier ":" ] | "algorithm" ) identifier [ "[" schema_params "]" ] "(" [ identifier_list ] ")" [ "->" type_expression ]
                  [ "requires" formula ]
                  [ "ensures"  formula ]
                  [ "decreasing" term_list ]
                  algorithm_body ";" ;

schema_params    ::= identifier { "," identifier } ;
identifier_list  ::= identifier { "," identifier } ;

algorithm_body   ::= "do" algo_statement_list "end" ;
```

The `[ "->" type_expression ]` is optional: algorithms with no return type are **void** (procedures). The optional `[ "decreasing" term_list ]` declares the recursion termination measure (§20.5.2) at the header level; for loop termination see §20.2.2.

An algorithm name is always an `identifier`. Algorithm declarations do not
introduce lexer user-symbol dictionary entries. A terminating algorithm may be
promoted to a callable functor semantically (§20.7.2), but that promotion does
not create a new operator-like spelling; use a functor synonym (§11.1.2) or an
ordinary `func` definition when mathematical notation is required.

**Template algorithms.** `algorithm_def` is a valid `template_item` (§18.2.1). When the enclosing `definition` block declares schema parameters — **type** (`let T be type`), **pred** (`let P be pred(...)`), or **func** (`let F be func(...) -> ...`) — those parameters may be referenced in the algorithm body and in `requires`/`ensures` clauses. The algorithm name takes a `[...]` bracket suffix listing the schema parameters, following the same convention as schema theorems (§18.8.4). Instantiation is performed at each call site by supplying concrete type, pred, or func names in the brackets.

```mizar
definition
  let n be Nat;

  terminating algorithm FactorialDef: factorial(n) -> Nat
    ensures result >= 1
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    return n * factorial(n - 1);
  end;
end;
```

The `terminating` modifier (§20.7.2) declares that the algorithm terminates for all inputs satisfying `requires`. It is optional — algorithms without `terminating` are treated as partially defined and cannot be used as first-class functors.

```ebnf
algorithm_application ::= identifier [ template_args ] "(" [ algorithm_inputs ] ")" ;
algorithm_inputs ::= expr_input { "," expr_input } ;
expr_input ::= term_expression | formula | label_identifier | "thesis" ;
```
This contextual argument grammar connects algorithm calls to their expected
parameter types: formulas/labels/thesis are admitted only for expr of boolean.
Other parameters use ordinary term arguments; formulas do not become terms.
`thesis` placement and label citation follow §16.5.1. R1/R2/R3 follow §20.5.3.

### 20.1.2 Parameters and Return Type

Parameters are positional and **immutable** within the algorithm body (they behave as `const`). To use a mutable version of a parameter, create a `var` copy:

```mizar
definition
  let x be Nat;

  algorithm copy_and_modify(x) -> Nat
  do
    var y := x;
    y := y + 1;
    return y;
  end;
end;
```

The return type specifies the type of every `return` expression. The special identifier `result` in `ensures` clauses refers to the return value:

```mizar
definition
  let n be Integer;

  algorithm abs_val(n) -> Nat
    ensures result >= 0
  do
    if n >= 0 do
      return n;
    end;
    return -n;
  end;
end;
```

### 20.1.3 Variable Declarations (`var`, `const`)

Inside an algorithm body, variables are introduced with `var` (mutable) or `const` (immutable). **Ghost variables** (`ghost var`, `ghost const`) exist only at the specification level and are erased at extraction time.

```ebnf
var_decl         ::= "var"         var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
ghost_var_decl   ::= "ghost" "var" var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
const_decl       ::= "const"       const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;
ghost_const_decl ::= "ghost" "const" const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;

var_binding   ::= identifier [ ":=" term ] ;
const_binding ::= identifier ":=" term ;

justification ::= simple_justification | proof | computation_proof ;
(* simple_justification, proof, computation_proof, reasoning, references — defined in §15/§16/§20.9.2 *)
```

| Keyword | Mutability | Runtime | Use case |
|---|---|---|---|
| `const` | Immutable | Yes | Intermediate results, captured values, picks |
| `var` | Mutable | Yes | Loop counters, accumulators, state |
| `ghost const` | Immutable | No (spec only) | Proof witnesses, specification values |
| `ghost var` | Mutable | No (spec only) | Proof tracking (visited sets, abstract state) |

**Cast rules between variable kinds.** The four kinds form a hierarchy from most concrete to most abstract. A value of a more concrete kind may be used wherever a more abstract kind is expected; the reverse is forbidden.

| From \ To | `const` | `ghost const` | `ghost var` |
|---|---|---|---|
| `var` | ✓ (current value, read-only) | ✓ | ✓ |
| `const` | — | ✓ | — |
| `ghost var` | ✗ | ✓ (current value) | — |
| `ghost const` | ✗ | — | — |

The upward direction (concrete → ghost) is always safe: reading a runtime value in a specification context does not affect execution. The downward direction (ghost → runtime) is always forbidden: a ghost value has no runtime representation and cannot be assigned to a non-ghost variable or passed to a non-ghost call.

Ghost variables may appear only in **specification contexts**: `invariant`, `ensures`, `requires`, and `assert`. They may not appear on the right-hand side of non-ghost assignments, and may not be passed to non-ghost algorithm calls.

The verifier checks that ghost variables do not influence runtime behaviour. The extractor silently removes all ghost declarations and ghost assignments.

```mizar
definition
  let S be finite set of Integer;

  algorithm find_min(S) -> Integer
    requires S <> {}
    ensures result in S & for x being Integer st x in S holds result <= x
  do
    ghost var visited := {} as set of Integer;
    var current := S;
    var best := the Element of S;
    while current <> {} do
      invariant visited = S \ current;
      invariant best in S & for x being Integer st x in visited holds best <= x;
      decreasing card current;
      const x := the Element of current;
      if x < best do best := x; end;
      visited := visited \/ {x};       :: ghost update — erased at extraction
      current := current \ {x};
    end;
    return best;
  end;
end;
```

The optional `as T` annotation corresponds to Mizar's `reconsider x = e as T`: it asserts that the initializer expression has type `T`. Widening coercions (e.g. `Nat` to `Integer`) and disambiguation of overloaded literals (e.g. `0 as Real`) are resolved automatically by the type hierarchy and require no proof. Narrowing coercions (e.g. `Integer` to `Nat`) generate a proof obligation; if the automatic prover cannot discharge it, supply a justification (`by` or `proof ... end`):

```mizar
var n := some_int as Nat by non_negative_lemma;
var m := some_int as Nat
proof
  some_int >= 0 by ...;
  thus some_int is Nat;
end;
const r := 0 as Real;             :: automatic — no justification needed
```

If the annotation is omitted entirely, the type is inferred from the initializer expression (see [Chapter 8, Type Inference](./08.type_inference.md)).

**Multiple bindings** may appear in a single `var` or `const` statement. A trailing `as T` annotation applies to all bindings in the statement. If individual bindings require different type annotations or justifications, use separate statements.

```mizar
var a := 1, b := 2 as Nat;          :: two vars, both typed Nat
const lo := 0, hi := n - 1 as Nat;   :: two constants, shared type
```

**Uninitialized bindings** (no `:=`) leave the variable without a value; the verifier rejects any use before assignment — except as pattern variables in a `match` statement (§20.2.5), where the `match` itself provides the initial assignment on a successful case:

```mizar
var p, q, r as Element of PolyRing[K,x];  :: uninitialized; valid as match pattern variables
match t do
  case p * (q + r) do  :: p, q, r are assigned here
    ...
  end;
  otherwise
    ...
  end;
end;
```

### 20.1.4 Assignment

Mutable variables are updated with `:=`:

```ebnf
assignment ::= lvalue ":=" term ";" ;
lvalue     ::= identifier
             | lvalue "." identifier ;
```

The right-hand side is any term expression. The left-hand side must be a `var`-declared identifier or a field thereof. Assigning to a `const` identifier, a `let`-bound variable, or a parameter is a **compile-time error**.

The right-hand side is evaluated in the pre-state of the assignment. For VC
generation, an assignment is not modeled by textual substitution in the
accumulated facts. Instead, the verifier introduces fresh old-state names for
the mutable locations that may change, preserves facts whose free locations
cannot alias the target, and adds the post-state equality. For example,
`x := x + 1` records an old value `x₀` for the pre-state and adds
`x = x₀ + 1`; it does not rewrite an existing fact `x = 5` into
`x + 1 = 5`. Field updates use the same old-state discipline: `p.f := e`
evaluates both `p` and `e` in the pre-state and then updates the resolved
lvalue identity for `p.f`.

Aliases in this section mean multiple resolved lvalue paths for the same
mutable storage cell, not reference semantics for ordinary values. Assigning
`var y := x` copies the value of `x`; it does not make `y` an alias of `x`.

Assignments to `ghost var` identifiers use the same `:=` syntax; the verifier determines from the declaration that the target is a ghost variable. Assigning a `ghost var` or `ghost const` value to a non-ghost variable is a **compile-time error** — ghost values have no runtime representation and must not influence non-ghost state.

```mizar
counter := counter + 1;              :: runtime assignment
state.value := state.value + 1;      :: field update
S_visited := S_visited \/ {x};       :: ghost assignment — legal, target is ghost var
counter := S_visited;                :: compile-time error — ghost value on rhs of non-ghost assignment
```

## 20.2 Control Flow

### 20.2.1 Conditional (`if`)

```ebnf
if_stmt ::= "if" formula "do" algo_statement_list if_tail ;
if_tail ::= "end" ";"
          | "else" if_stmt
          | "else" algo_statement_list "end" ";" ;
```


```mizar
if n = 0 do
  return 1;
end;

if n mod 2 = 0 do
  return n div 2;
else
  return 3 * n + 1;
end;

:: if-else-if chain
if n < 0 do
  return -1;
else if n = 0 do
  return 0;
else
  return 1;
end;
```

Both branches must return the same type when `return` is used, or both must fall through to subsequent statements.

### 20.2.2 Bounded Loop (`while`)

```ebnf
while_stmt ::= "while" formula "do"
                 { while_annotation ";" }
                 algo_statement_list
               "end" ";" ;

while_annotation ::= "invariant" formula [ justification ]
                   | "decreasing" term_list [ justification ] ;
```

`while_annotation` clauses (`invariant`, `decreasing`) appear at the **top** of the `while` body, before any other statements. The optional `justification` supplies lemmas for the verification conditions generated by the clause: establishment and maintenance for `invariant`, strict decrease for `decreasing`.

```mizar
var i := 1;
var s := 0;
while i <= n do
  invariant s = i * (i - 1) div 2 & i >= 1 by arithmetic, triangle_step;
  decreasing n - i + 1 by arithmetic;
  s := s + i;
  i := i + 1;
end;
```

### 20.2.3 Range Loop (`for ... to`)

```ebnf
for_range_stmt ::= "for" identifier "=" expr ( "to" | "downto" ) expr
                   [ "step" expr ]
                   "do" { for_annotation ";" } algo_statement_list "end" ";" ;

for_annotation ::= "invariant" formula [ justification ] ;
```

The loop variable is immutable within the body and scoped to the loop. Bounds and step are evaluated once before the loop begins. The `step` expression must be a positive `Nat` value; the default step is `1`.

- `for i = 1 to n` — iterates i = 1, 2, …, n (ascending).
- `for i = n downto 1` — iterates i = n, n−1, …, 1 (descending).
- `for i = 0 to n step 2` — iterates i = 0, 2, 4, … (ascending by 2).
- `for i = n downto 0 step 3` — iterates i = n, n−3, … (descending by 3).

```mizar
var s := 0;
for i = 1 to n do
  s := s + i;
end;

for i = 10 downto 1 do
  process(i);
end;

:: Every other element, descending
for i = n downto 1 step 2 do
  handle(i);
end;
```

Termination is **automatically guaranteed** — no `decreasing` annotation is needed. An optional `invariant` clause may be placed at the top of the body to assist verification of the loop's accumulated effect:

```mizar
var s := 0;
for i = 1 to n do
  invariant s = i * (i - 1) div 2;
  s := s + i;
end;
```

### 20.2.4 Collection Loop (`for ... in`)

```ebnf
for_collection_stmt ::= "for" identifier "in" expr [ "processed" identifier ] "do"
                          { for_annotation ";" }
                          algo_statement_list
                        "end" ";" ;
```

Iterates over all elements of a **finite set**. The verifier requires the collection expression to have type `finite set of T` (or a type registered as `finite`). Finite sequences are also supported: visit positions 1 through len S in order, preserving duplicates. The existing processed-set rules below apply only to sets; sequence invariants follow successive positions. Generalizing processed bindings to sequences is deferred. Ghost collections cannot bind non-ghost elements.

**Iteration order is implementation-defined.** For sets the loop makes no guarantee about visitation order; sequences use position order.

**The `processed` binding.** When the optional `processed V` clause is present, `V` is a **loop-scoped ghost binding** of type `set of T`, managed automatically by the loop:

- Before the first iteration: `V = {}`
- After each iteration of element `x`: the loop implicitly extends `V` with `{x}`
- On normal exit: `V = S` is added to the logical context automatically
- `V` is erased at extraction time (no runtime representation)
- If `processed` is omitted, no tracking binding is created

The user names `V` freely and uses it in `invariant` clauses.

**Invariant verification.** The verifier checks the standard three conditions using the loop-managed `V`:

1. **Establishment** — invariant holds with `V = {}`
2. **Maintenance** — for an arbitrary `x ∈ S \ V`, if the invariant holds before the body, it holds after the body (with `V` extended by `{x}`)
3. **Post-condition** — on normal exit, `V = S` and the invariant give the final result

Because condition 2 uses an **arbitrary** `x ∈ S \ V`, the proof never assumes a particular enumeration order. Order-independence is implicit in the invariant being stated in terms of the set `V`, not a sequence.

The iteration order itself is unspecified. An algorithm that contains an unordered **set** `for ... in` loop can therefore be evaluated by `by computation` only when its `ensures` determines its result uniquely (§20.9.2).

**`Fold` template and set functors.** The standard way to express order-independent accumulation is via the **`Fold` template algorithm** (§20.1.1), which abstracts the recursive structure of set-valued computation:

```mizar
:: Conceptual definition of the Fold template algorithm
:: Fold[op, e](S) for a commutative, associative op with unit e
::
:: terminating algorithm Fold[op, e](S) -> T
::   ensures (S = {} implies result = e)
::         & (for x being object st x in S holds
::              result = op(x, Fold[op, e](S \ {x})))
::   decreasing card S
:: do
::   if S = {} do return e; end;
::   const x := the Element of S;
::   return op(x, Fold[op, e](S \ {x}));
:: end;
::
:: The ensures clause applies Fold only to smaller sets (§20.4.1). Proving
:: it for every x in S, not only for the chosen one, is the
:: order-independence argument: for x ≠ y in S,
::   op(x, op(y, Fold[op,e](S\{x,y})))
::   = op(y, op(x, Fold[op,e](S\{x,y})))  :: by commutativity and associativity of op
:: using the induction hypothesis for S\{x} and S\{y} (§20.13.4).
```

Because the `ensures` clause of `Fold` holds for every choice of `x`, it determines the result uniquely; this is exactly order-independence. It is proved once at the template level from commutativity and associativity of `op`, all instantiations inherit it, and `by computation` may evaluate `Fold` despite its Pick site (§20.9.2).

Standard library set functors are pre-defined instances of `Fold`:

```mizar
:: Sum(S)              = Fold[+, 0](S)
:: Product(S)          = Fold[*, 1](S)
:: BigUnion(F, S)      = Fold[∪, {}](S)    (element mapped by F)
:: BigIntersection(F, S) = Fold[∩, univ](S) (element mapped by F)
:: Count(S, P)      = Fold[+, 0](S)     (element mapped to 1 if P holds, else 0)
```

Users who need a custom accumulation define their own `Fold` instance and cite the commutativity/associativity of their operation to discharge the `ensures` obligation.

```mizar
:: Sum of elements — processed V tracks the accumulated set.
var total := 0;
for x in S processed V do
  invariant total = Sum(V);
  total := total + x;
end;
:: After normal exit: V = S (automatic), so total = Sum(S).

:: Product of elements.
var prod := 1;
for x in S processed V do
  invariant prod = Product(V);
  prod := prod * x;
end;

:: Existence check — no accumulator; visited clause not needed.
for x in S do
  if x mod 2 = 0 do
    return x;
  end;
end;
```

If the loop body has genuine order dependence (no commutative characterisation exists), `for ... in` is the wrong construct. Use `for ... to` over an explicitly ordered structure instead.

> [!NOTE]
> If `return` or `break` exits the loop early, the context contains `V c= S` and whatever the invariant states about `V`. The post-condition `V = S` is only guaranteed on **normal** exit.

### 20.2.5 AST Pattern Match (`match`)

The scrutinee must have type `expr of T`; matching uses its immutable
structure and resolved definitions, never algebraic or semantic equality.
`=` on captured syntax objects is structural object identity (§20.5.3).

```ebnf
match_stmt ::= "match" expr "do" match_case+
               [ "otherwise" algo_statement_list "end" ";" ] "end" ";" ;
match_case ::= "case" term_pattern "do" algo_statement_list "end" ";" ;
term_pattern ::= term_expression | formula ;
```

Capture names are immutable branch-local bindings. No preceding `var`
declaration is required when their expr types are uniquely inferred.
Non-linear captures require structurally identical subobjects. Typed syntax
views use expr covariance without erasing original types/context. Dedicated
pattern-variable type-annotation syntax remains deferred.
Cases are tried in order; the first match executes. Node forms are open-ended:
`otherwise` is the only exhaustiveness mechanism, with no `exhaustive` or
`exhaustiveness_proof`. It is mandatory for terminating algorithms (E0503).
In partial algorithms omission means `otherwise fail "no case matched", e; end;`.
Opaque leaf internals are not decomposed. Binder capture follows §13.10.

### 20.2.6 Jump Statements (`return`, `break`, `continue`, `fail`)

```ebnf
return_stmt   ::= "return" [ expr [ justification ] ] ";" ;
break_stmt    ::= "break" ";" ;
continue_stmt ::= "continue" ";" ;
fail_stmt     ::= "fail" [ string_literal { "," expr } ] ";" ;
```

| Statement | Effect | Verification obligation |
|---|---|---|
| `return expr` | Exit algorithm with value `expr` | `expr` must satisfy `ensures`; preconditions of any tail call are discharged |
| `return expr by ...` | Shorthand for `assert` + `return` (§20.4.2) | Same as `return expr`, with the justification applied to the `ensures` discharge |
| `return` | Exit a void algorithm | All `ensures` conditions must hold |
| `break` | Exit the immediately enclosing loop | Loop `invariant` must hold at break point |
| `continue` | Skip to the next loop iteration | Loop `invariant` must hold; **`decreasing` measure must have decreased** relative to the start of the current iteration |
| `fail` | Stop the evaluation with a runtime verification failure (§20.9.3) | None |

**Every path returns.** In an algorithm with a return type, every control path through the body must end in a `return` or `fail` statement. Reaching the end of the body without either, including after a loop exits, is a static error (E0501, §22.5.5). A void algorithm may reach the end of its body, which is equivalent to `return;`.

**`fail` — explicit runtime failure.** `fail` stops the evaluation without a result. The MVM reports a runtime verification failure (§20.9.3, E0331) that shows the optional message and the values of the listed expressions. The path that reaches `fail` neither returns nor produces a value, so it has no verification condition and needs no `ensures` proof. The listed expressions must be non-ghost; they are evaluated only by the MVM, for the report.

`fail` may appear only in an algorithm that is not `terminating`, and not inside a `ghost` statement or a specification formula. A `terminating` algorithm must return on every input satisfying `requires`, so a `fail` there is an error (E0503, §22.5.5). No construct catches a failure; it ends the whole evaluation.

```mizar
definition
  let a, b be Integer;

  algorithm exact_div_algo(a, b) -> Integer
    ensures result * b = a
  do
    if b = 0 do fail "division by zero"; end;
    if a mod b <> 0 do fail "not divisible:", a, b; end;
    return a div b by ...;
  end;
end;
```

**`continue` and termination.** Because `continue` bypasses the end of the loop body where the termination check normally occurs, the verifier checks that the `decreasing` measure has **already decreased** at the `continue` point. If no `decreasing` annotation is present, `continue` generates no termination obligation (the loop is treated as potentially diverging).

```mizar
:: continue: the decreasing measure must have already decreased at the continue point.
while i <= n do
  invariant s = sum_of_odds_up_to(i - 1);
  decreasing n - i + 1;
  if i mod 2 = 0 do
    i := i + 1;
    continue;  :: n - (i + 1) + 1 < n - i + 1 already holds before continue
  end;
  s := s + i;
  i := i + 1;
end;
```

## 20.3 Non-determinism (Pick)

A **Pick** operation selects an arbitrary element from a non-empty set, expressed using Mizar's existing `the` term forms. These are not new Chapter 20-specific expressions: they remain part of the general `term_expression` syntax (Chapter 13), exactly as in classical Mizar. In this chapter we use the name **Pick** only for the algorithmic semantics of Mizar's existing `the`-expressions.

```mizar
const x := the Element of S;    :: pick any element of S
const p := the prime Number;     :: pick any prime
```

**Semantics.** Outside executable algorithm bodies, `the` is the stable choice
term defined in [Chapter 13, §13.5](./13.term_expression.md#135-the-choice-operator-the).
Inside an algorithm body, a statement right-hand side that contains `the T` is
lowered to a site-local Pick binding in `ControlFlowIr`. This includes
`const`/`var` initializers and later assignments. The logical VC treats the
binding as an arbitrary fresh value satisfying the membership or type predicate,
and the MVM selects one concrete value non-deterministically at runtime when the
binding feeds non-ghost state. A Pick binding that feeds only ghost state is
specification-only and is erased with the ghost state; it still creates the same
non-emptiness obligation and may not flow into non-ghost computation. Algorithm
specification formulas (`requires`, `ensures`, `assert`, `invariant`, and
`decreasing`) use the stable choice semantics of Chapter 13 instead of creating
runtime Pick sites. The surrounding proof system observes only the algorithm
contract, not the internal generated choice name. Each Pick site introduces its
own fresh binding unless the program explicitly stores the result in a variable
and reuses that variable.

**Proof safety.** The contracts of an algorithm (`requires`, `ensures`) are the only interface visible to the surrounding proof system. An `ensures` clause that mentions a Pick result must hold for **every** possible choice; the verifier generates a proof obligation to that effect. Properties not stated in `ensures` cannot be assumed by callers regardless of the choice made. This containment guarantees that non-determinism inside an algorithm cannot silently weaken external proofs.

**Computation restriction.** Because the MVM chooses Pick values non-deterministically, an algorithm that contains a non-ghost Pick site can be evaluated by `by computation` only when its `ensures` determines its result uniquely (§20.9.2). Otherwise its relational contract remains meaningful, but promotion/function-symbol introduction still requires E1 single-valuedness (§20.13.1).

**Non-emptiness obligations.** The verifier generates a non-emptiness obligation at each Pick site, but its form differs by variant:

- *Set-based* (`the Element of S`): the obligation `S <> {}` is a verification condition discharged by proof. If it cannot be discharged statically, a partial algorithm has an implicit `fail` on a non-ghost unsupported path; ghost-only Pick still requires static discharge because ghost cannot fail; a `terminating` algorithm is rejected (E0503). A runtime check cannot replace its normal-return obligation.
- *Type-based* (`the prime Number`): the obligation is that the type is **inhabited** — i.e., there exists at least one term of that type. This is a standard Mizar type-inhabitation obligation discharged statically; no runtime check is needed.

```mizar
definition
  let S be finite set of Integer;

  terminating algorithm check_even_exists(S) -> boolean
    ensures result = true iff ex y being Integer st y in S & y mod 2 = 0
  do
    var current := S;
    while current <> {} do
      invariant current c= S;
      invariant for y being Integer st y in S \ current holds y mod 2 <> 0;
      decreasing card current;
      const x := the Element of current;
      if x mod 2 = 0 do
        return true;
      end;
      current := current \ {x};
    end;
    return false;
  end;
end;
```

> [!NOTE]
> Whether a Pick expression can be executed by the MVM depends not on finiteness but on whether the MVM can produce a concrete witness at runtime:
> - `the Element of S` where `S` is a finite set known at runtime: the MVM can enumerate `S` and select an element — **executable**.
> - `the prime Number`: if the Mizar library registers a computable canonical representative (e.g., `2`), the MVM can use it — **executable**.
> - A type or set for which no algorithm can produce a concrete element in finite time: **not executable**. For example, `the Element of S` where membership in `S` is undecidable.
>
> Non-executable Pick expressions are still mathematically sound in algorithm definitions and may be used in proofs where only the logical specification (contracts) matters. An algorithm containing a non-executable Pick cannot be promoted to `terminating`.

R1 syntax-input reflection of a `the` expression saves an opaque leaf;
it does not execute a runtime Pick. The Pick rules above concern runtime
value computations, with specification-only ghost obligations kept separate.

## 20.4 Contracts (`requires`, `ensures`, `assert`)

### 20.4.1 Preconditions and Postconditions

- `requires P` — `P` must hold at every call site. The algorithm body may assume `P`.
- `ensures Q` — `Q` holds upon normal termination. `result` in `Q` refers to the return value.

The `requires` and `decreasing` clauses of an algorithm must not apply the algorithm itself or another member of its recursive group (§20.8.2), because the domain and the measure must not depend on the function being defined. An `ensures` clause may apply them only when the algorithm and every member of its recursive group are declared `terminating` (§20.7.2), so that each application denotes a value of a promoted functor. In the algorithm's own verification, the contract is assumed only at arguments whose header `decreasing` measure (§20.5.2) is strictly smaller, as the induction hypothesis of §20.13.4. Nothing is assumed about the current arguments, and nothing at all when no header measure is declared. Other self-reference is rejected (E0502, §22.5.5).

Each clause appears at most once, in the fixed order `requires` → `ensures` → `decreasing`. Multiple conditions within a clause are expressed using `&` or `and`:

```mizar
definition
  let a, b be Real;

  algorithm divide(a, b) -> Real
    requires b <> 0
    ensures result * b = a
  do
    return a / b;
  end;
end;
```

Contracts are **proof obligations**:
- At each call site `divide(x, y)`, the verifier demands a proof that `y <> 0`.
- After `return v`, the verifier demands a proof that `v * b = a`.

If the automatic prover cannot discharge an obligation, the user adds an `assert` (§20.4.2) with a justification (`by` or `proof ... end`) at the relevant site.

### 20.4.2 Inline Assertions

```ebnf
assert_stmt ::= "assert" formula [ justification ] ";" ;
```

`assert P` inserts a proof checkpoint: the verifier must establish `P` at that program point, using the current logical context plus any cited lemmas or an inline proof.

**`return expr by ...` — inline assertion shorthand.**
When a `return` carries a justification, it is syntactic sugar for an `assert` that discharges the `ensures` postcondition for `expr`, followed by the `return`:

```mizar
  ensures result = a
do
  ...
  return b by th1;   :: sugar for: assert a = b by th1; return b;
  ...
```

The asserted formula is the `ensures` clause with `result` substituted by the returned expression.  Using a full `proof ... end` block is also allowed:

```mizar
  return b
  proof
    ...
  end;
```

```mizar
definition
  let arr be FinSequence of Real;
  let lo, hi, target be Integer;

  algorithm binary_search(arr, lo, hi, target) -> Integer
  do
    var l := lo;
    var r := hi;
    while l <= r do
      invariant lo <= l & r <= hi;
      decreasing r - l + 1;
      const mid := (l + r) div 2;
      assert l <= mid & mid <= r by arithmetic;
      if arr.mid = target do
        return mid;
      else if arr.mid < target do
        l := mid + 1;
      else
        r := mid - 1;
      end;
    end;
    return -1;
  end;
end;
```

### 20.4.3 Verification Obligations

| Construct | Obligation |
|---|---|
| Call site `f(args)` | `requires` preconditions of `f`, instantiated with `args` |
| `return expr` | `ensures` postconditions, with `result` bound to `expr` |
| `assert P` | `P` holds at that program point |
| `break` inside loop | loop `invariant` holds at break point |
| `continue` inside loop | loop `invariant` holds at continue point; `decreasing` measure has already decreased relative to start of current iteration |
| `fail` | none; not permitted in a `terminating` algorithm |
| unordered set `for x in S` with mutable state | loop `invariant` must be stated in terms of a set-based functor (via `ghost var`), proving result is order-independent |
| `for x in S` | `S` is `finite` |
| `the Element of S` | `S <> {}` |
| `decreasing e` (loop) | `e` is `Nat`-valued; `e` decreases strictly on each loop iteration |
| `decreasing e` (header) | `e` is `Nat`-valued; `e` decreases strictly on each recursive call |
| `terminating` | all `decreasing` measures are valid; algorithm returns on all inputs satisfying `requires` |

## 20.5 Loop Verification

### 20.5.1 Loop Invariants (`invariant`)

A loop invariant must hold:
1. **Before** the first iteration (establishment).
2. **At the loop head on every subsequent iteration** (maintenance).
3. **On normal exit** — when the loop condition becomes false.
4. **At every `break` statement** — the invariant must hold at the break point.
5. **At every `continue` statement** — the invariant must hold at the continue point (the loop will re-enter from the top).

```mizar
var i := 1;
var s := 0;
while i <= n do
  invariant s = (i - 1) * i div 2;
  decreasing n - i + 1;
  s := s + i;
  i := i + 1;
end;
:: After loop: i = n + 1, s = n * (n + 1) div 2
```

Multiple `invariant` clauses are interpreted as a conjunction.

### 20.5.2 Termination Measure (`decreasing`)

```ebnf
(* loop termination — inside while body, via while_annotation *)
(* while_annotation ::= "invariant" formula | "decreasing" term_list ; *)

(* recursion termination — in algorithm header *)
(* algorithm_def ::= ... [ "decreasing" term_list ] algorithm_body ";" ; *)

term_list ::= term_expression { "," term_expression } ;
```

The `decreasing` annotation is used in two distinct positions:

- **Algorithm header** (`[ "decreasing" term_list ]` in `algorithm_def`) — declares the recursion termination measure; the tuple must decrease on every recursive call.
- **`while` body** (`while_annotation`) — declares the loop termination measure; the tuple must decrease on every iteration.

The `for` loop does **not** accept `decreasing` — iteration over a finite set is guaranteed to terminate by the finiteness obligation.

In both positions the verifier generates the same obligations:

1. Every expression in the list is **`Nat`-valued** (non-negative integer).
2. The tuple **decreases lexicographically** on every loop iteration or recursive call.

| Form | Ordering | Example |
|---|---|---|
| `decreasing e` | `<` on `Nat` | `decreasing n - i` |
| `decreasing e, f` | Lexicographic `<` on `Nat × Nat` | `decreasing m, n` |

For a custom well-founded ordering, map the measure to `Nat` via a user-defined functor before using `decreasing`:

```mizar
:: User-defined measure mapping a tree to its depth (a Nat)
const d := tree_depth(t);
decreasing d;
```

The non-negativity obligation (`e >= 0`) is discharged at the definition site. If the automatic prover cannot establish it, add an `assert`:

```mizar
assert n - i >= 0 by arithmetic;
decreasing n - i;
```

#### Structure, construction and measures (S1–S7)

`expr` objects are immutable finite acyclic structures; DAG sharing is allowed.
Internal notation Var(κ), Node_f(args), Opaque(e), Abs(κ,A,B,b) is explanatory,
not public constructors or a UID API. Structural `=` compares node kind,
resolved definition, literal payload, opaque saved elaborated original,
ordered substructure and declaration UID. Alpha-renaming changes the tree;
semantic equality is separate. Sharing, cache, storage and diagnostic locations
are excluded; equal children/FV alone do not identify opaque leaves.

R1 reflects a T term in expected expr of T (a formula in expr of boolean).
R2 embeds an existing expr object with its free UIDs and required context.
R3 builds resolved func/pred nodes, reflecting ordinary args and embedding expr
args in complete formal order. Algorithm applications always execute, including
promoted terminating algorithms; returned trees embed by R2. Type widening
retains original types, UIDs and necessary conditions. Meaning uses explicit
`val`; R2 construction code is not automatically a mathematical source term.

| Kind | Executable `expr_children(t)` | FV and exact ghost `expr_size(t)` |
|---|---|---|
| Var(κ) | empty sequence | FV={κ}; size=1 |
| Variable-independent atomic constant/literal | empty sequence | FV={}; size=1 |
| Node_f(a1,…,an) | args in complete formal order, duplicates kept | union of child FV; 1 + sum of size at each child position |
| Opaque(e) | Var of semantic FV, elaborated first-occurrence order, UID deduplicated | saved semantic FV; 1 + cardinality FV |
| Abs(κ,A,B,b) | A,B,Var(κ),b, duplicates kept | FV(A)∪FV(B)∪(FV(b)−{κ}); 2+size A+size B+size b |

`expr_children` is a non-ghost pure executable operation returning
FinSequence of expr of object, usable in bodies and contracts. Retrieval/match
preserves stored UIDs and each child's original type/context; declaration,
attribute, environment, proof, parent and cache links are not structural edges.
For Abs, A/B use the outer context; Var(κ)/b keep the extended body context.
`t is variable iff ex κ st t=Var(κ)` is an executable structural property,
not permission to assign a value or reconstruct a Binder. For non-variable t,
FV(t) ⊆ union of child FV; the declaration child can overapproximate dependence.

`expr_size(t)=1+Σ_i expr_size(expr_children(t).i)` counts unfolded occurrences,
not allocated nodes. Each child is strictly smaller, so structural induction
and recursive termination use this lemma. Any other recursive argument is also
allowed if the **selected** measure strictly decreases and other obligations
hold. MVM need not recompute a verified decreasing size at every call.
Concrete sizes use exact naturals without overflow, saturation or rounding;
sharing/caching may avoid materializing the unfolded tree. Resource exhaustion
leaves the operation incomplete. Finite structure alone proves neither
consistency of meaning rules nor termination of arbitrary definition rewriting.
`expr_size` is ghost; val/val_at/valid_at are ghost (§20.5.3 meaning rules).
Ghost values cannot drive ordinary conditions, returns, iteration counts or
non-ghost sequence elements; no ghost-sequence traversal exception exists.
A library evaluator may compute only supported syntax using ordinary operations
and prove result=val t; finite/closed/Nat syntax alone is not a universal evaluator.

#### Meaning, environments and valuation (M1–M8)

A retained context Γ records original declarations, types/attributes,
application/dependency conditions and necessary verified type-view premises.
Adm_Γ(ρ) means their satisfaction in environment ρ. Semantic FV concerns the
value expression: y:Element of A(x) has FV={y}; its dependency on x remains
in Adm. No public environment type or substitution API is introduced.

`t:expr of T` has `val t:ghost const T`, meaning internal Val(t,ρ) in the
current compatible logical environment. For a formula tree p the proposition
is `val p=true`; val p is a boolean **term**, not an FOL formula.

| Rule | Meaning and conditions |
|---|---|
| M1 | Val(Var(κ),ρ)=ρ(κ). Val(Node_f(p1,…,pn),ρ)=f(Val(p1,ρ),…); for pred P, Val(Node_P(args),ρ)=true iff P(Val(args),…). Include implicit values, resolved signature and application conditions. Logical nodes use the corresponding truth conditions (&,or,not,implies,iff). |
| M2 | Pure R1 of term e satisfies Val(t,ρ)=⟦e⟧ρ; pure formula P satisfies Val(t,ρ)=true iff ⟦P⟧ρ. R2 keeps the inserted object's meaning: mixed sin p means sin(Val(p,ρ)), not the AST p as a Real. |
| M3 | Opaque(e) has its saved elaborated term's meaning; Opaque(P) has true iff its saved formula holds. Keep free UIDs and typing context, even for quantified formulas; opacity restricts structural decomposition, not truth conditions. |
| M4 | Binder meaning uses internal extended environments and certified function construction (§13.10), including empty domain. |
| M5 | For variable node x with UID i and a common compatible Γ: Adm_Γ(ρ) implies (valid_at(t,x,v) iff Adm_Γ(ρ[i↦v])). Interpret v **before** updating. Retain original type/attributes, dependent declarations/applications and necessary type-view premises. |
| M6 | `val_at[R](t:expr of R,x:expr of object,v:object)->ghost const R` denotes Val(t,ρ[i↦v]) only under current Adm and valid_at. R must be independent of i; widen a dependent return type only with a justified view, without erasing original constraints. |
| M7 | If i∉FV(t), two compatible environments agreeing outside i give equal meanings. Compatibility is required on both sides; the converse is not a structural non-occurrence rule. |
| M8 | Open-syntax contracts mean, for each ρ: Adm_Γ(ρ) & InputOK(args,ρ) & P_ρ(args) & returns_alg(args,r) implies Q_ρ(args,r). InputOK preserves correspondence of runtime values to logical inputs. |

In M8 args are the same complete input in execution, contracts, returns and
logical function symbols: syntax, ordinary values, required retained context
and any reconstruction C (§13.10). One environment's precondition does not
justify reuse in another. Entering Binder bodies requires new environment
correspondence and premises. Matching a body, including an empty-domain one,
does not establish an environment, a domain element or a concrete meaning.
A vacuously true universal contract cannot manufacture such values.

Public val_at requires variable-node/context compatibility and proof of the
updated conditions in its **local** context. valid_at may be stated or negated,
even when an update is invalid; it does not generate a value/environment.
Finite recorded conditions KΓ satisfy Adm_Γ(ρ) iff conjunction KΓ(ρ), with
row-specific generation following the classification table. Record only used
type/attribute/dependency/application/view premises, not every surrounding
assumption; quantified conditions remain finite formulas, never enumerations.
Expanding valid_at describes an equivalent condition, not its proof.
Quantified restrictions and implication guards retain those conditions locally;
do not require every candidate v to satisfy a guarded update unconditionally.

For dependent children, compose meanings with internal Val in the updated
environment; do not mechanically generate publicly ill-typed val_at on each
child. The substitution lemma for ordinary terms is
`⟦e[i:=w]⟧ρ = ⟦e⟧(ρ[i↦⟦w⟧ρ])` under both environments' compatibility;
for formulas use truth-condition equivalence. Replace free UID occurrences
only, capture-avoiding across binders and required type/domain references.
Other UIDs stay fixed; do not recursively substitute inside inserted w or
replace by display name. This lemma also handles opaque leaves with i in FV,
not merely the non-occurrence case. It requires the certified reflection range
and excludes unrestricted self-evaluation.

A check_occurs false contract states val/val_at/valid_at update invariance in
all compatible environments. Structural non-occurrence is an internal proof
lemma; true need not imply semantic dependence. Pointwise y=0 does not prove
invariance of y |-> y*x with respect to x. Verified type views require all-input
range proof and its retained premises; a single value observation is insufficient.

## 20.6 Snapshot and Claim

### 20.6.1 Snapshots

A **snapshot** records the complete local state of an algorithm at a specific program point. It is a specification-only construct: snapshots are erased at code extraction (§20.10) and incur no runtime cost.

```ebnf
snapshot_stmt ::= "snapshot" identifier ";" ;
```

A snapshot captures all bindings visible at that point — `var`, `const`, `ghost var`, `ghost const`, and algorithm parameters — under a single name. The snapshot name must be unique within the algorithm body.

### 20.6.2 Claim Blocks

A `claim` block groups theorems about the snapshot states of a single algorithm, expressing internal verification properties that go beyond what `requires`/`ensures` contracts alone can state.

```ebnf
claim_block ::= "claim" identifier "do"
                  { annotated_theorem_item }
                "end" ";" ;
annotated_theorem_item ::= { annotation } theorem_item ;
```

The identifier names the algorithm whose snapshots are brought into scope. Inside the block, snapshot variables are accessed as `S.x` (snapshot `S`, variable `x`).

**Universal quantification.** Every theorem in a `claim` block is implicitly
universally quantified over all valid executions — that is, over all calls
satisfying the algorithm's `requires` precondition. Reserved identifiers in the
theorem proposition are closed first according to §4.3, before this
execution-level quantification is applied.

**Snapshot semantics.** A snapshot captures the complete local state: all `var`, `const`, `ghost var`, and `ghost const` bindings visible at that program point, together with the algorithm parameters.

### 20.6.3 Example

The following algorithm counts from `0` to `n`. The snapshot `Init` captures the state before the loop; snapshot `S` captures the state at the top of each iteration.

```mizar
definition
  let n be Nat;

  algorithm count_up(n) -> Nat
    requires n >= 0
    ensures result = n
  do
    var x := 0;
    var i := 0;
    snapshot Init;
    while i < n do
      snapshot S;
      x := x + 1;
      i := i + 1;
    end;
    return x;
  end;
end;

claim count_up do
  :: state before the loop
  theorem InitState:
    Init.x = 0 & Init.i = 0;

  :: loop invariant: accumulator equals iteration counter at each step
  theorem Progress:
    S.x = S.i;
end;
```

`InitState` states that `x` and `i` are both zero before the loop begins. `Progress` states that at every iteration step the accumulator `x` equals the counter `i` — an internal property that `ensures result = n` alone does not capture.

## 20.7 Termination Proofs

### 20.7.1 Declaring a Termination Measure

For a recursive algorithm, `decreasing` is placed in the **algorithm header**, between the contracts and the body:

```mizar
definition
  let m, n be Nat;

  terminating algorithm ackermann(m, n) -> Nat
    decreasing m, n
  do
    if m = 0 do
      return n + 1;
    end;
    if n = 0 do
      return ackermann(m - 1, 1);
    end;
    return ackermann(m - 1, ackermann(m, n - 1));
  end;
end;
```

The verifier checks that on each recursive call the tuple `(m, n)` decreases lexicographically:

- `ackermann(m - 1, 1)` — first component `m - 1 < m`. ✓
- `ackermann(m, n - 1)` — first components equal, second `n - 1 < n`. ✓
- `ackermann(m - 1, ackermann(m, n - 1))` — first component `m - 1 < m`. ✓

### 20.7.2 Terminating Algorithms and Promotion to `func`

An algorithm prefixed with `terminating` guarantees **normal return** for every input satisfying its `requires` precondition, after that guarantee has been verified. This makes the algorithm usable everywhere a `func` is expected — not only in `by computation` proofs, but in arbitrary formal reasoning.

This is the only path for recursive definitions to enter the mathematical
`func` layer. Ordinary `func` definitions are definitional extensions in
first-order predicate logic and cannot be recursive (§10.3.3). If the intended
definition needs self-calls or mutually recursive calls, write it as an
`algorithm`, provide a termination argument such as `decreasing`, discharge the
generated termination obligations, and then rely on the verified `terminating`
promotion.

See §20.1.1 for the full `algorithm_def` grammar.

```mizar
definition
  let n be Nat;

  terminating algorithm FactorialDef: factorial(n) -> Nat
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    return n * factorial(n - 1);
  end;
end;
```

Once `terminating` is declared and verified, `factorial` may be used as a functor:

```mizar
theorem FactorialZero: factorial(0) = 1 by FactorialDef;
theorem FactorialStep:
  for n being Nat holds factorial(n + 1) = (n + 1) * factorial(n)
  by FactorialDef;
```

Both theorems follow from the defining equations that promotion generates for this definitional algorithm (§20.7.3). Citing its definition label cites the promotion axioms (§16.5.1).

> [!NOTE]
> Without `terminating`, the algorithm is not promoted to a first-class functor and cannot be universally quantified over as one. If computable (§20.9.3), it can still be called with `by computation` for concrete values, subject to the evaluation checks. A completed evaluation shows that this one call returns, and the contract then applies to it (§20.13.1).

The verified guarantee has the form `P(x) implies ex r st returns_f(x,r)`
(void procedures omit r); it is not emitted from the declaration alone.
For syntax-bearing input, retain Adm_Γ(ρ), InputOK(x,ρ) and P_ρ(x)
for each compatible environment and the same complete logical input.
It covers explicit and implicit failure, partial child calls, and evaluation
of iteration ranges. Every partial child call requires its precondition and
normal-return evidence; assuming the continuation is reached proves only
partial correctness. A proof of stopping, or a value equation alone, is
insufficient. This logical guarantee does not promise completion within every
finite MVM resource budget; a failed or exhausted attempt proves neither a new
normal return nor the absence of all possible normal returns.

### 20.7.3 Definitional Algorithms

A `terminating` algorithm whose body lies in the **definitional fragment** below is a **definitional algorithm**. Promotion then also generates its **defining equations** (§20.13.6): one guarded equation per `return` statement, of the same shape as a conditional `equals` definition (§10.12.2). The promoted functor can therefore be unfolded and reasoned about like a `func`, although it is recursive. Generation is automatic and needs no additional syntax. Citing its definition label in `by` cites its defining equations together with its other promotion axioms (§16.5.1).

| Body element | Definitional fragment |
|---|---|
| `const` and `ghost const` declarations | allowed |
| `if` / `else` | allowed |
| `return`, with or without justification | allowed |
| calls to `func`s, `pred`s, promoted algorithms, and members of the same recursive group | allowed |
| `ghost` statements, `assert`, snapshots, and claim blocks | allowed; they do not contribute to the equations |
| `var` declarations and assignments | not allowed |
| `while`, `for ... to`, `for ... in`, `break`, `continue` | not allowed |
| `match` | not allowed |
| non-ghost Pick (§20.3) | not allowed |
| calls to algorithms that are not promoted | not allowed |

Mutable state and loops are excluded because they do not yield one closed equation per `return`. `match` is excluded because its case hypothesis `e = π` (§20.2.5) does not determine the captured subterms uniquely. Non-ghost Pick is excluded because its result is not unique.

`factorial` (§20.7.2) and `fibonacci` (§20.8.1) are definitional algorithms. A functor synonym (§11.1.2) gives a definitional algorithm mathematical notation without a separate `func` definition:

```mizar
synonym n ! for factorial(n);
```

**Algorithms outside the fragment.** A terminating algorithm outside the fragment is promoted with its totality and contract axioms only (§20.13.2). To connect it with a mathematical definition, define the function first as an ordinary `func` and state the connection in `ensures`. The loop invariants then carry the proof inside the algorithm; an external theorem could not, because the body is not unfolded.

```mizar
definition
  let x, n be Nat;
  func power(x, n) -> Nat equals x |^ n;
end;

definition
  let x, n be Nat;

  terminating algorithm fast_power_loop(x, n) -> Nat
    ensures result = power(x, n)
  do
    var r := 1;
    var b := x;
    var e := n;
    while e > 0 do
      invariant r * power(b, e) = power(x, n);
      decreasing e;
      if e mod 2 = 1 do
        r := r * b;
      end;
      b := b * b;
      e := e div 2;
    end;
    return r;
  end;
end;
```

Alternatively, a recursive characterization can be stated directly in `ensures` (§20.4.1). The following loop computes the factorial. Its header `decreasing n` supplies the induction hypothesis, and its invariant needs the contract only at arguments below `n`:

```mizar
definition
  let n be Nat;

  terminating algorithm fact_loop(n) -> Nat
    ensures (n = 0 implies result = 1)
          & (n > 0 implies result = n * fact_loop(n - 1))
    decreasing n
  do
    var r := 1;
    var i := 0;
    while i < n do
      invariant i <= n & (i = 0 implies r = 1)
              & (i > 0 implies r = i * fact_loop(i - 1));
      decreasing n - i;
      r := r * (i + 1);
      i := i + 1;
    end;
    return r;
  end;
end;
```

For a public definitional algorithm, the generated defining equations belong to the public statement surface; a body edit that changes them is a MAJOR change (§23.2).

## 20.8 Recursive Definitions

### 20.8.1 Direct Recursion

An algorithm may call itself recursively. The verifier accepts recursive calls without additional annotation, but requires `decreasing` to prove termination. Without `decreasing`, the algorithm is treated as partially defined.

The same recursion cannot be written directly as a `func` definition: the
`definition` layer encoded in first-order predicate logic rejects direct and
mutual circular definitions (§10.3.3, §22.5.2). Recursive mathematical functions
must be expressed through the algorithm termination workflow and promoted only
after termination is verified (§20.7.2).

```mizar
definition
  let n be Nat;

  terminating algorithm fibonacci(n) -> Nat
    decreasing n
  do
    if n = 0 do return 0; end;
    if n = 1 do return 1; end;
    return fibonacci(n - 1) + fibonacci(n - 2);
  end;
end;
```

The body lies in the definitional fragment, so promotion generates the defining equations `fibonacci(n) = 0` when `n = 0`, `fibonacci(n) = 1` when `n ≠ 0 ∧ n = 1`, and `fibonacci(n) = fibonacci(n - 1) + fibonacci(n - 2)` otherwise (§20.13.6).

Each recursive call site generates a proof obligation that the `requires` preconditions are satisfied.

### 20.8.2 Mutual Recursion

Two or more algorithms may call each other mutually. They are placed within the **same `definition` block**; no special declaration is needed — the verifier detects mutual recursion automatically.

`boolean` is the built-in truth-value type; its values are `true` and `false`.

```mizar
definition
  let n be Nat;

  terminating algorithm is_even(n) -> boolean
    decreasing n
  do
    if n = 0 do return true; end;
    return is_odd(n - 1);
  end;

  terminating algorithm is_odd(n) -> boolean
    decreasing n
  do
    if n = 0 do return false; end;
    return is_even(n - 1);
  end;
end;
```

The `decreasing` measures must collectively establish termination across the call cycle. The verifier checks that no infinite call sequence can occur. When every member of the group is definitional, each member receives its own defining equations (§20.13.6).

## 20.9 Execution Model and Computability

### 20.9.1 The Mizar Virtual Machine (MVM)

The **Mizar Virtual Machine (MVM)** evaluates algorithm expressions during verification. It is invoked when:

- A `by computation` proof step is used (§20.9.2).
- An algorithm is called with fully concrete (ground) arguments in a verification context.

The MVM uses a **call-by-value** model. Side effects are confined to local `var` state; there is no global mutable state.

**Cross-package computation follows `public` / `private` visibility.** A computable public algorithm, including one with an omitted visibility modifier, is available to importers for MVM evaluation and `by computation`. Publication must provide a verified runtime artifact for that public computational interface; no separate opt-in export flag is used. A private algorithm cannot be named or invoked directly by importers. Non-computable public algorithms remain usable through their contracts. Evaluation requires validated artifacts and execution dependencies; missing artifacts are an error, not a contract-only publication mode. Local source availability (`path` or `git` dependencies) does not bypass validation.

The artifact must bind the exported algorithm identity, signature and contracts to the executable content, verification evidence, execution dependencies, and compatible MVM semantics. Its validation must establish that the executable implements the verified algorithm; executing arbitrary supplied code or trusting an unverified result is not a proof. Contract preconditions, termination requirements, and computation replay checks remain applicable. The artifact includes the private helpers needed by its public entry points without exposing their names to importers. Private helpers retain their defining-file visibility in source; their validated internal calls may execute inside the artifact. Every call across a package boundary, including transitive calls, must target a public computable algorithm through a validated artifact; missing or invalid artifacts cannot fall back to loading dependency source bodies.

A computation proof records the exact artifact content identities, including its transitive execution dependencies and MVM semantics. Changed executable content invalidates affected computation caches even when the package update is semantically compatible (§23.2). Contract-only consumers retain the opaque-import boundary and do not load execution artifacts.

Computational export is a language design requirement. The source visibility syntax is defined in §12.5. Artifact serialization and the build/loader protocol remain deferred with the MVM backend; this section does not claim implementation availability.

### 20.9.2 `by computation` Proof Step

```ebnf
computation_proof  ::= "by" "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_argument ::= algorithm_application | computation_option ;
computation_reference ::= "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_option ::= "steps"   ":" nat_literal
                     | "timeout" ":" nat_literal
                     | "nest"    ":" nat_literal ;
```

Options:

| Option | Default | Meaning |
|---|---|---|
| `steps` | `0` (unlimited) | Maximum number of MVM execution steps |
| `timeout` | `0` (unlimited) | Wall-clock time limit in milliseconds |
| `nest` | `0` (unlimited) | Maximum function call stack depth |

```mizar
theorem FactorialFiveByComputation: factorial(5) = 120 by computation;

theorem Fact10 : factorial(10) = 3628800
proof
  thus thesis by computation(steps: 100000);
end;
```

**What `by computation` can prove:**

| Goal form | MVM behaviour |
|---|---|
| `f(v₁, …, vₙ) = c` (ground equality) | Evaluate `f(v₁, …, vₙ)`, check result equals `c` |
| `P(v₁, …, vₙ)` (ground predicate) | Evaluate `P`, check it holds |
| Non-ground goals | Direct runtime evaluation needs resolved executable values; explicit structural calls may prove such goals through converted verified contracts and justified premises (§20.13.7). |

For a partial `f`, `f(v₁, …, vₙ) = c` is an ordinary equality; its computation proof confirms normal return internally (§20.13.1). The `requires` of `f` must be established at `v₁, …, vₙ`, as at any call site.

**Determinism requirement.** `by computation`, like any other MVM evaluation used to discharge an obligation (§20.9.1), must yield a value that does not depend on non-deterministic choices. Consider the computation closure of the goal, meaning every algorithm evaluated directly or transitively. Each value-returning algorithm `g` in it that contains a non-ghost Pick site (§20.3) or an unordered set `for ... in` loop (§20.2.4) must have an `ensures` clause that determines its result uniquely. For such a `g` with parameter type guards, precondition `P`, and postcondition `Q`, the step generates the uniqueness obligation

```
∀x₁,…,xₙ, r₁, r₂. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) ∧ Q(x₁,…,xₙ, r₁) ∧ Q(x₁,…,xₙ, r₂) → r₁ = r₂)
```

The obligation holds without proof when `ensures` has the form `result = t` or `result = true iff φ`, where `t` and `φ` do not mention `result`. Every execution of a verified algorithm satisfies its `ensures`, so a uniquely determined result is the same for every choice. When the obligation cannot be discharged, the step is rejected (E0330, §22.4.5). A relational contract may allow multiple results; it alone cannot justify E1 function-symbol introduction or promotion.

For example, the following algorithm visits a finite set in an unspecified order, but its `ensures` determines the result, so `by computation` may evaluate it:

```mizar
definition
  let S be finite set of Nat;
  let k be Nat;

  terminating algorithm exists_greater(S, k) -> boolean
    ensures result = true iff ex x being Nat st x in S & x > k
  do
    for x in S processed V do
      invariant for y being Nat st y in V holds y <= k;
      if x > k do return true; end;
    end;
    return false;
  end;
end;

theorem ExistsGreater: exists_greater({1, 5, 3}, 4) = true by computation;
```

A `func` defined by `equals` or `means` has no algorithm body and is not evaluated (§20.9.3). To establish a concrete value of such a `func`, compute the value of an algorithm whose `ensures` relates it to the `func`, and import its verified contract through an explicit computation call:

```mizar
theorem PowerLoop2_10: fast_power_loop(2, 10) = 1024 by computation;
theorem Power2_10: power(2, 10) = 1024 by computation(fast_power_loop(2, 10));
```

For existential goals of the form `ex x st P(x)`, the recommended approach is to implement a search algorithm explicitly:

```mizar
terminating algorithm find_witness(S) -> Integer
  requires S <> {}
  ensures result in S & P(result)
do
  ...
end;
```

The `ensures` clause then provides the existential witness within the proof system, without requiring special MVM search semantics.

Explicit computation calls and goal calls are evaluated together; omitted
calls are not inferred from thesis or supplied facts. Options apply to all
calls in that computation reference. Requires, current compatibility and
InputOK must be justified independently of the same call's consequences.
Normal return yields candidates for the complete ensures instance and ordinary
value equality; internal returns/AST-argument equalities remain evidence.
Every public candidate requires §20.13.7 conversion and residual inspection.

### 20.9.3 Computability and Runtime Failures

Algorithm definitions may reference non-constructive operations (non-computable functions, Pick on abstract sets, etc.). Such definitions are mathematically valid, but the MVM cannot execute them.

When the MVM encounters an unexecutable operation, it raises a **runtime verification failure**:

| Operation | Runtime failure condition |
|---|---|
| `the Element of S` | MVM cannot enumerate `S` (e.g., `S` is infinite and has no registered enumerator) |
| Call to `func f(x)` with no `algorithm` body | `f` has no computable implementation |
| Call to `pred P(x)` or `func F(x)` template parameter | Concrete instantiation has no computable implementation (e.g., a `means`-defined functor) |
| Division by zero (`a / 0`) | Zero denominator |
| `fail` statement (§20.2.6), including the implicit `fail` of a `match` without `otherwise` | Reached during evaluation |

A runtime failure causes the `by computation` step to **fail** (E0331, §22.4.5) — but does not invalidate the algorithm's definition. The definition remains mathematically meaningful; only its executability via the MVM is limited. A failed evaluation establishes nothing about the call.

> [!NOTE]
> `the Element of S` where `S` is a mathematically valid infinite set (e.g., `NAT`) is not an error at the definition level. The MVM simply cannot execute it. The algorithm can still be used in classical proofs through its contracts.

### 20.9.4 Gas Limit

To prevent diverging algorithms from hanging the verifier, the MVM enforces a **gas limit**: a maximum number of execution steps per `by computation` invocation.

```mizar
theorem HardComputation42: hard_computation(42) = 123456789
proof
  thus thesis by computation(steps: 1000000);
end;
```

Setting any option to `0` disables that limit (default). Options may be combined:

```mizar
thus thesis by computation(steps: 500000, timeout: 2000, nest: 200);
```

## 20.10 Code Extraction

Code extraction from verified algorithms is provided as a **separate tool**, not part of the core language specification. The extractor takes `terminating` algorithms and produces executable code in a target language (Python, C with GMP, Rust, etc.), preserving all formally verified properties by construction.

Configuration such as target language, numeric type mapping (e.g., `Nat` → GMP `mpz_t` in C), and host-library bindings is supplied via an extractor configuration file rather than inline annotations.

Refer to the extraction tool's documentation for details.

## 20.11 Complete Syntax (EBNF)

```ebnf
(* ── Algorithm definition ─────────────────────────────── *)
algorithm_def ::= ( "terminating" "algorithm" [ label_identifier ":" ] | "algorithm" ) identifier [ "[" schema_params "]" ] "(" [ identifier_list ] ")" [ "->" type_expression ]
                  [ "requires" formula ]
                  [ "ensures"  formula ]
                  [ "decreasing" term_list ]
                  algorithm_body ";" ;

identifier_list   ::= identifier { "," identifier } ;

algorithm_body    ::= "do" algo_statement_list "end" ;

(* ── Statement list ────────────────────────────────────── *)
algo_statement_list ::= { algo_statement } ;

algo_statement ::= var_decl
                 | const_decl
                 | ghost_var_decl
                 | ghost_const_decl
                 | assignment
                 | ghost_assignment
                 | if_stmt
                 | while_stmt
                 | for_range_stmt
                 | for_collection_stmt
                 | match_stmt
                 | return_stmt
                 | break_stmt
                 | continue_stmt
                 | fail_stmt
                 | assert_stmt
                 | snapshot_stmt
                 | standalone_diagnostic_annotation ;

(* ── Declarations and assignment ───────────────────────── *)
var_decl         ::= "var"         var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
ghost_var_decl   ::= "ghost" "var" var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
const_decl       ::= "const"       const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;
ghost_const_decl ::= "ghost" "const" const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;

var_binding   ::= identifier [ ":=" term ] ;
const_binding ::= identifier ":=" term ;

assignment       ::= lvalue ":=" term ";" ;
ghost_assignment ::= "ghost" lvalue ":=" term ";" ;
lvalue           ::= identifier
                   | lvalue "." identifier ;

justification ::= simple_justification | proof | computation_proof ;
(* simple_justification, proof, computation_proof, reasoning, references — defined in §15/§16/§20.9.2 *)

(* ── Control flow ──────────────────────────────────────── *)
if_stmt ::= "if" formula "do" algo_statement_list if_tail ;
if_tail ::= "end" ";"
          | "else" if_stmt
          | "else" algo_statement_list "end" ";" ;

while_stmt ::= "while" formula "do"
                 { while_annotation ";" }
                 algo_statement_list
               "end" ";" ;

while_annotation ::= "invariant" formula [ justification ]
                   | "decreasing" term_list [ justification ] ;

term_list ::= term_expression { "," term_expression } ;

for_range_stmt ::= "for" identifier "=" expr ( "to" | "downto" ) expr
                   [ "step" expr ]
                   "do" { for_annotation ";" } algo_statement_list "end" ";" ;

for_collection_stmt ::= "for" identifier "in" expr [ "processed" identifier ] "do"
                          { for_annotation ";" }
                          algo_statement_list
                        "end" ";" ;

for_annotation ::= "invariant" formula [ justification ] ;

match_stmt ::= "match" expr "do"
               match_case+
               [ "otherwise" algo_statement_list "end" ";" ]
               "end" ";" ;

match_case           ::= "case" term_pattern "do" algo_statement_list "end" ";" ;
term_pattern         ::= term_expression | formula ;

return_stmt   ::= "return" [ expr [ justification ] ] ";" ;
break_stmt    ::= "break" ";" ;
continue_stmt ::= "continue" ";" ;
fail_stmt     ::= "fail" [ string_literal { "," expr } ] ";" ;
assert_stmt   ::= "assert" formula [ justification ] ";" ;
snapshot_stmt ::= "snapshot" identifier ";" ;

(* ── Snapshot and Claim ────────────────────────────────────── *)
claim_block ::= "claim" identifier "do"
                  { annotated_theorem_item }
                "end" ";" ;
annotated_theorem_item ::= { annotation } theorem_item ;

(* snapshot_access inside claim_block theorems:                  *)
(*   snapshot_name "." identifier                                 *)

(* ── Proof step ─────────────────────────────────────────────
   Used in proof blocks (outside algorithm bodies) as:
     "thus" formula "by" "computation" ...
   or in short-form theorems:
     theorem label_identifier ":" formula "by" "computation" ... ";" *)
computation_proof   ::= "by" "computation"
                        [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_argument ::= algorithm_application | computation_option ;
computation_reference ::= "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_option  ::= "steps"   ":" nat_literal
                      | "timeout" ":" nat_literal
                      | "nest"    ":" nat_literal ;

(* ── Pick expression ─────────────────────────────────────────
   Used as a term on the right-hand side of const_decl, var_decl,
   assignment, ghost_var_decl, ghost_const_decl, or ghost_assignment
   inside an algorithm body:
     const x := the Element of S ;
     const p := the prime Number ;
     ghost witness := the Element of S ;                         *)
pick_expr ::= "the" type_expression ;
algorithm_application ::= identifier [ template_args ] "(" [ algorithm_inputs ] ")" ;
algorithm_inputs ::= expr_input { "," expr_input } ;
expr_input ::= term_expression | formula | label_identifier | "thesis" ;
expr_size_expr ::= "expr_size" "(" term_expression ")" ;
```

## 20.12 Extended Examples

### Fast Exponentiation (Exponentiation by Squaring)

Demonstrates recursion with a non-trivial termination measure and a mathematical `ensures` clause verified by `by computation`.

```mizar
definition
  let x be Nat;
  let n be Nat;

  terminating algorithm fast_power(x, n) -> Nat
    ensures result = x |^ n
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    if n mod 2 = 0 do
      const half := fast_power(x, n div 2);
      return half * half;
    end;
    return x * fast_power(x, n - 1);
  end;
end;

:: Verified by computation for concrete inputs
theorem FastPower2_10: fast_power(2, 10) = 1024 by computation;
theorem FastPower3_5:  fast_power(3, 5)  = 243  by computation;

:: Promoted to func via terminating; usable in general proofs
theorem fast_power_correct :
  for x, n being Nat holds fast_power(x, n) = x |^ n;
```

### Integer Factorisation (Trial Division)

```mizar
definition
  let n be Nat;

  algorithm trial_factor(n) -> Nat
    requires n >= 2
    ensures result >= 2 & result divides n
  do
    var d := 2;
    while d * d <= n do
      invariant d >= 2 & for k being Nat st 2 <= k & k < d holds not k divides n;
      assert n - d * d >= 0 by arithmetic;
      decreasing n - d * d + 1;
      if n mod d = 0 do
        return d;
      end;
      d := d + 1;
    end;
    return n;   :: n is prime
  end;
end;
```

### Euclidean GCD Algorithm

The algorithm is named `euclid_gcd` to distinguish it from the mathematical functor `Gcd` defined in the standard library. Both the `ensures` clause and the loop invariant use `Gcd` (mathematical) — not the algorithm itself — so there is no circularity.

```mizar
definition
  let a, b be Nat;

  terminating algorithm euclid_gcd(a, b) -> Nat
    requires a >= 1 & b >= 1
    ensures result = Gcd(a, b)
  do
    var x := a;
    var y := b;
    while y <> 0 do
      invariant x >= 1 & y >= 0 & Gcd(a, b) = Gcd(x, y);
      decreasing y;
      const r := x mod y;
      x := y;
      y := r;
    end;
    return x;
  end;
end;

theorem EuclidGcd12_8: euclid_gcd(12, 8) = 4 by computation;
theorem EuclidGcd100_75: euclid_gcd(100, 75) = 25 by computation;
```

### Symbolic Differentiation

Demonstrates `match` on an expression AST, structural recursion with `expr_size`, and `return ... by` shorthand. `Expr[K, x]` is an arithmetic expression type over field `K` and variable `x`. `Diff(t, x)` is the mathematical (formal derivative) functor defined in the supporting theory.

```mizar
definition
  let K be Field;
  let x be Variable;
  let t be Expr[K, x];

  terminating algorithm diff(t) -> Expr[K, x]
    ensures result = Diff(t, x)
    decreasing expr_size(t)
  do
    var p, q as Expr[K, x];
    match t do
      case p + q do
        :: D(p + q) = D(p) + D(q)
        return diff(p) + diff(q) by diff_add;
      end;
      case p * q do
        :: D(p * q) = D(p) * q + p * D(q)
        return diff(p) * q + p * diff(q) by diff_mul;
      end;
      case x do
        :: D(x) = 1
        return 1 by diff_var;
      end;
      otherwise
        :: t is a constant (no occurrence of x); D(c) = 0
        return 0 by diff_const;
      end;
    end;
  end;
end;

:: Spot-check on concrete expressions
theorem DiffSquare: diff(x * x) = x + x by computation;           :: D(x^2) = 2x
theorem DiffSquarePlusX: diff(x * x + x) = x + x + 1 by computation;
```


## 20.13 Logical Encoding

This section specifies how algorithm constructs map to logical formulas in the Mizar kernel. It complements the operational description in §20.4–§20.7 with the formal axioms generated for `terminating` algorithms and the verification-condition (VC) schema for each statement form.

### 20.13.1 Contract Axioms

Every algorithm call site generates proof obligations from `requires`, and every `return` generates obligations from `ensures`. The table below gives the FOL encoding. Type parameters of the enclosing `definition` block are universally quantified and appear as type guards `is_A(x)`.

| Construct | FOL Encoding |
|---|---|
| `requires P` | Proof obligation at each call site: `Γ ⊢ P(a₁, …, aₙ)` |
| `ensures Q` at `return e` | Proof obligation: `Γ ⊢ Q[result/e]` |
| `ensures Q` (caller side, partial algorithm) | The evaluation axiom below; `Q` holds for a call only when that call is known to return |
| `assert φ` | Proof obligation: `Γ ⊢ φ` at that program point; `φ` is added to `Γ` afterwards |
| call `f(a₁, …, aₙ)`, `f` promoted | (1) `Γ ⊢ requires_f(a₁, …, aₙ)`; (2) `ensures_f(a₁, …, aₙ, f(a₁, …, aₙ))` is added to `Γ` |
| call `g(a₁, …, aₙ)` in an algorithm body, `g` partial | (1) `Γ ⊢ requires_g(a₁, …, aₙ)`; (2) `returns_g(a₁, …, aₙ, r)` and `ensures_g(a₁, …, aₙ, r)` are added to `Γ` for a fresh `r` |

Multiple `requires` and `ensures` clauses are conjoined.

**Function graph and verified contracts (E1–E5).** Value-returning partial
algorithms also have logical function symbols. For the same complete input x
(syntax, ordinary values, retained context and any reconstruction C), use:

| Rule | Formula / adoption condition |
|---|---|
| E1 | returns_f(x,r) implies f(x)=r. Before introduction justify result typing, single-valued execution for complete input, and existence of a value of any return type asserted on **all** typed inputs, including unreturned ones. A dependent type available only under P is not asserted outside P. |
| E2 | P(x) & returns_f(x,r) implies Q(x,r), adopted only after body partial-correctness verification. For syntax use Adm_Γ(ρ) & InputOK(x,ρ) & P_ρ(x) in each environment (§20.5.3 M8). |
| E3 | returns_f(x,r1) & returns_f(x,r2) implies r1=r2 follows from E1 and equality; execution single-valuedness is also a prerequisite for E1, not repaired by an extra axiom. |
| E4 | Verified normal-return guarantee P(x) implies ex r st returns_f(x,r), with M8 environment/InputOK guards for syntax. Together E1/E2 yield P(x) implies Q(x,f(x)), cited by definition label. Direct/implicit failure, child calls and iteration ranges are included (§20.7.2). |
| E5 | MVM-confirmed finite normal return for complete c supplies internal returns_f(c,v), bound to verified body/input/result. Failure/resource exhaustion supplies no new return evidence and does not prove nonexistence of a normal return. |

For unreturned input, f(x) is an unspecified value. `f(x)=r` is an ordinary
substitutable equality everywhere; it implies neither returns_f nor ensures.
Void procedures omit r in returns and have no value function symbol.
No algorithm name is a citation; contracts after body calls are already in
continuation context. Promotion requires verified E4, not declaration alone.
Introducing a function symbol requires E1 single-valuedness even when a Pick
contract allows several outcomes; such a contract alone does not justify it.

A call is **known to return** when a `returns_f` fact for its arguments is available. Such a fact has exactly three sources:

1. A completed MVM evaluation of a ground call `f(c₁, …, cₙ)` that returns `v` yields `returns_f(c₁, …, cₙ, v)` for that call only (§20.9.2). A failed evaluation yields nothing (§20.9.3).
2. Inside an algorithm body, a call to `f` yields `returns_f(args, r)` for a fresh `r` in the context of the statements that follow it. This is partial correctness: those statements run only if the call has returned. It applies to recursive calls as well (§20.13.4).
3. A verified theorem establishing existence of a **normal return** for the specific call, cited or in context; merely proving that execution stops is insufficient.

A `terminating` algorithm must establish by source 1 or 3 that each call to a partial algorithm in its body returns. Source 2 does not count for this purpose, because it assumes the return.

### 20.13.2 Promotion Axioms for `terminating`

When `terminating` is declared and verified, the algorithm is promoted to a `func` and the following axioms are emitted into the Mizar kernel:

| Axiom | FOL Schema |
|---|---|
| **Totality** | `∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) → is_T(f(x₁,…,xₙ)))` |
| **Contract** | `∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) → Q(x₁,…,xₙ, f(x₁,…,xₙ)))` |
| **Defining equations** | Definitional algorithms only (§20.7.3): one guarded equation per `return` statement (§20.13.6) |

If `requires` is absent, `P` defaults to `⊤` — the functor is total on all inputs of the declared types. Multiple `ensures` clauses are conjoined into a single `Q`.

**Example** — `factorial` (body as in §20.1.1):

```
terminating algorithm FactorialDef: factorial(n) -> Nat
  ensures result >= 1
  decreasing n
```

Emitted axioms:

| Axiom | Formula |
|---|---|
| Totality | `∀n. (is_Nat(n) → is_Nat(factorial(n)))` |
| Contract | `∀n. (is_Nat(n) → factorial(n) ≥ 1)` |
| Defining equation | `∀n. (is_Nat(n) ∧ n = 0 → factorial(n) = 1)` |
| Defining equation | `∀n. (is_Nat(n) ∧ ¬(n = 0) → factorial(n) = n * factorial(n - 1))` |

These axioms become available to the proof system as soon as `terminating` is verified. The defining equations are the only form in which a body is unfolded, and only a definitional algorithm receives them. For any other terminating algorithm, further properties must follow from the contract.

### 20.13.3 Verification Condition Schema

The verifier traverses the algorithm body and generates VCs by a standard Hoare-logic schema. `Γ` denotes the current logical context (accumulated facts at that program point).

Statement verification returns separate exit contexts: `Normal`, `Return`,
`Break(loop)`, and `Continue(loop)`. Sequential composition continues only from
`Normal`; loop constructs consume their own `Break` and `Continue` contexts and
leave unrelated exits untouched. A loop's post-context is the join of its normal
exit and its break exits. Facts guarded only by normal termination, such as
`¬C` for a `while C`, are not added to break exits.

`assign(Γ, l, e)` denotes the old-state assignment transformer described in
§20.1.4: evaluate `e` in the pre-state, forget or rename facts that mention
locations that may alias `l`, preserve non-aliasing facts, and add the
post-state equality for `l`. `assign_field` is the corresponding transformer for
field updates through the resolved lvalue identity.

Loop heads use the same old-state discipline at a cutpoint. `MayWrite(S)` is
the set of mutable locations that the loop body `S` may assign on any path,
closed over resolved aliasing lvalue paths. `havoc(Γ, W)` forgets or freshens
facts in `Γ` that mention locations that may alias a location in `W`, while
preserving facts about non-aliasing locations and immutable hidden values. For
a loop body `S`, write `Γ_loop = havoc(Γ, MayWrite(S))`. The invariant and loop
guard are then assumed over `Γ_loop`, not over the entry context `Γ`; otherwise
entry facts such as `x = 0` would unsoundly survive arbitrary iterations that
assign `x`. Range bounds, range steps, and collection domains are evaluated
once before `Γ_loop` is formed and are represented below by hidden immutable
values such as `a₀`, `b₀`, `s₀`, and `S₀`; when such values are introduced,
`Γ_loop` is computed from `Γ` extended with those immutable bindings.

`V_after` is the loop measure evaluated in the post-state on a normal back edge
or `continue` edge; `V_before` is the same measure evaluated at the loop head
before the body. For range loops, `step` defaults to `1`, must be a positive
`Nat`, and `next(i)` is `i + s₀` for `to` loops and `i - s₀` for `downto`
loops.

| Statement | VC generated | Context after |
|---|---|---|
| `var x := e` | — | `Γ ∪ { x = e, is_inferred_T(x) }` |
| `var x := e as T` | `Γ ⊢ is_T(e)` (auto or via justification) | `Γ ∪ { x = e, is_T(x) }` |
| `const x := e` | — | `Γ ∪ { x = e }` |
| `x := e` | — | `assign(Γ, x, e)` |
| `p.f := e` | `Γ ⊢ field_update_well_typed(p, f, e)` | `assign_field(Γ, p.f, e)`; aliases of `p.f` are updated only through the resolved lvalue identity |
| `ghost x := e` | — (spec only) | `assign(Γ, x, e)` in the ghost state; any Pick site is ghost-only |
| `return e` | `Γ ⊢ ensures[result/e]` | — (exits) |
| `return` (void) | `Γ ⊢ ensures` | — (exits) |
| `assert φ` | `Γ ⊢ φ` | `Γ ∪ { φ }` |
| call `f(args)`, `f` promoted | `Γ ⊢ requires_f(args)` | `Γ ∪ { ensures_f(args, result) }` |
| call `g(args)`, `g` partial | `Γ ⊢ requires_g(args)`; in a `terminating` algorithm, also that the call returns (§20.13.1) | `Γ ∪ { returns_g(args, r), ensures_g(args, r) }` for a fresh `r` |
| `fail …` | — | — (ends the path; contributes no exit context) |
| `if C do S₁ end` | verify `S₁` under `Γ ∪ {C}`; the absent `else` branch contributes `Γ ∪ {¬C}` | join of the normal exit contexts from `S₁` and `Γ ∪ {¬C}` |
| `if C do S₁ else S₂ end` | verify `S₁` under `Γ ∪ {C}`; verify `S₂` under `Γ ∪ {¬C}` | join of exit contexts |
| `while C do invariant I; decreasing V; S end` | Let `Γ_loop = havoc(Γ, MayWrite(S))`. (1) `Γ ⊢ I` (establishment); (2) verify `S` under `Γ_loop ∪ {I, C}`; every normal back edge and `continue` edge proves `I`; (3) `Γ_loop ∪ {I, C} ⊢ is_Nat(V_before)`; (4) every normal back edge and `continue` edge proves `V_after < V_before`; every `break` edge proves `I` | join of `Γ_loop ∪ { I, ¬C }` for normal exit and the loop's break exit contexts; break exits do not gain `¬C` |
| `break` inside loop | `Γ ⊢ I` for the innermost loop | `Break(loop, Γ ∪ {I})` |
| `continue` inside loop | `Γ ⊢ I`; `Γ ⊢ V_after < V_before` when a decreasing measure is declared | `Continue(loop, Γ ∪ {I})` |
| `for i = a (to | downto) b [step s] do invariant I; S end` | Evaluate `a`, `b`, and `s` once as hidden `a₀`, `b₀`, and `s₀`; let `Γ_loop = havoc(Γ, MayWrite(S))`. (1) `Γ ⊢ is_positive_Nat(s₀)`; (2) `Γ ⊢ I[i/a₀]`; (3) verify `S` under `Γ_loop ∪ {I, in_range(i)}`; every normal back edge proves `I[i/next(i)]`; every `break` edge proves `I` | join of the normal exit summary `Γ_loop ∪ { I[i/i_exit] ∧ past_end(i_exit) }` and the loop's break exit contexts. `i_exit` is hidden loop metadata, not a source-visible variable. For `to`, `in_range(i)` is `a₀ ≤ i ≤ b₀` and `past_end(i_exit)` is `i_exit > b₀`; for `downto`, `in_range(i)` is `b₀ ≤ i ≤ a₀` and `past_end(i_exit)` is `i_exit < b₀` |
| set `for x in S processed V do invariant I; S_body end` | Evaluate `S` once as hidden `S₀`; let `Γ_loop = havoc(Γ, MayWrite(S_body))`. (1) `Γ ⊢ I[V/∅]` (establishment); (2) `Γ_loop ∪ { I, x ∈ S₀ ∖ V } ⊢ wp(S_body, I[V ↦ V ∪ {x}])` (maintenance, for arbitrary `x`) | `Γ_loop ∪ { I ∧ V = S₀ }` |
| set `for x in S do S_body end` (no `processed`) | Evaluate `S` once as hidden `S₀`; let `Γ_loop = havoc(Γ, MayWrite(S_body))`; verify `S_body` under `Γ_loop ∪ { x ∈ S₀ }` | `Γ_loop` |
| `match e do case π₁ do S₁ end; … end` | for case `i`: bind capture vars; verify `Sᵢ` under `Γ ∪ { e = πᵢ, ¬(∃ cvars₁. e = π₁), …, ¬(∃ cvarsᵢ₋₁. e = πᵢ₋₁) }`; in a `terminating` algorithm, verify `otherwise` present | join of exit contexts; an omitted `otherwise` acts as `fail` and contributes none |

Multiple `invariant` clauses are conjoined: `invariant P; invariant Q;` is treated as `invariant P ∧ Q;`.

For finite-sequence for-in, evaluate/freeze S once as a sequence V; visit
positions i=1,…,len V binding x=V.i, duplicates included. Apply the range-loop
invariant/exit schema to these positions, not set membership/order-independence.
Sequence-expression evaluation must satisfy call/normal-return obligations;
processed-set annotation semantics are not generalized to sequences here.

### 20.13.4 Recursive Algorithm Encoding

Termination of a recursive `terminating` algorithm is established by a **well-founded recursion argument**. The underlying principle is:

> *If for every input `x` satisfying `requires`, every recursive call `f(y)` satisfies `measure(y) < measure(x)` (lexicographically on `Nat`), and `measure` is `Nat`-valued, then `f` is total on all inputs satisfying `requires`.*

This corresponds to the well-founded induction schema on `Nat` (or `Nat × Nat × …`):

```
∀x. (∀y. (measure(y) < measure(x) → P(y))) → P(x)
─────────────────────────────────────────────────────
∀x. P(x)
```

where `P(x)` is the conjunction of totality and contract for input `x`.

For **mutual recursion**, the same principle applies collectively: the verifier checks that no infinite call sequence can occur by verifying that the shared `decreasing` measure decreases on every cross-algorithm call, treating the mutually recursive group as a single induction.

The promotion axioms (§20.13.2) are emitted for each algorithm in the group once termination is verified for all.

**Induction hypothesis in the algorithm's own verification.** When a `terminating` algorithm declares a header `decreasing` measure `μ`, the initial context of its body contains, for the algorithm itself and for each member `h` of its recursive group, with type guards `is_Bⱼ`, precondition `P_h`, postcondition `Q_h`, and measure `μ_h`:

```
∀y₁,…,yₘ. (is_B₁(y₁) ∧ … ∧ P_h(y₁,…,yₘ) ∧ μ_h(y₁,…,yₘ) < μ(x₁,…,xₙ) → Q_h(y₁,…,yₘ, h(y₁,…,yₘ)))
```

Here `<` is the lexicographic order of §20.5.2. This is the hypothesis of the well-founded induction above, and it justifies `ensures` clauses that apply the algorithm itself (§20.4.1). No hypothesis about the current arguments `x₁,…,xₙ` is available, so the contract of the current call cannot be used to prove itself. By the same induction, the contract axiom of §20.13.2 holds at every admitted input.

The restriction to a strictly smaller measure is essential. With hypotheses at all other arguments, a clause such as `ensures result = f(n + 1) + 1` would yield `f(n + 1) = f(n + 2) + 1 = f(n + 3) + 2 = …`, an infinite descent in `Nat` from which the verifier could derive a contradiction and accept an inconsistent contract.

**Recursion in partial algorithms.** A partial algorithm may call itself or another member of its recursive group without a `decreasing` measure. Source 2 of §20.13.1 applies to these calls as to any other: after a recursive call returns, its `ensures` holds for the returned value. This is the recursion rule of partial correctness. It is sound by induction on the length of an evaluation: an evaluation that returns contains only shorter evaluations of its inner calls, each of which returns and satisfies `ensures` by the induction hypothesis. The rule gives nothing about arguments at which no evaluation returns, so it proves no termination and cannot yield an infinite descent like the one above.

```mizar
definition
  let n be Nat;

  terminating algorithm collatz_step_algo(n) -> Nat
  do
    if n mod 2 = 0 do return n div 2; end;
    return 3 * n + 1;
  end;
end;

definition
  let n be Nat;

  :: Not terminating: termination for every n >= 1 is an open problem.
  algorithm collatz_steps_algo(n) -> Nat
    requires n >= 1
    ensures iterate[Nat, collatz_step_algo](result, n) = 1
  do
    if n = 1 do return 0; end;
    return collatz_steps_algo(collatz_step_algo(n)) + 1 by IterateShift;
  end;
end;

theorem Collatz27: collatz_steps_algo(27) = 111 by computation;
theorem Collatz27Reaches1: iterate[Nat, collatz_step_algo](111, 27) = 1
  by computation;
```

`collatz_step_algo` is a definitional algorithm, so the MVM can evaluate it and it is a valid functor actual (§18.8.4). `iterate` is the template algorithm of §18.8.4, The zero return requires the verified zero equation for iterate; `IterateShift` is the lemma `iterate[T, F](k + 1, x) = iterate[T, F](k, F(x))`. The recursive `return` is verified from the `ensures` of the inner call (source 2). `Collatz27` is an ordinary value equality; its computation internally confirms normal return. `Collatz27Reaches1` computes the call too, then uses the verified contract; the equality alone is not return evidence.

### 20.13.5 Ghost Variable Erasure

Ghost variables exist in the logical context during verification but are erased from the runtime program. The erasure is **sound** in the following sense:

> *Any non-ghost contract (`requires`, `ensures`, `assert`) that is verified in the presence of ghost variables also holds in the erased program — provided the erased statements mention no ghost variables.*

| Property | Statement |
|---|---|
| **Contract preservation** | Let `S'` be `S` with all `ghost var`, `ghost const`, and `ghost` assignments removed. If `S` satisfies contracts `P`/`Q` where `P`, `Q` mention no ghost variables, then `S'` also satisfies `P`/`Q`. |
| **Invariant projection** | Loop invariants that mention ghost variables (e.g. `S_visited`) are verified during type-checking only; they generate no runtime obligation. |
| **Ghost isolation** | The verifier statically checks that ghost variables do not appear on the right-hand side of non-ghost assignments and are not passed to non-ghost algorithm calls (§20.1.3). This is the key condition for soundness of erasure. |

### 20.13.6 Defining Equations of Definitional Algorithms

For a definitional algorithm `f` (§20.7.3) with parameters `x₁,…,xₙ`, parameter type guards `is_A₁(x₁) ∧ …`, and precondition `P`, let `r₁,…,rₖ` be its `return` statements in textual order, returning expressions `e₁,…,eₖ`.

- The **local guard** `gᵢ` of `rᵢ` is the conjunction of the conditions of the `if` branches enclosing `rᵢ`: `C` for a `do` branch and `¬C` for an `else` branch.
- The **path condition** is `πᵢ = gᵢ ∧ ¬π₁ ∧ … ∧ ¬πᵢ₋₁`. Because the fragment has no loops, a textually earlier `return` is the only way to leave the body before `rᵢ`, so `πᵢ` holds exactly when execution reaches `rᵢ`.
- `σ` substitutes each `const` occurring in `πᵢ` or `eᵢ` by its defining term, repeatedly, until no `const` remains. A condition that is a `boolean` term `t` rather than a formula is read as `t = true`. When `f` returns `boolean` and `eᵢ` is a formula `φ`, the equation below takes the form `f(x₁,…,xₙ) = true ↔ φσ`.

Promotion emits, for each `i`:

```
∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) ∧ πᵢσ → f(x₁,…,xₙ) = eᵢσ)
```

`ghost` statements, `assert`, snapshots, claim blocks, and `return` justifications do not contribute to the equations.

**No additional obligations.** The path conditions are pairwise disjoint by construction, and they are jointly exhaustive under `P` because every path returns (§20.2.6). Unlike an overlapping conditional definiens (§10.12.2), a definitional algorithm therefore needs no consistency or coverage obligation.

**Soundness.** Termination is verified by the measure obligations of §20.13.4; a body without recursive calls terminates trivially. The fragment excludes every source of non-determinism in the body. Hence, for any interpretation of the functors that the body calls, exactly one function on the inputs admitted by the type guards and `P` satisfies the equations, by well-founded recursion on the measure. The promotion is a conservative extension. The equations are ordinary axioms with provenance and do not change the kernel.

For a mutually recursive group, equations are generated only when every member is definitional, and they are emitted for all members once termination is verified for the whole group. A template algorithm (§20.1.1) receives its equations with its schema parameters left abstract.

**Example** — `fibonacci` (§20.8.1):

| Return | Emitted equation |
|---|---|
| `return 0` | `∀n. (is_Nat(n) ∧ n = 0 → fibonacci(n) = 0)` |
| `return 1` | `∀n. (is_Nat(n) ∧ n = 1 ∧ ¬(n = 0) → fibonacci(n) = 1)` |
| `return fibonacci(n - 1) + fibonacci(n - 2)` | `∀n. (is_Nat(n) ∧ ¬(n = 0) ∧ ¬(n = 1 ∧ ¬(n = 0)) → fibonacci(n) = fibonacci(n - 1) + fibonacci(n - 2))` |
