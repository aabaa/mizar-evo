Mizar Evolution は、**実行可能なアルゴリズム**を形式的な証明システムと統合します。 `algorithm` ブロックは、次のような計算を定義します。

- **検証中に Mizar 仮想マシン (MVM) によって実行** (`by computation`)。
- **Hoare 論理 コントラクト (`requires`、`ensures`、`invariant`) を使用する理由**。
- (`terminating` 経由で) 完全な正確性が確立されると、**数学functor (`func`) に昇格**します。

この設計は、**デフォルトで部分的正しさ**の原則に従っています。つまり、明示的な終了引数が指定されない限り、アルゴリズムは分岐することが許可されます。これにより、具体的な入力または制限されたコンテキストでのみ使用されるアルゴリズムに対する終了証明の要求が回避されます。

## 20.1 アルゴリズム構文

### 20.1.1 アルゴリズム定義ブロック

アルゴリズムは **`definition` ブロック内**で宣言する必要があります。周囲の `let` 宣言は型コンテキストをバインドします。アルゴリズムのパラメータ リストは、それらのバインディングのうちどれが仮引数になるかを選択します。

`definitional_item` (§12.5) として、algorithm は通常の `public` / `private` 可視性規則に従い、省略時は `public` です。public algorithm は署名と `requires` / `ensures` 契約を公開し、計算可能な場合は検証済みランタイムアーティファクトを通じてパッケージ間の MVM 評価にも利用できます (§20.9.1)。計算用公開のための別の修飾子は不要です。可視性だけで計算可能性や停止性が証明されるわけではありません。実装の互換性は §23.2 に従います。

```ebnf
algorithm_def ::= ( "terminating" "algorithm" [ label_identifier ":" ] | "algorithm" ) identifier [ "[" schema_params "]" ] "(" [ identifier_list ] ")" [ "->" type_expression ]
                  [ "requires" formula ]
                  [ "ensures"  formula ]
                  [ "decreasing" term_list ]
                  algorithm_body ";" ;

schema_params    ::= identifier { "," identifier } ;
identifier_list  ::= identifier { "," identifier } ;

algorithm_body   ::= "do" algo_statement_list "end" ;
```

`[ "->" type_expression ]` はオプションです。戻り値の型のないアルゴリズムは **void** (プロシージャ) です。オプションの `[ "decreasing" term_list ]` は、ヘッダー レベルで再帰終了措置 (§20.5.2) を宣言します。ループの終了については、§20.2.2 を参照してください。

アルゴリズム名は常に `identifier` です。アルゴリズム宣言は、レクサーのユーザー
シンボル辞書エントリを導入しません。停止するアルゴリズムは、意味論上は呼び出し可能な
functor に昇格できます (§20.7.2) が、その昇格は新しい演算子風の綴りを作りません。
数学的な記法が必要な場合は、functor の同義語 (§11.1.2) または通常の `func` 定義を使います。

**template algorithm。** `algorithm_def` は有効な `template_item` (§18.2.1) です。囲んでいる `definition` ブロックがスキーマ パラメーター (**type** (`let T be type`)、**pred** (`let P be pred(...)`)、または **func** (`let F be func(...) -> ...`)) を宣言する場合、これらのパラメーターはアルゴリズム本体および `requires`/`ensures` 句で参照される場合があります。アルゴリズム名には、スキーマ定理 (§18.8.4) と同じ規則に従って、スキーマ パラメーターをリストする `[...]` 括弧接尾辞が付けられます。インスタンス化は、括弧内に具体的な型、pred、または func 名を指定することによって、各呼び出しサイトで実行されます。

```mizar
definition
  let n be Nat;

  terminating algorithm FactorialDef: factorial(n) -> Nat
    ensures result >= 1
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    return n * factorial(n - 1);
  end;
end;
```

`terminating` 修飾子 (§20.7.2) は、`requires` を満たすすべての入力に対してアルゴリズムが終了することを宣言します。これはオプションです。`terminating` のないアルゴリズムは部分的に定義されているものとして扱われ、ファーストクラスのfunctorとして使用できません。

```ebnf
algorithm_application ::= ( identifier | namespace_path "." identifier ) [ template_args ] "(" [ algorithm_inputs ] ")" ;
algorithm_inputs ::= expr_input { "," expr_input } ;
expr_input ::= term_expression | formula | label_identifier | "thesis" ;
```
この文脈付き引数文法はalgorithm呼び出しを期待引数型へ接続する。
論理式・ラベル・thesisはexpr of booleanを期待する場合だけ許し、
他の引数は通常の項を使う。論理式を項にはしない。
thesisの配置とラベルの引用は§16.5.1、R1/R2/R3は§20.5.3に従う。

### 20.1.2 パラメータと戻り値の型

パラメータはアルゴリズム本体内で位置指定されており、**不変**です (`const` として動作します)。パラメータの可変バージョンを使用するには、`var` コピーを作成します。

```mizar
definition
  let x be Nat;

  algorithm copy_and_modify(x) -> Nat
  do
    var y := x;
    y := y + 1;
    return y;
  end;
end;
```

戻り値の型は、すべての `return` 式の型を指定します。 `ensures` 句の特別な識別子 `result` は、戻り値を参照します。

```mizar
definition
  let n be Integer;

  algorithm abs_val(n) -> Nat
    ensures result >= 0
  do
    if n >= 0 do
      return n;
    end;
    return -n;
  end;
end;
```

### 20.1.3 変数宣言(`var`、`const`)

アルゴリズム本体内では、変数は `var` (可変) または `const` (不変) で導入されます。 **ゴースト変数** (`ghost var`、`ghost const`) は仕様レベルでのみ存在し、抽出時に消去されます。

```ebnf
var_decl         ::= "var"         var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
ghost_var_decl   ::= "ghost" "var" var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
const_decl       ::= "const"       const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;
ghost_const_decl ::= "ghost" "const" const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;

var_binding   ::= identifier [ ":=" algorithm_rhs ] ;
const_binding ::= identifier ":=" algorithm_rhs ;
algorithm_rhs ::= term_expression | formula ;

justification ::= simple_justification | proof | computation_proof ;
(* simple_justification, proof, computation_proof, reasoning, references — defined in §15/§16/§20.9.2 *)
```

|キーワード |可変性 |ランタイム |使用例 |
|---|---|---|---|
| `const` |不変 |はい |中間結果、取得された値、選択 |
| `var` |可変 |はい |ループ カウンタ、アキュムレータ、状態 |
| `ghost const` |不変 |いいえ (仕様のみ) |証人、仕様値 |
| `ghost var` |可変 |いいえ (仕様のみ) |証明追跡 (訪問済みセット、抽象状態) |

**変数の種類間のキャスト ルール。** 4 つの種類は、最も具体的なものから最も抽象的なものまでの階層を形成します。より抽象的な種類が期待される場合はどこでも、より具体的な種類の値を使用できます。逆は禁止です。

|から \ まで | `const` | `ghost const` | |
|---|---|---|---|
| `var` | ✓ (現在の値、読み取り専用) | ✓ | ✓ |
| `const` | — | ✓ | — |
| `ghost var` | ✗ | ✓ (現在値) | — |
| `ghost const` | ✗ | — | — |

上向き方向 (コンクリート → ゴースト) は常に安全です。仕様コンテキストでのランタイム値の読み取りは実行に影響しません。下方向 (ゴースト→ランタイム) は常に禁止されています。ゴースト値にはランタイム表現がなく、非ゴースト変数に割り当てたり、非ゴースト呼び出しに渡したりすることはできません。

ゴースト変数は、**仕様コンテキスト**: `invariant`、`ensures`、`requires`、および `assert` でのみ表示される場合があります。これらは非ゴースト割り当ての右側に表示されない場合があり、非ゴースト アルゴリズム呼び出しに渡されない場合があります。

検証器は、ゴースト変数が実行時の動作に影響を与えないことをチェックします。エクストラクターは、すべてのゴースト宣言とゴースト割り当てをサイレントに削除します。

```mizar
definition
  let S be finite set of Integer;

  algorithm find_min(S) -> Integer
    requires S <> {}
    ensures result in S & for x being Integer st x in S holds result <= x
  do
    ghost var visited := {} as set of Integer;
    var current := S;
    var best := the Element of S;
    while current <> {} do
      invariant visited = S \ current;
      invariant best in S & for x being Integer st x in visited holds best <= x;
      decreasing card current;
      const x := the Element of current;
      if x < best do best := x; end;
      visited := visited \/ {x};       :: ghost update — erased at extraction
      current := current \ {x};
    end;
    return best;
  end;
end;
```

オプションの `as T` アノテーションは、Mizar の `reconsider x = e as T` に対応します。これは、初期化子式の型が `T` であることをアサートします。強制の拡張 (例: `Nat` から `Integer`) とoverloadされたリテラルの曖昧さの解消 (例: `0 as Real`) は型階層によって自動的に解決され、証明は必要ありません。縮小強制 (例: `Integer` から `Nat`) は証明義務を生じます。自動証明器がそれを無効にできない場合は、正当な理由 (`by` または `proof ... end`) を指定します。

```mizar
var n := some_int as Nat by non_negative_lemma;
var m := some_int as Nat
proof
  some_int >= 0 by ...;
  thus some_int is Nat;
end;
const r := 0 as Real;             :: automatic — no justification needed
```

注釈が完全に省略された場合、型は初期化子の式から推測されます ([第 8 章、型推論](./08.type_inference.md) を参照)。

**複数のバインディング**が 1 つの `var` または `const` ステートメントに出現する場合があります。末尾の `as T` 注釈は、ステートメント内のすべてのバインディングに適用されます。個々のバインディングに異なる型の注釈または正当化が必要な場合は、別のステートメントを使用します。

```mizar
var a := 1, b := 2 as Nat;          :: two vars, both typed Nat
const lo := 0, hi := n - 1 as Nat;   :: two constants, shared type
```

**未初期化の束縛** は代入前の使用を拒否する。match捕捉は独立した分岐局所の
不変構文束縛であり (§20.2.5)、外側の可変変数への初期代入ではない。

### 20.1.4 割り当て

可変変数は `:=` で更新されます。

```ebnf
assignment ::= lvalue ":=" algorithm_rhs ";" ;
lvalue     ::= identifier
             | lvalue "." identifier ;
```

右辺は任意の項式です。左側は、`var` で宣言された識別子またはそのフィールドでなければなりません。 `const` 識別子、`let` にバインドされた変数、またはパラメーターに代入すると、**コンパイル時エラー**になります。

右辺は代入前状態で評価されます。VC 生成では、代入を蓄積済み fact への
テキスト置換としてモデル化しません。代わりに、変更され得る mutable location
に対して fresh な old-state 名を導入し、target と alias しない free location
だけを含む fact を保存し、post-state equality を追加します。たとえば
`x := x + 1` は pre-state の値 `x₀` を記録して `x = x₀ + 1` を追加します。
既存 fact `x = 5` を `x + 1 = 5` へ書き換えることはありません。field update も
同じ old-state discipline を使います。`p.f := e` は `p` と `e` を pre-state で
評価してから、`p.f` の解決済み lvalue identity を更新します。

この節でいう alias は、同じ mutable storage cell に対する複数の解決済み
lvalue path を指します。通常の値に reference semantics があるという意味ではありません。
`var y := x` は `x` の値をコピーするだけで、`y` を `x` の alias にはしません。

`ghost var` 識別子への割り当てには、同じ `:=` 構文が使用されます。検証器は宣言からターゲットがゴースト変数であると判断します。 `ghost var` または `ghost const` 値を非ゴースト変数に割り当てると、**コンパイル時エラー**になります。ゴースト値には実行時表現がなく、非ゴースト状態に影響を与えてはなりません。

```mizar
counter := counter + 1;              :: runtime assignment
state.value := state.value + 1;      :: field update
S_visited := S_visited \/ {x};       :: ghost assignment — legal, target is ghost var
counter := S_visited;                :: compile-time error — ghost value on rhs of non-ghost assignment
```

## 20.2 制御フロー

### 20.2.1 条件付き(`if`)

```ebnf
if_stmt ::= "if" formula "do" algo_statement_list if_tail ;
if_tail ::= "end" ";"
          | "else" if_stmt
          | "else" algo_statement_list "end" ";" ;
```


```mizar
if n = 0 do
  return 1;
end;

if n mod 2 = 0 do
  return n div 2;
else
  return 3 * n + 1;
end;

:: if-else-if chain
if n < 0 do
  return -1;
else if n = 0 do
  return 0;
else
  return 1;
end;
```

`return` が使用される場合、両方の分岐が同じ型を返すか、両方が後続のステートメントに渡される必要があります。

### 20.2.2 有界ループ(`while`)

```ebnf
while_stmt ::= "while" formula "do"
                 { while_annotation ";" }
                 algo_statement_list
               "end" ";" ;

while_annotation ::= "invariant" formula [ justification ]
                   | "decreasing" term_list [ justification ] ;
```

`while_annotation` 句 (`invariant`、`decreasing`) は、他のステートメントの前に、`while` 本体の **先頭**に表示されます。オプションの `justification` は、句によって生成される検証条件の補題を提供します: `invariant` の確立と維持、`decreasing` の厳密な減少。

```mizar
var i := 1;
var s := 0;
while i <= n do
  invariant s = i * (i - 1) div 2 & i >= 1 by arithmetic, triangle_step;
  decreasing n - i + 1 by arithmetic;
  s := s + i;
  i := i + 1;
end;
```

### 20.2.3 範囲ループ (`for ... to`)

```ebnf
for_range_stmt ::= "for" identifier "=" expr ( "to" | "downto" ) expr
                   [ "step" expr ]
                   "do" { for_annotation ";" } algo_statement_list "end" ";" ;

for_annotation ::= "invariant" formula [ justification ] ;
```

ループ変数は本体内で不変であり、スコープはループ内にあります。境界とステップは、ループが開始される前に 1 回評価されます。 `step` 式は正の `Nat` 値である必要があります。デフォルトのステップは `1` です。

- `for i = 1 to n` — i = 1、2、…、n (昇順) を繰り返します。
- `for i = n downto 1` — i = n, n−1, …, 1 (降順) を繰り返します。
- `for i = 0 to n step 2` — i = 0、2、4、… (2 ずつ昇順) を繰り返します。
- `for i = n downto 0 step 3` — i = n, n−3, … (3 ずつ降順) を繰り返します。

```mizar
var s := 0;
for i = 1 to n do
  s := s + i;
end;

for i = 10 downto 1 do
  process(i);
end;

:: Every other element, descending
for i = n downto 1 step 2 do
  handle(i);
end;
```

終了は **自動的に保証されます** - `decreasing` 注釈は必要ありません。ループの累積効果の検証を支援するために、オプションの `invariant` 句を本文の先頭に配置できます。

```mizar
var s := 0;
for i = 1 to n do
  invariant s = i * (i - 1) div 2;
  s := s + i;
end;
```

### 20.2.4 収集ループ (`for ... in`)

```ebnf
for_collection_stmt ::= "for" identifier "in" expr [ "processed" identifier ] "do"
                          { for_annotation ";" }
                          algo_statement_list
                        "end" ";" ;
```

**有限集合**または有限列を走査する。集合では有限性を要求し、下記の集合・processed規則を使う。有限列では1からlen Sまで位置順に重複を保って走査する。processedの既存規則は集合だけに適用し、列の不変条件は次の位置に沿って検証する。列へのprocessed拡張は先送りする。ghost列から非ghost要素を束縛しない。

**集合の反復順序は実装定義、列は位置順です。** 集合では順序を保証しません。

**`processed` バインディング。** オプションの `processed V` 句が存在する場合、`V` は `set of T` 型の **ループ スコープのゴースト バインディング**であり、ループによって自動的に管理されます。

- 最初の反復の前: `V = {}`
- 要素 `x` の各反復後: ループは `V` を `{x}` で暗黙的に拡張します。
- 通常終了時: `V = S` が論理コンテキストに自動的に追加されます。
- `V` は抽出時に消去されます (実行時表現はありません)
- `processed` が省略された場合、追跡バインディングは作成されません

ユーザーは `V` に自由に名前を付け、`invariant` 句で使用します。

**不変検証。** 検証器は、ループ管理された `V` を使用して、標準の 3 つの条件をチェックします。

1. **確立** — `V = {}` で不変式が成り立つ
2. **メンテナンス** — 任意の `x ∈ S \ V` について、不変式が本体の前で成立する場合、不変式は本体の後にも成立します (`V` を `{x}` で拡張)
3. **事後条件** - 通常の終了時、`V = S` と不変条件により最終結果が得られます。

条件 2 では **任意** `x ∈ S \ V` が使用されるため、証明では特定の列挙順序が仮定されることはありません。順序の独立性は、シーケンスではなく、セット `V` に関して記述される不変条件に暗黙的に含まれます。

集合の反復順序そのものは規定されません。そのため、集合の `for ... in` ループを含むアルゴリズムを `by computation` で評価できるのは、その `ensures` が結果を一意に決める場合に限られます (§20.9.2)。

**`Fold` templateとセット functor** 順序に依存しない累積を表現する標準的な方法は、**`Fold` template algorithm** (§20.1.1) を使用することです。これは、セット値計算の再帰構造を抽象化します。

```mizar
:: Conceptual definition of the Fold template algorithm
:: Fold[op, e](S) for a commutative, associative op with unit e
::
:: terminating algorithm Fold[op, e](S) -> T
::   ensures (S = {} implies result = e)
::         & (for x being object st x in S holds
::              result = op(x, Fold[op, e](S \ {x})))
::   decreasing card S
:: do
::   if S = {} do return e; end;
::   const x := the Element of S;
::   return op(x, Fold[op, e](S \ {x}));
:: end;
::
:: The ensures clause applies Fold only to smaller sets (§20.4.1). Proving
:: it for every x in S, not only for the chosen one, is the
:: order-independence argument: for x ≠ y in S,
::   op(x, op(y, Fold[op,e](S\{x,y})))
::   = op(y, op(x, Fold[op,e](S\{x,y})))  :: by commutativity and associativity of op
:: using the induction hypothesis for S\{x} and S\{y} (§20.13.4).
```

`Fold` の `ensures` 句は `x` の選び方によらず成り立つため、結果を一意に決めます。これがまさに順序独立性です。`op` の可換性と結合性から template レベルで一度証明され、すべてのインスタンス化がそれを継承し、Pick サイトがあっても `by computation` で `Fold` を評価できます (§20.9.2)。

標準library のセットfunctorは、`Fold` の事前定義されたインスタンスです。

```mizar
:: Sum(S)              = Fold[+, 0](S)
:: Product(S)          = Fold[*, 1](S)
:: BigUnion(F, S)      = Fold[∪, {}](S)    (element mapped by F)
:: BigIntersection(F, S) = Fold[∩, univ](S) (element mapped by F)
:: Count(S, P)      = Fold[+, 0](S)     (element mapped to 1 if P holds, else 0)
```

カスタム累積を必要とするユーザーは、独自の `Fold` インスタンスを定義し、操作の可換性/結合性を引用して `ensures` の義務を果たします。

```mizar
:: Sum of elements — processed V tracks the accumulated set.
var total := 0;
for x in S processed V do
  invariant total = Sum(V);
  total := total + x;
end;
:: After normal exit: V = S (automatic), so total = Sum(S).

:: Product of elements.
var prod := 1;
for x in S processed V do
  invariant prod = Product(V);
  prod := prod * x;
end;

:: Existence check — no accumulator; visited clause not needed.
for x in S do
  if x mod 2 = 0 do
    return x;
  end;
end;
```

本体が順序に依存する場合、順序未指定の集合走査ではなく、順序付き列のfor ... inまたはfor ... toを使う。

> [！注記]
> `return` または `break` がループを早期に終了した場合、コンテキストには `V c= S` と、`V` に関する不変式の記述がすべて含まれます。事後条件 `V = S` は **通常** 終了時にのみ保証されます。

### 20.2.5 ASTパターンマッチ（`match`）

対象は `expr of T` 型に限り、不変な構造と解決済み定義で照合する。
代数的・意味上の等しさでは照合しない。捕捉した構文対象の `=` は
構造的な対象の同一性である (§20.5.3)。

```ebnf
match_stmt ::= "match" expr "do" match_case+
               [ "otherwise" algo_statement_list "end" ";" ] "end" ";" ;
match_case ::= "case" term_pattern "do" algo_statement_list "end" ";" ;
term_pattern ::= term_expression | formula ;
```

p & q等の論理式オペランド位置の裸の捕捉はexpr of booleanを表し、
未解決の零引数predを要求しない。解決済みfunc/pred頭部は記号として照合する。
反射する論理式では既存expr of booleanオペランドをR2でUID/文脈ごと埋め込み、
零引数pred定義として検索しない。

捕捉名は分岐内だけの不変な束縛で、expr型が一意に推論できれば
前置のvar宣言は不要。同じ捕捉名の複数出現は構造的に同じ部分対象を要する。
型ビューにはexprの共変性を使い、元の型・文脈を消さない。
パターン変数専用の型注記文法は先送りとする。
caseを順に試し、最初の一致を実行する。節点形は開いた集合なので
網羅性はotherwiseだけで扱い、exhaustive/exhaustiveness_proofは廃止する。
terminatingではotherwiseを必須とし (E0503)、部分的algorithmでの省略は
`otherwise fail "no case matched", e; end;` とする。
不透明な葉の内部は分解しない。Binder捕捉は§13.10に従う。

### 20.2.6 ジャンプステートメント (`return`、`break`、`continue`、`fail`)

```ebnf
return_stmt   ::= "return" [ algorithm_rhs [ justification ] ] ";" ;
break_stmt    ::= "break" ";" ;
continue_stmt ::= "continue" ";" ;
fail_stmt     ::= "fail" [ string_literal { "," expr } ] ";" ;
```

|声明 |効果 |検証義務 |
|---|---|---|
| `return expr` |値 `expr` でアルゴリズムを終了 | `expr` は `ensures` を満たす必要があります。末尾呼び出しの前提条件は解除されます。
| `return expr by ...` | `assert` + `return` (§20.4.2) の短縮形 | `return expr` と同じですが、`ensures` の放電に正当化が適用されます。
| `return` | void アルゴリズムを終了する |すべての `ensures` 条件が満たされる必要があります |
| `break` |すぐに囲まれているループを終了します |ループ `invariant` はブレークポイントで保持する必要があります |
| `continue` |次のループ反復にスキップ |ループ `invariant` は保持する必要があります。 **`decreasing` メジャーは現在の反復の開始と比較して減少している必要があります** |
| `fail` | 実行時検証失敗 (§20.9.3) で評価を止める | なし |

**すべての経路で戻る。** 戻り値の型を持つアルゴリズムでは、本体を通るすべての制御経路が `return` 文または `fail` 文で終わらなければなりません。ループを抜けた後も含め、どちらもなしで本体の終わりに到達することは静的エラーです (E0501、§22.5.5)。void アルゴリズムは本体の終わりに到達してよく、これは `return;` と同等です。

**`fail` — 明示的な実行時失敗。** `fail` は結果を返さずに評価を止めます。MVM は実行時検証失敗 (§20.9.3、E0331) を報告し、省略可能なメッセージと、その後に並べた式の値を表示します。`fail` に至る経路は戻らず値も生まないので、検証条件を持たず、`ensures` の証明も要りません。並べる式は ghost であってはならず、報告のために MVM が評価するだけです。

`fail` は `terminating` でないアルゴリズムの中でだけ使え、`ghost` 文や仕様の論理式の中では使えません。`terminating` のアルゴリズムは `requires` を満たすすべての入力で戻らなければならないため、そこでの `fail` はエラーです (E0503、§22.5.5)。失敗を捕捉する構文はなく、失敗は評価全体を終わらせます。

```mizar
definition
  let a, b be Integer;

  algorithm exact_div_algo(a, b) -> Integer
    ensures result * b = a
  do
    if b = 0 do fail "division by zero"; end;
    if a mod b <> 0 do fail "not divisible:", a, b; end;
    return a div b by ...;
  end;
end;
```

**`continue` と終了。** `continue` は、終了チェックが通常行われるループ本体の終わりをバイパスするため、検証器は、`decreasing` メジャーが `continue` ポイントで **すでに減少している**ことを確認します。 `decreasing` アノテーションが存在しない場合、`continue` は終了義務を生成しません (ループは分岐する可能性があるものとして扱われます)。

```mizar
:: continue: the decreasing measure must have already decreased at the continue point.
while i <= n do
  invariant s = sum_of_odds_up_to(i - 1);
  decreasing n - i + 1;
  if i mod 2 = 0 do
    i := i + 1;
    continue;  :: n - (i + 1) + 1 < n - i + 1 already holds before continue
  end;
  s := s + i;
  i := i + 1;
end;
```

## 20.3 非決定論（選択）

**Pick** 操作は、Mizar の既存の `the` 用語形式を使用して表現された、空ではないセットから任意の要素を選択します。これらは、新しい第 20 章固有の式ではありません。これらは、従来の Mizar とまったく同様に、一般的な `term_expression` 構文 (第 13 章) の一部のままです。この章では、Mizar の既存の `the` 式のアルゴリズム 意味論に対してのみ **Pick** という名前を使用します。

```mizar
const x := the Element of S;    :: pick any element of S
const p := the prime Number;     :: pick any prime
```

**意味論。** 実行可能な algorithm body の外では、`the` は
[第13章, §13.5](./13.term_expression.md#135-選択演算子-the) で定義される
安定 choice 項です。algorithm body の内部では、`the T` を含む statement 右辺が
`ControlFlowIr` の site-local Pick binding へ低位化されます。これには
`const`/`var` initializer と後続の assignment が含まれます。論理 VC はその
binding を membership または型述語を満たす任意の fresh 値として扱い、その
binding が non-ghost state に流れる場合、MVM は実行時に具体値を非決定的に
1 つ選びます。ghost state だけに流れる Pick binding は仕様専用であり、ghost state
とともに消去されます。それでも同じ non-emptiness obligation を生成し、non-ghost
computation へ流れてはなりません。algorithm specification formula (`requires`、
`ensures`、`assert`、`invariant`、`decreasing`) は runtime Pick site を作らず、
第13章の stable choice semantics を使います。周囲の証明システムから見えるのは
algorithm contract だけであり、内部の生成 choice 名は観測できません。各 Pick site は、
program が結果を明示的に変数へ格納して再利用しない限り、それぞれ fresh binding を導入します。

**証明の安全性。** アルゴリズムのコントラクト (`requires`、`ensures`) は、周囲の証明システムから見える唯一のインターフェイスです。 Pick の結果を記述する `ensures` 句は、**すべて**の可能な選択肢に適用される必要があります。検証器はその旨の証明義務を負います。 `ensures` に記載されていないプロパティは、選択に関係なく、呼び出し元が想定することはできません。この封じ込めにより、アルゴリズム内の非決定性が外部の証明を黙って弱めることができないことが保証されます。

**計算の制限。** MVM は Pick の値を非決定的に選ぶため、ゴーストでない Pick サイトを含むアルゴリズムを `by computation` で評価できるのは、その `ensures` が結果を一意に決める場合に限られます (§20.9.2)。関係的契約だけではE1の関数記号導入・昇格を正当化できない。

**非空性義務。** 検証器は各ピック サイトで非空性義務を生成しますが、その形式はバリアントによって異なります。

- *セットベース* (`the Element of S`): 義務 `S <> {}` は、証明によって免除される検証条件です。静的に示せない場合、部分的な algorithm では非ghostの未対応経路に暗黙の `fail` を置き、ghostだけのPickは失敗できないため静的に義務を解消し、`terminating` では拒否します (E0503)。実行時検査で正常返却の義務を置き換えません。
- *型ベース* (`the prime Number`): 義務は、型が**存在**であることです。つまり、その型の用語が少なくとも 1 つ存在します。これは、静的に実行される標準的なMizar 型居住義務です。実行時チェックは必要ありません。

```mizar
definition
  let S be finite set of Integer;

  terminating algorithm check_even_exists(S) -> boolean
    ensures result = true iff ex y being Integer st y in S & y mod 2 = 0
  do
    var current := S;
    while current <> {} do
      invariant current c= S;
      invariant for y being Integer st y in S \ current holds y mod 2 <> 0;
      decreasing card current;
      const x := the Element of current;
      if x mod 2 = 0 do
        return true;
      end;
      current := current \ {x};
    end;
    return false;
  end;
end;
```

> [！注記]
> MVM で Pick 式を実行できるかどうかは、有限性ではなく、MVM が実行時に具体的な監視を生成できるかどうかによって決まります。
> - `the Element of S` ここで、`S` は実行時に既知の有限セットです。MVM は `S` を列挙し、要素 (**実行可能file**) を選択できます。
> - `the prime Number`: Mizar libraryが計算可能な正規表現 (`2` など) を登録している場合、MVM はそれを使用できます (**実行可能file**)。
> - どのアルゴリズムも有限時間内に具象要素を生成できないタイプまたはセット: **実行可能ではありません**。たとえば、`S` のメンバーシップが決定できない `the Element of S` などです。
>
> 実行不可能な Pick 式は、アルゴリズム定義において依然として数学的に適切であり、論理仕様 (契約) のみが重要な証明に使用できます。実行不可能な Pick を含むアルゴリズムは、`terminating` に昇格できません。

R1の構文入力でthe式を反射する場合は不透明な葉として保存し、実行時Pickに
しない。上記Pick規則は実行値の計算についてのもので、ghostの仕様上の義務を
別に保持する。

## 20.4 契約 (`requires`、`ensures`、`assert`)

### 20.4.1 事前条件と事後条件

- `requires P` — `P` はすべての通話サイトで保持する必要があります。アルゴリズム本体は `P` を想定する場合があります。
- `ensures Q` — `Q` は正常終了時に保持されます。 `Q` の `result` は戻り値を指します。

アルゴリズムの `requires` 句と `decreasing` 句は、そのアルゴリズム自身や、その再帰グループ (§20.8.2) の他のメンバーを適用してはなりません。定義域と測度が、定義しようとしている関数自身に依存してはならないためです。`ensures` 句がそれらを適用できるのは、アルゴリズムとその再帰グループのすべてのメンバーが `terminating` と宣言されている場合 (§20.7.2) に限られます。これにより、各適用は昇格した functor の値を表します。アルゴリズム自身の検証では、見出しの `decreasing` 測度 (§20.5.2) が厳密に小さい引数についてだけ、契約を §20.13.4 の帰納法の仮定として使えます。現在の引数については何も仮定されず、見出しの測度が宣言されていない場合は何も仮定されません。それ以外の自己参照は拒否されます (E0502、§22.5.5)。

各句は、固定順序 `requires` → `ensures` → `decreasing` で最大 1 回出現します。句内の複数の条件は、`&` または `and` を使用して表現されます。

```mizar
definition
  let a, b be Real;

  algorithm divide(a, b) -> Real
    requires b <> 0
    ensures result * b = a
  do
    return a / b;
  end;
end;
```

契約は**証明義務**です:
- 各呼び出しサイト `divide(x, y)` で、検証器は `y <> 0` の証明を要求します。
- `return v` の後、検証器は `v * b = a` であるという証明を要求します。

自動証明器が義務を履行できない場合、ユーザーは関連するサイトで正当な理由 (`by` または `proof ... end`) を含む `assert` (§20.4.2) を追加します。

### 20.4.2 インラインアサーション

```ebnf
assert_stmt ::= "assert" formula [ justification ] ";" ;
```

`assert P` は証明チェックポイントを挿入します。検証器は、現在の論理コンテキストと引用された補題またはインライン証明を使用して、そのプログラム ポイントで `P` を確立する必要があります。

**`return expr by ...` — インライン アサーションの省略表記。**
`return` が正当化を伴う場合、それは `expr` の `ensures` 事後条件を実行し、その後に `return` を実行する `assert` の糖衣構文です。

```mizar
  ensures result = a
do
  ...
  return b by th1;   :: sugar for: assert a = b by th1; return b;
  ...
```

アサートされた式は、返された式によって `result` が置換された `ensures` 句です。  完全な `proof ... end` ブロックの使用も許可されます。

```mizar
  return b
  proof
    ...
  end;
```

```mizar
definition
  let arr be FinSequence of Real;
  let lo, hi, target be Integer;

  algorithm binary_search(arr, lo, hi, target) -> Integer
  do
    var l := lo;
    var r := hi;
    while l <= r do
      invariant lo <= l & r <= hi;
      decreasing r - l + 1;
      const mid := (l + r) div 2;
      assert l <= mid & mid <= r by arithmetic;
      if arr.mid = target do
        return mid;
      else if arr.mid < target do
        l := mid + 1;
      else
        r := mid - 1;
      end;
    end;
    return -1;
  end;
end;
```

### 20.4.3 検証義務

|構築 |義務 |
|---|---|
|サイト `f(args)` に電話する | `requires` `f` の前提条件、`args` でインスタンス化 |
| `return expr` | `ensures` 事後条件、`result` が `expr` にバインドされる |
| `assert P` | `P` はそのプログラム ポイントで保持されます。
| `break` ループ内 |ループ `invariant` はブレークポイントで保持されます |
| `continue` ループ内 |ループ `invariant` は継続ポイントで保持されます。 `decreasing` メジャーは、現在の反復の開始と比較してすでに減少しています。
| `fail` | なし。`terminating` のアルゴリズムでは使えない |
|可変状態の集合 `for x in S` |ループ `invariant` は、結果が順序に依存しないことを証明するために、(`ghost var` 経由で) セットベースのfunctorに関して記述する必要があります。
| `for x in S` | `S` は `finite` |
| `the Element of S` | `S <> {}` |
| `decreasing e` (ループ) | `e` は `Nat` 値です。 `e` はループ反復ごとに厳密に減少します。
| `decreasing e` (ヘッダー) | `e` は `Nat` 値です。 `e` は再帰呼び出しごとに厳密に減少します。
| `terminating` |すべての `decreasing` 対策が有効です。アルゴリズムは、`requires` を満たすすべての入力に対して戻ります。

## 20.5 ループ検証

### 20.5.1 ループの不変条件 (`invariant`)

ループ不変式は次の条件を満たしている必要があります。
1. **最初の反復 (確立) の前**。
2. **後続のすべての反復のループ先頭** (メンテナンス)。
3. **通常の終了時** — ループ条件が false になったとき。
4. **すべての `break` ステートメント** — ブレークポイントで不変式が保持される必要があります。
5. **すべての `continue` ステートメント** — 継続点で不変式が保持される必要があります (ループは先頭から再入力されます)。

```mizar
var i := 1;
var s := 0;
while i <= n do
  invariant s = (i - 1) * i div 2;
  decreasing n - i + 1;
  s := s + i;
  i := i + 1;
end;
:: After loop: i = n + 1, s = n * (n + 1) div 2
```

複数の `invariant` 句は接続詞として解釈されます。

### 20.5.2 終了措置(`decreasing`)

```ebnf
(* loop termination — inside while body, via while_annotation *)
(* while_annotation ::= "invariant" formula | "decreasing" term_list ; *)

(* recursion termination — in algorithm header *)
(* algorithm_def ::= ... [ "decreasing" term_list ] algorithm_body ";" ; *)

term_list ::= term_expression { "," term_expression } ;
```

`decreasing` 注釈は、次の 2 つの異なる位置で使用されます。

- **アルゴリズム ヘッダー** (`algorithm_def` の `[ "decreasing" term_list ]`) — 再帰終了手段を宣言します。タプルは再帰呼び出しごとに減少する必要があります。
- **`while` 本体** (`while_annotation`) — ループ終了措置を宣言します。タプルは反復ごとに減少する必要があります。

`for` ループは `decreasing` を受け入れません**。有限セットの反復は有限性義務によって終了することが保証されています。

どちらの立場でも、検証器は同じ義務を生成します。

1. リスト内のすべての式は **`Nat` 値 ** (負ではない整数) です。
2. タプルは、ループの反復または再帰呼び出しごとに **辞書順に減少**します。

|フォーム |注文 |例 |
|---|---|---|
| `decreasing e` | `<` の `Nat` | |
| `decreasing e, f` | `Nat × Nat` の辞書編集用 `<` | |

十分に根拠のあるカスタムの順序付けを行うには、`decreasing` を使用する前に、ユーザー定義のfunctorを介してメジャーを `Nat` にマップします。

```mizar
:: User-defined measure mapping a tree to its depth (a Nat)
const d := tree_depth(t);
decreasing d;
```

非負性義務 (`e >= 0`) は定義サイトで履行されます。自動証明器がそれを確立できない場合は、`assert` を追加します。

```mizar
assert n - i >= 0 by arithmetic;
decreasing n - i;
```

#### 構造・構築・尺度（S1–S7）

expr対象は不変・有限・非循環の構造とし、DAG共有を許す。
Var(κ)、Node_f(args)、Opaque(e)、Abs(κ,A,B,b)は説明用メタ記法であり、
公開構成子・UID APIではない。構造的な `=` は節点種、解決済み定義、
リテラル内容、葉に保存した精緻化済み元式、順序付き部分構造、宣言UIDを比較する。
α改名は別の木であり、意味の等しさは別に扱う。共有・キャッシュ・格納先・
診断位置を含めず、子列/FVの一致だけで不透明な葉を同一視しない。

R1はexpr of Tの期待位置のT型項（booleanの場合は論理式）を反射する。
R2は既存expr対象を自由UIDと必要文脈を保って埋め込む。
R3は解決済みfunc/predを節点にし、通常引数を反射しexpr引数を埋め、完全な
仮引数順を使う。昇格terminatingを含めalgorithm適用は常に実行し、返却木は
R2で埋め込む。型拡大は元の型・UID・必要条件を保持する。意味には明示的valを
用い、R2を含む構築コードを自動的に元の数学項とはしない。

|---|---|---|
| Var(κ) | 空列 | FV={κ}、size=1 |

返し本体と契約で使える。取得・照合で格納済みUIDと各子の元の型・文脈を保つ。

付値やBinder再構成の権利を与えない。非変数tではFV(t)が子FVの和集合に
含まれる。宣言の子により依存を過大評価してよい。

割り当て節点数ではない。各子の厳密な減少を構造帰納・再帰停止に使う。
直接の子でない再帰引数も、選んだ尺度の厳密な減少と他の義務を示せれば許す。
MVMに検証済みdecreasingのサイズを毎回再計算することは要求しない。
具体的サイズは正確な自然数とし、オーバーフロー・飽和・丸めを採用しない。
共有・キャッシュで展開木の実体化を避けてよい。資源切れは未完了とする。
有限構造だけで意味規則の無矛盾性や任意の定義展開の停止を説明しない。
expr_sizeとval/val_at/valid_atはghost（意味規則は本節）。通常の条件・返値・
反復回数・非ghost列の要素へghost値を持ち出せず、列走査の例外も置かない。
ライブラリ評価器は対応構文だけを通常演算で計算しresult=val tを証明できる。
有限・閉じた・Nat型という条件だけで万能の評価器を認めない。

#### 意味・環境・付値（M1–M8）

保持文脈Γには元の宣言、型・属性、適用・依存条件、検証済み型ビューの
必要前提を記録する。Adm_Γ(ρ)は環境ρでのそれらの充足を表す。
意味上のFVは値の式について定め、y:Element of A(x)のFVは{y}で、
xへの依存はAdmに保持する。公開環境型・置換APIは追加しない。

t:expr of Tに対するval t:ghost const Tは、現在の適合論理環境での
内部Val(t,ρ)を表す。論理式の木pの命題はval p=trueであり、
val p自体はbooleanの **項** であってFOL論理式ではない。

| 規則 | 意味と条件 |
|---|---|
| M1 | Val(Var(κ),ρ)=ρ(κ)。Val(Node_f(p1,…,pn),ρ)=f(Val(p1,ρ),…)。pred PではVal(Node_P(args),ρ)=true iff P(Val(args),…)。暗黙値・解決済み署名・適用条件を含む。論理節点は&,or,not,implies,iffの真理条件を使う。 |

| M3 | Opaque(e)は保存した精緻化済み項の意味、Opaque(P)は保存した論理式の成立とtrueの同値を持つ。量化式も自由UID・型文脈を保持。不透明性は構造分解の制限であり、真理条件を捨てない。 |
| M4 | Binderは内部の拡張環境と認定された関数構成で解釈し、空領域も扱う (§13.10)。 |
| M5 | UID iの変数節点xと共通の適合文脈Γについて、Adm_Γ(ρ) implies (valid_at(t,x,v) iff Adm_Γ(ρ[i↦v]))。vは更新 **前** に解釈。元の型・属性、依存宣言・適用条件、型ビューの必要前提を保持する。 |

M8のargsは実行・契約・returns・論理関数記号で同じ完全入力とし、構文、
通常値、必要な保持文脈、使用する再構成C (§13.10) を含む。一環境の前提を
別環境での再利用の根拠にしない。Binder本体へ入る際は環境の対応と前提を
改めて示す。空領域を含め本体の照合から環境・領域要素・具体的意味を得ない。
全称契約の空虚な成立からもそのような値を生成しない。

公開val_atには変数節点・文脈の整合と、**局所** 文脈での更新条件の証明を要する。
valid_atは無効な更新について述べたり否定できるが、値・環境を生成しない。
有限な条件記録KΓとAdm_Γ(ρ) iff conjunction KΓ(ρ)の対応を持ち、
生成規則は分類表の各行に従う。使用した型・属性・依存・適用・view前提だけを
記録し、全周辺仮定を集めない。量化条件は有限な式とし要素を列挙しない。
valid_atの展開は同値条件を記述するだけで、その証明ではない。
制限付き量化と含意のガードを局所的に保持し、ガード付き更新に対し
全ての候補vで無条件に適合すると示すことは要求しない。

依存する子の意味は更新後環境の内部Valで合成し、各子について型の不正な
公開val_atを機械的に生成しない。通常項の代入補題は両環境の適合性の下で
`⟦e[i:=w]⟧ρ = ⟦e⟧(ρ[i↦⟦w⟧ρ])`、論理式では真理条件の同値とする。
自由UID出現だけを捕獲回避で置換し、束縛・必要な型/領域参照を区別する。
他UIDを固定し、挿入したw内部へ再び同じ代入をせず、表示名で置換しない。
この補題はiがFVに含まれる不透明な葉も扱い、非出現の場合だけではない。
認定した反射範囲を要求し、無制限な自己評価を除く。

check_occursのfalse契約は全適合環境でval/val_at/valid_atによる更新不変性を
述べる。構造上の非出現は内部証明補題であり、trueから意味依存を結論しない。
y=0の一点ではy |-> y*xのxに関する不変性を証明できない。
検証済み型ビューには全入力の値域証明と保持前提を要し、一点の観察では足りない。

構文構築では、解決済み期待型がexpr of booleanとなる初期化・代入・返値の
位置で論理式をR1反射する。通常RHSは項とし、既存boolean論理式返却規則
(§20.13.6)だけを例外として保つ。後者は通常論理式を反射せず評価し、ghost意味を
実行値へ流入させない。主張ラベル/thesisは明示computation入力に限る。

## 20.6 スナップショットとクレーム

### 20.6.1 スナップショット

**スナップショット**は、特定のプログラム ポイントにおけるアルゴリズムの完全なローカル状態を記録します。これは仕様のみの構成です。スナップショットはコード抽出時に消去され (§20.10)、実行時のコストはかかりません。

```ebnf
snapshot_stmt ::= "snapshot" identifier ";" ;
```

スナップショットは、その時点で表示されるすべてのバインディング (`var`、`const`、`ghost var`、`ghost const`、およびアルゴリズム パラメーター) を単一の名前でキャプチャします。スナップショット名はアルゴリズム本体内で一意である必要があります。

### 20.6.2 クレームブロック

`claim` ブロックは、単一アルゴリズムのスナップショット状態に関する定理をグループ化し、`requires`/`ensures` コントラクトだけで述べられるものを超える内部検証プロパティを表現します。

```ebnf
claim_block ::= "claim" identifier "do"
                  { annotated_theorem_item }
                "end" ";" ;
annotated_theorem_item ::= { annotation } theorem_item ;
```

識別子は、スナップショットがスコープ内に取り込まれるアルゴリズムの名前を指定します。ブロック内では、スナップショット変数は `S.x` (スナップショット `S`、変数 `x`) としてアクセスされます。

**普遍的定量化。** `claim` ブロック内のすべての定理は、すべての有効な実行、つまり、
アルゴリズムの `requires` 前提条件を満たすすべての呼び出しにわたって、暗黙的に普遍的に
定量化されます。theorem proposition 内の reserved identifier は、この execution-level
quantification を適用する前に、§4.3 に従って先に閉包されます。

**スナップショット 意味論。** スナップショットは、完全なローカル状態、つまりそのプログラム ポイントで表示されるすべての `var`、`const`、`ghost var`、および `ghost const` バインディングとアルゴリズム パラメーターをキャプチャします。

### 20.6.3 例

次のアルゴリズムは、`0` から `n` までカウントします。スナップショット `Init` は、ループ前の状態をキャプチャします。スナップショット `S` は、各反復の先頭の状態をキャプチャします。

```mizar
definition
  let n be Nat;

  algorithm count_up(n) -> Nat
    requires n >= 0
    ensures result = n
  do
    var x := 0;
    var i := 0;
    snapshot Init;
    while i < n do
      snapshot S;
      x := x + 1;
      i := i + 1;
    end;
    return x;
  end;
end;

claim count_up do
  :: state before the loop
  theorem InitState:
    Init.x = 0 & Init.i = 0;

  :: loop invariant: accumulator equals iteration counter at each step
  theorem Progress:
    S.x = S.i;
end;
```

`InitState` は、ループが開始される前に `x` と `i` が両方とも 0 であることを示します。 `Progress` は、各反復ステップでアキュムレータ `x` がカウンタ `i` と等しいことを示します。これは、`ensures result = n` だけではキャプチャできない内部プロパティです。

## 20.7 終了証明

### 20.7.1 終了措置の宣言

再帰的アルゴリズムの場合、`decreasing` はコントラクトと本文の間の **アルゴリズム ヘッダー**に配置されます。

```mizar
definition
  let m, n be Nat;

  terminating algorithm ackermann(m, n) -> Nat
    decreasing m, n
  do
    if m = 0 do
      return n + 1;
    end;
    if n = 0 do
      return ackermann(m - 1, 1);
    end;
    return ackermann(m - 1, ackermann(m, n - 1));
  end;
end;
```

検証器は、再帰呼び出しごとにタプル `(m, n)` が辞書順に減少していることをチェックします。

- `ackermann(m - 1, 1)` — 最初のコンポーネント `m - 1 < m`。 ✓
- `ackermann(m, n - 1)` — 最初のコンポーネントは等しい、2 番目の `n - 1 < n`。 ✓
- `ackermann(m - 1, ackermann(m, n - 1))` — 最初のコンポーネント `m - 1 < m`。 ✓

### 20.7.2 アルゴリズムの終了と`func`への昇格

`terminating` のアルゴリズムは、その保証を検証した後、`requires` を満たすすべての入力で **正常返却** することを保証します。これにより、`by computation` 証明だけでなく、任意の形式的推論においても、`func` が期待されるあらゆる場所でアルゴリズムを使用できるようになります。

これが、再帰定義を数学的な `func` レイヤーへ入れる唯一の経路です。通常の
`func` 定義は一階述語論理の定義拡張であり、再帰的にはできません (§10.3.3)。
意図した定義が自己呼び出しまたは相互再帰呼び出しを必要とする場合は、
`algorithm` として書き、`decreasing` などの終了根拠を与え、生成された終了性の
証明義務を解消してから、検証済みの `terminating` 昇格に依存します。

`algorithm_def` の完全な文法については、§20.1.1 を参照してください。

```mizar
definition
  let n be Nat;

  terminating algorithm FactorialDef: factorial(n) -> Nat
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    return n * factorial(n - 1);
  end;
end;
```

`terminating` が宣言され検証されると、`factorial` をfunctorとして使用できるようになります。

```mizar
theorem FactorialZero: factorial(0) = 1 by FactorialDef;
theorem FactorialStep:
  for n being Nat holds factorial(n + 1) = (n + 1) * factorial(n)
  by FactorialDef;
```

どちらの定理も、この定義的アルゴリズムに対して昇格が生成する定義式から従います (§20.7.3)。定義ラベルを引用すると、その昇格公理が引用されます (§16.5.1)。

> [！注記]
> `terminating` がなければ、algorithm は第一級の functor に昇格せず、そのような functor として普遍量化できません。計算可能な場合 (§20.9.3) は、評価時の検査を条件として、具体的な値に対して `by computation` で呼び出せます。評価が完了すれば、その 1 回の呼び出しが戻ることが示され、契約がその呼び出しに適用されます (§20.13.1)。

検証済みの保証は `P(x) implies ex r st returns_f(x,r)` の形とし
（void では r を省略）、宣言だけからは発行しない。
構文入力では各適合環境のAdm_Γ(ρ)、InputOK(x,ρ)、P_ρ(x)と、
同じ完全な論理入力を保持する。
明示・暗黙の失敗、部分的な子呼び出し、反復範囲の評価も対象とする。
部分的な子呼び出しごとに前提と正常返却の証拠を要求し、後続経路へ
到達したとの仮定は部分正当性だけを示す。単なる停止や値の等式では足りない。
この論理上の保証は任意の有限な MVM 資源上限内での完了を保証しない。
失敗・資源切れの試行は、新しい正常返却も、あらゆる正常返却の不存在も示さない。

### 20.7.3 定義的アルゴリズム

本体が下記の**定義的断片**に収まる `terminating` アルゴリズムを**定義的アルゴリズム**と呼びます。このとき昇格は、アルゴリズムの**定義式** (§20.13.6) も生成します。定義式は `return` 文ごとに 1 つのガード付き等式で、条件付きの `equals` 定義 (§10.12.2) と同じ形をしています。したがって、昇格した functor は再帰的であっても、`func` と同じように展開して推論に使えます。生成は自動で行われ、追加の構文は必要ありません。`by` で定義ラベルを引用すると、他の昇格公理とともに定義式が引用されます (§16.5.1)。

| 本体の要素 | 定義的断片 |
|---|---|
| `const` と `ghost const` の宣言 | 可 |
| `if` / `else` | 可 |
| `return` (正当化の有無を問わない) | 可 |
| `func`、`pred`、昇格したアルゴリズム、同じ再帰グループのメンバーの呼び出し | 可 |
| `ghost` 文、`assert`、スナップショット、claim ブロック | 可。定義式には寄与しない |
| `var` の宣言と代入 | 不可 |
| `while`、`for ... to`、`for ... in`、`break`、`continue` | 不可 |
| `match` | 不可 |
| ゴーストでない Pick (§20.3) | 不可 |
| 昇格していないアルゴリズムの呼び出し | 不可 |

可変な状態とループは、`return` ごとに閉じた等式を 1 つ与えないため除外されます。`match` は、ケースの仮定 `e = π` (§20.2.5) がキャプチャされる部分項を一意に定めないため除外されます。ゴーストでない Pick は、結果が一意でないため除外されます。

`factorial` (§20.7.2) と `fibonacci` (§20.8.1) は定義的アルゴリズムです。functor の同義語 (§11.1.2) を使うと、別の `func` 定義を書かずに、定義的アルゴリズムに数学的な記法を与えられます。

```mizar
synonym n ! for factorial(n);
```

**定義的断片の外にあるアルゴリズム。** 定義的断片の外にある停止アルゴリズムは、全体性と契約の公理だけを伴って昇格します (§20.13.2)。数学的な定義と結び付けるには、先に通常の `func` として関数を定義し、その関係を `ensures` に書きます。証明はアルゴリズム内部のループ不変式が担います。本体は展開されないため、外部の定理ではこの証明を行えません。

```mizar
definition
  let x, n be Nat;
  func power(x, n) -> Nat equals x |^ n;
end;

definition
  let x, n be Nat;

  terminating algorithm fast_power_loop(x, n) -> Nat
    ensures result = power(x, n)
  do
    var r := 1;
    var b := x;
    var e := n;
    while e > 0 do
      invariant r * power(b, e) = power(x, n);
      decreasing e;
      if e mod 2 = 1 do
        r := r * b;
      end;
      b := b * b;
      e := e div 2;
    end;
    return r;
  end;
end;
```

別の方法として、再帰的な特徴付けを直接 `ensures` に書くこともできます (§20.4.1)。次のループは階乗を計算します。見出しの `decreasing n` が帰納法の仮定を与え、不変式の証明に必要な契約は `n` より小さい引数についてのものだけです。

```mizar
definition
  let n be Nat;

  terminating algorithm fact_loop(n) -> Nat
    ensures (n = 0 implies result = 1)
          & (n > 0 implies result = n * fact_loop(n - 1))
    decreasing n
  do
    var r := 1;
    var i := 0;
    while i < n do
      invariant i <= n & (i = 0 implies r = 1)
              & (i > 0 implies r = i * fact_loop(i - 1));
      decreasing n - i;
      r := r * (i + 1);
      i := i + 1;
    end;
    return r;
  end;
end;
```

公開された定義的アルゴリズムでは、生成された定義式は公開された命題の一部です。定義式を変える本体の変更は MAJOR の変更になります (§23.2)。

## 20.8 再帰的定義

### 20.8.1 直接再帰

アルゴリズムはそれ自体を再帰的に呼び出すことがあります。検証器は追加の注釈なしで再帰呼び出しを受け入れますが、終了を証明するために `decreasing` が必要です。 `decreasing` がない場合、アルゴリズムは部分的に定義されているものとして扱われます。

同じ再帰は `func` 定義として直接書くことはできません。一階述語論理の
`definition` レイヤーは、直接および相互の循環定義を拒否します (§10.3.3,
§22.5.2)。再帰的な数学関数は algorithm の終了性ワークフローを通して表現し、
終了性が検証された後にだけ昇格させなければなりません (§20.7.2)。

```mizar
definition
  let n be Nat;

  terminating algorithm fibonacci(n) -> Nat
    decreasing n
  do
    if n = 0 do return 0; end;
    if n = 1 do return 1; end;
    return fibonacci(n - 1) + fibonacci(n - 2);
  end;
end;
```

本体は定義的断片に収まっているため、昇格は定義式として、`n = 0` のとき `fibonacci(n) = 0`、`n ≠ 0 ∧ n = 1` のとき `fibonacci(n) = 1`、それ以外のとき `fibonacci(n) = fibonacci(n - 1) + fibonacci(n - 2)` を生成します (§20.13.6)。

各再帰呼び出しサイトは、`requires` 前提条件が満たされていることの証明義務を生成します。

### 20.8.2 相互再帰

2 つ以上のアルゴリズムが相互に呼び出しを行う場合があります。これらは **同じ `definition` ブロック**内に配置されます。特別な宣言は必要ありません。検証器は相互再帰を自動的に検出します。

`boolean` は組み込みの真理値型です。その値は `true` および `false` です。

```mizar
definition
  let n be Nat;

  terminating algorithm is_even(n) -> boolean
    decreasing n
  do
    if n = 0 do return true; end;
    return is_odd(n - 1);
  end;

  terminating algorithm is_odd(n) -> boolean
    decreasing n
  do
    if n = 0 do return false; end;
    return is_even(n - 1);
  end;
end;
```

`decreasing` 対策は、通話サイクル全体にわたって集合的に終了を確立する必要があります。検証器は、無限の呼び出しシーケンスが発生しないことを確認します。グループのすべてのメンバーが定義的である場合、各メンバーはそれぞれの定義式を受け取ります (§20.13.6)。

## 20.9 実行モデルと計算可能性

### 20.9.1 Mizar 仮想マシン (MVM)

**Mizar Virtual Machine (MVM)** は、検証中にアルゴリズム式を評価します。次の場合に呼び出されます。

- `by computation` 証明ステップが使用されます (§20.9.2)。
- アルゴリズムは、検証コンテキストで完全に具体的な (根拠) 引数を使用して呼び出されます。

MVM は **値による呼び出し** モデルを使用します。副作用はローカルの `var` 状態に限定されます。グローバルな可変状態はありません。

**パッケージ間の計算は `public` / `private` の可視性に従います。** 可視性を省略した場合も含め、計算可能な public algorithm はインポート側の MVM 評価と `by computation` に利用できます。公開処理は、その計算用インターフェースに対応する検証済みランタイムアーティファクトを提供しなければなりません。別の公開フラグによる選択は行いません。private algorithm はインポート側から直接名前を参照・呼び出しできません。計算不可能な public algorithm は契約を通じて利用できます。評価には検証済み成果物と実行依存が必要であり、成果物の欠落はエラーです。契約のみを公開するためのモードではありません。依存ソースがローカルにあること (`path` / `git` 依存) で検証を省略することはできません。

成果物は、公開 algorithm の識別子・署名・契約を、実行内容・検証証拠・実行依存・互換な MVM 意味論に結び付けなければなりません。その検証は、実行内容が検証済み algorithm を実装することを保証します。任意の提供コードの実行や未検証の結果への信頼は証明になりません。契約の事前条件、停止性要件、計算のリプレイ検査は引き続き適用されます。成果物は public な入口に必要な private 補助関数を含みますが、その名前をインポート側に公開しません。private 補助関数のソース上の可視性は定義ファイル内に限られ、検証済みの内部呼び出しは成果物内で実行できます。推移的な呼び出しを含め、パッケージ境界を越える呼び出しは、検証済み成果物を通じて計算可能な public algorithm を対象としなければなりません。成果物の欠落・不正を依存ソース本体のロードで補ってはいけません。

計算証明は、推移的な実行依存と MVM 意味論を含め、利用した成果物の正確な内容識別子を記録します。実行内容が変われば、パッケージ更新が意味的に互換でも、影響する計算キャッシュは無効化されます (§23.2)。契約のみを利用する側は、不透明なインポート境界を維持し、実行成果物をロードしません。

計算用公開は言語設計上の要件です。ソースの可視性構文は §12.5 で定義されています。成果物の直列化・ビルドおよびローダーのプロトコルは MVM バックエンドとともに保留です。本節は実装済みであるとは主張しません。

### 20.9.2 `by computation` の証明ステップ

```ebnf
computation_proof  ::= "by" "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_argument ::= algorithm_application | computation_option ;
computation_reference ::= "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_option ::= "steps"   ":" nat_literal
                     | "timeout" ":" nat_literal
                     | "nest"    ":" nat_literal ;
```

オプション:

|オプション |デフォルト |意味 |
|---|---|---|
| `steps` | `0` (無制限) | MVM 実行ステップの最大数 |
| `timeout` | `0` (無制限) |実時間の制限時間 (ミリ秒) |
| `nest` | `0` (無制限) |関数呼び出しスタックの最大深さ |

```mizar
theorem FactorialFiveByComputation: factorial(5) = 120 by computation;

theorem Fact10 : factorial(10) = 3628800
proof
  thus thesis by computation(steps: 100000);
end;
```

**`by computation` が証明できること:**

|ゴールフォーム | MVM の動作 |
|---|---|
| `f(v₁, …, vₙ) = c` (接地等価) | `f(v₁, …, vₙ)` を評価し、結果が `c` と等しいことを確認します。
| `P(v₁, …, vₙ)` (接地述語) | `P` を評価し、それが成立することを確認します。
| 非ground目標 | 直接実行には解決済み実行値を要する。明示構造呼び出しは変換済み検証契約と正当化した前提で非ground目標も証明できる (§20.13.7)。 |

部分的なfのf(v₁, …, vₙ)=cも通常の等式で、計算証明は内部で正常返却を確認する (§20.13.1)。どの呼び出し位置とも同様に、`v₁, …, vₙ` で `f` の `requires` が成り立つことを示す必要があります。

**決定性の要件。** `by computation` は、義務の解消に使われる他の MVM 評価 (§20.9.1) と同様に、非決定的な選択に依存しない値を与えなければなりません。目標の計算閉包、すなわち直接または推移的に評価されるすべてのアルゴリズムを考えます。その中で、ゴーストでない Pick サイト (§20.3) または順序未指定の集合 `for ... in` ループ (§20.2.4) を含む、値を返すアルゴリズム `g` は、結果を一意に決める `ensures` 句を持たなければなりません。パラメータの型ガード、前提条件 `P`、事後条件 `Q` を持つそのような `g` について、このステップは次の一意性の義務を生成します。

```
∀x₁,…,xₙ, r₁, r₂. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) ∧ Q(x₁,…,xₙ, r₁) ∧ Q(x₁,…,xₙ, r₂) → r₁ = r₂)
```

`ensures` が `result = t` または `result = true iff φ` (`t` と `φ` は `result` を含まない) の形であれば、この義務は証明なしに成り立ちます。検証済みのアルゴリズムはどの実行でも `ensures` を満たすため、結果が一意に決まっていれば、どの選択でも同じ値になります。義務を解消できない場合、このステップは拒否されます (E0330、§22.4.5)。複数結果を許す関係的契約だけではE1の関数記号導入・昇格を正当化できない。

たとえば次のアルゴリズムは有限集合を規定されない順序で走査しますが、`ensures` が結果を決めているため、`by computation` で評価できます。

```mizar
definition
  let S be finite set of Nat;
  let k be Nat;

  terminating algorithm exists_greater(S, k) -> boolean
    ensures result = true iff ex x being Nat st x in S & x > k
  do
    for x in S processed V do
      invariant for y being Nat st y in V holds y <= k;
      if x > k do return true; end;
    end;
    return false;
  end;
end;

theorem ExistsGreater: exists_greater({1, 5, 3}, 4) = true by computation;
```

`equals` や `means` で定義された `func` にはアルゴリズム本体がなく、評価されません (§20.9.3)。そのような `func` の具体的な値を示すには、`ensures` でその `func` と関係付けられたアルゴリズムの値を計算し、明示computation呼び出しで検証済み契約を取り込みます。

```mizar
theorem PowerLoop2_10: fast_power_loop(2, 10) = 1024 by computation;
theorem Power2_10: power(2, 10) = 1024 by computation(fast_power_loop(2, 10));
```

`ex x st P(x)` 形式の存在目標の場合、推奨されるアプローチは、検索アルゴリズムを明示的に実装することです。

```mizar
terminating algorithm find_witness(S) -> Integer
  requires S <> {}
  ensures result in S & P(result)
do
  ...
end;
```

`ensures` 句は、特別な MVM 検索意味論を必要とせずに、証明システム内で存在証明を提供します。

明示した呼び出しと目標内の呼び出しをともに評価し、thesisや引用事実から
未指定引数を推測しない。オプションはそのcomputation参照の全呼び出しに適用。
requires・現在の適合性・InputOKは同じ呼び出しの帰結によらず正当化する。
正常返却後にensures実例全体と通常値等式を候補とし、内部returnsと
AST引数の等式は証拠として保持する。公開候補全体を§20.13.7で変換・検査する。

### 20.9.3 計算可能性と実行時の障害

アルゴリズム定義は、非構築的な操作 (計算不可能な関数、抽象セットの選択など) を参照する場合があります。このような定義は数学的には有効ですが、MVM はそれらを実行できません。

MVM が実行不可能な操作に遭遇すると、**実行時検証エラー**が発生します。

|操作 |実行時のエラー状態 |
|---|---|
| `the Element of S` | MVM は `S` を列挙できません (たとえば、`S` は無限で、登録された列挙子がありません)。
| `algorithm` ボディなしで `func f(x)` を呼び出します | `f` には計算可能な実装がありません。
| `pred P(x)` または `func F(x)` template パラメータを呼び出します。具体的なインスタンス化には計算可能な実装がありません (例: `means` 定義のfunctor)。
|ゼロ除算 (`a / 0`) |ゼロの分母 |
| `fail` 文 (§20.2.6)。`otherwise` のない `match` の暗黙の `fail` を含む | 評価中に到達した |

実行時のエラーにより、`by computation` ステップは **失敗** しますが (E0331、§22.4.5)、アルゴリズムの定義は無効になりません。この定義は依然として数学的に意味があります。 MVM を介した実行可能性のみが制限されます。失敗した評価は、その呼び出しについて何も確立しません。

> [！注記]
> `S` が数学的に有効な無限集合である `the Element of S` (例: `NAT`) は、定義レベルではエラーではありません。 MVM は単純にそれを実行できません。このアルゴリズムは、そのコントラクトを通じて古典的な証明で引き続き使用できます。

### 20.9.4 ガス制限

分岐アルゴリズムによって検証器がハングアップするのを防ぐために、MVM は **ガス制限**、つまり `by computation` 呼び出しごとの実行ステップの最大数を強制します。

```mizar
theorem HardComputation42: hard_computation(42) = 123456789
proof
  thus thesis by computation(steps: 1000000);
end;
```

いずれかのオプションを `0` に設定すると、その制限が無効になります (デフォルト)。オプションは組み合わせることができます:

```mizar
thus thesis by computation(steps: 500000, timeout: 2000, nest: 200);
```

## 20.10 コードの抽出

検証済みのアルゴリズムからのコード抽出は、コア言語仕様の一部ではなく、**別のtool**として提供されます。エクストラクターは `terminating` アルゴリズムを採用し、ターゲット言語 (Python、GMP を使用した C、Rust など) で実行可能コードを生成し、構築によって形式的に検証されたすべてのプロパティを保持します。

ターゲット言語、数値型マッピング (C の `Nat` → GMP `mpz_t` など)、ホスト library バインディングなどの構成は、インライン アノテーションではなくエクストラクター構成fileを介して提供されます。

詳細については、抽出toolのドキュメントを参照してください。

## 20.11 完全な構文 (EBNF)

```ebnf
(* ── Algorithm definition ─────────────────────────────── *)
algorithm_def ::= ( "terminating" "algorithm" [ label_identifier ":" ] | "algorithm" ) identifier [ "[" schema_params "]" ] "(" [ identifier_list ] ")" [ "->" type_expression ]
                  [ "requires" formula ]
                  [ "ensures"  formula ]
                  [ "decreasing" term_list ]
                  algorithm_body ";" ;

identifier_list   ::= identifier { "," identifier } ;

algorithm_body    ::= "do" algo_statement_list "end" ;

(* ── Statement list ────────────────────────────────────── *)
algo_statement_list ::= { algo_statement } ;

algo_statement ::= var_decl
                 | const_decl
                 | ghost_var_decl
                 | ghost_const_decl
                 | assignment
                 | ghost_assignment
                 | if_stmt
                 | while_stmt
                 | for_range_stmt
                 | for_collection_stmt
                 | match_stmt
                 | return_stmt
                 | break_stmt
                 | continue_stmt
                 | fail_stmt
                 | assert_stmt
                 | snapshot_stmt
                 | standalone_diagnostic_annotation ;

(* ── Declarations and assignment ───────────────────────── *)
var_decl         ::= "var"         var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
ghost_var_decl   ::= "ghost" "var" var_binding   { "," var_binding   } [ "as" type_expression [ justification ] ] ";" ;
const_decl       ::= "const"       const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;
ghost_const_decl ::= "ghost" "const" const_binding { "," const_binding } [ "as" type_expression [ justification ] ] ";" ;

var_binding   ::= identifier [ ":=" algorithm_rhs ] ;
const_binding ::= identifier ":=" algorithm_rhs ;
algorithm_rhs ::= term_expression | formula ;

assignment       ::= lvalue ":=" algorithm_rhs ";" ;
ghost_assignment ::= "ghost" lvalue ":=" algorithm_rhs ";" ;
lvalue           ::= identifier
                   | lvalue "." identifier ;

justification ::= simple_justification | proof | computation_proof ;
(* simple_justification, proof, computation_proof, reasoning, references — defined in §15/§16/§20.9.2 *)

(* ── Control flow ──────────────────────────────────────── *)
if_stmt ::= "if" formula "do" algo_statement_list if_tail ;
if_tail ::= "end" ";"
          | "else" if_stmt
          | "else" algo_statement_list "end" ";" ;

while_stmt ::= "while" formula "do"
                 { while_annotation ";" }
                 algo_statement_list
               "end" ";" ;

while_annotation ::= "invariant" formula [ justification ]
                   | "decreasing" term_list [ justification ] ;

term_list ::= term_expression { "," term_expression } ;

for_range_stmt ::= "for" identifier "=" expr ( "to" | "downto" ) expr
                   [ "step" expr ]
                   "do" { for_annotation ";" } algo_statement_list "end" ";" ;

for_collection_stmt ::= "for" identifier "in" expr [ "processed" identifier ] "do"
                          { for_annotation ";" }
                          algo_statement_list
                        "end" ";" ;

for_annotation ::= "invariant" formula [ justification ] ;

match_stmt ::= "match" expr "do"
               match_case+
               [ "otherwise" algo_statement_list "end" ";" ]
               "end" ";" ;

match_case           ::= "case" term_pattern "do" algo_statement_list "end" ";" ;
term_pattern         ::= term_expression | formula ;

return_stmt   ::= "return" [ algorithm_rhs [ justification ] ] ";" ;
break_stmt    ::= "break" ";" ;
continue_stmt ::= "continue" ";" ;
fail_stmt     ::= "fail" [ string_literal { "," expr } ] ";" ;
assert_stmt   ::= "assert" formula [ justification ] ";" ;
snapshot_stmt ::= "snapshot" identifier ";" ;

(* ── Snapshot and Claim ────────────────────────────────────── *)
claim_block ::= "claim" identifier "do"
                  { annotated_theorem_item }
                "end" ";" ;
annotated_theorem_item ::= { annotation } theorem_item ;

(* snapshot_access inside claim_block theorems:                  *)
(*   snapshot_name "." identifier                                 *)

(* ── Proof step ─────────────────────────────────────────────
   Used in proof blocks (outside algorithm bodies) as:
     "thus" formula "by" "computation" ...
   or in short-form theorems:
     theorem label_identifier ":" formula "by" "computation" ... ";" *)
computation_proof   ::= "by" "computation"
                        [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_argument ::= algorithm_application | computation_option ;
computation_reference ::= "computation" [ "(" computation_argument { "," computation_argument } ")" ] ;
computation_option  ::= "steps"   ":" nat_literal
                      | "timeout" ":" nat_literal
                      | "nest"    ":" nat_literal ;

(* ── Pick expression ─────────────────────────────────────────
   Used as a term on the right-hand side of const_decl, var_decl,
   assignment, ghost_var_decl, ghost_const_decl, or ghost_assignment
   inside an algorithm body:
     const x := the Element of S ;
     const p := the prime Number ;
     ghost witness := the Element of S ;                         *)
pick_expr ::= "the" type_expression ;
algorithm_application ::= ( identifier | namespace_path "." identifier ) [ template_args ] "(" [ algorithm_inputs ] ")" ;
algorithm_inputs ::= expr_input { "," expr_input } ;
expr_input ::= term_expression | formula | label_identifier | "thesis" ;
expr_size_expr ::= "expr_size" "(" term_expression ")" ;
```

## 20.12 拡張例

### 高速累乗 (二乗による累乗)

非自明な終了手段と `by computation` によって検証された数学的 `ensures` 句を使用した再帰を示します。

```mizar
definition
  let x be Nat;
  let n be Nat;

  terminating algorithm fast_power(x, n) -> Nat
    ensures result = x |^ n
    decreasing n
  do
    if n = 0 do
      return 1;
    end;
    if n mod 2 = 0 do
      const half := fast_power(x, n div 2);
      return half * half;
    end;
    return x * fast_power(x, n - 1);
  end;
end;

:: Verified by computation for concrete inputs
theorem FastPower2_10: fast_power(2, 10) = 1024 by computation;
theorem FastPower3_5:  fast_power(3, 5)  = 243  by computation;

:: Promoted to func via terminating; usable in general proofs
theorem fast_power_correct :
  for x, n being Nat holds fast_power(x, n) = x |^ n;
```

### 整数因数分解（試行部門）

```mizar
definition
  let n be Nat;

  algorithm trial_factor(n) -> Nat
    requires n >= 2
    ensures result >= 2 & result divides n
  do
    var d := 2;
    while d * d <= n do
      invariant d >= 2 & for k being Nat st 2 <= k & k < d holds not k divides n;
      assert n - d * d >= 0 by arithmetic;
      decreasing n - d * d + 1;
      if n mod d = 0 do
        return d;
      end;
      d := d + 1;
    end;
    return n;   :: n is prime
  end;
end;
```

### ユークリッド GCD アルゴリズム

このアルゴリズムは、標準libraryで定義されている数学functor `Gcd` と区別するために、`euclid_gcd` という名前が付けられています。 `ensures` 句とループ不変式は両方とも、アルゴリズム自体ではなく `Gcd` (数学的) を使用するため、循環性はありません。

```mizar
definition
  let a, b be Nat;

  terminating algorithm euclid_gcd(a, b) -> Nat
    requires a >= 1 & b >= 1
    ensures result = Gcd(a, b)
  do
    var x := a;
    var y := b;
    while y <> 0 do
      invariant x >= 1 & y >= 0 & Gcd(a, b) = Gcd(x, y);
      decreasing y;
      const r := x mod y;
      x := y;
      y := r;
    end;
    return x;
  end;
end;

theorem EuclidGcd12_8: euclid_gcd(12, 8) = 4 by computation;
theorem EuclidGcd100_75: euclid_gcd(100, 75) = 25 by computation;
```

### 記号微分

式 AST での `match`、`expr_size` による構造再帰、および `return ... by` 短縮表現を示します。 `Expr[K, x]` は、フィールド `K` および変数 `x` に対する算術式タイプです。 `Diff(t, x)` は、支持理論で定義された数学的 (形式的導関数) functorです。

```mizar
definition
  let K be Field;
  let x be Variable;
  let t be Expr[K, x];

  terminating algorithm diff(t) -> Expr[K, x]
    ensures result = Diff(t, x)
    decreasing expr_size(t)
  do
    var p, q as Expr[K, x];
    match t do
      case p + q do
        :: D(p + q) = D(p) + D(q)
        return diff(p) + diff(q) by diff_add;
      end;
      case p * q do
        :: D(p * q) = D(p) * q + p * D(q)
        return diff(p) * q + p * diff(q) by diff_mul;
      end;
      case x do
        :: D(x) = 1
        return 1 by diff_var;
      end;
      otherwise
        :: t is a constant (no occurrence of x); D(c) = 0
        return 0 by diff_const;
      end;
    end;
  end;
end;

:: Spot-check on concrete expressions
theorem DiffSquare: diff(x * x) = x + x by computation;           :: D(x^2) = 2x
theorem DiffSquarePlusX: diff(x * x + x) = x + x + 1 by computation;
```


## 20.13 論理エンコーディング

このセクションでは、アルゴリズム構造が Mizar kernel内の論理式にどのようにマップされるかを指定します。これは、`terminating` アルゴリズム用に生成された形式公理と各ステートメント形式の検証条件 (VC) スキーマによって、§20.4 ～ §20.7 の動作記述を補完します。

### 20.13.1 契約公理

すべてのアルゴリズム呼び出しサイトは `requires` から証明義務を生成し、すべての `return` は `ensures` から証明義務を生成します。以下の表に FOL エンコーディングを示します。囲んでいる `definition` ブロックの型パラメーターは普遍的に定量化され、型ガード `is_A(x)` として表示されます。

|構築 | FOL エンコーディング |
|---|---|
| `requires P` |各コールサイトでの証明義務: `Γ ⊢ P(a₁, …, aₙ)` |
| `ensures Q` で `return e` |証明義務: `Γ ⊢ Q[result/e]` |
| `ensures Q` (呼び出し側、部分的なアルゴリズム) | 下記の評価公理。`Q` は、戻ることが分かっている呼び出しについてだけ成り立つ |
| `assert φ` |証明義務: そのプログラム時点での `Γ ⊢ φ`。 `φ` はその後 `Γ` に追加されます |
| 呼び出し `f(a₁, …, aₙ)`、`f` は昇格済み | (1) `Γ ⊢ requires_f(a₁, …, aₙ)`; (2) `ensures_f(a₁, …, aₙ, f(a₁, …, aₙ))` を `Γ` に追加 |
| アルゴリズム本体内の呼び出し `g(a₁, …, aₙ)`、`g` は部分的 | (1) `Γ ⊢ requires_g(a₁, …, aₙ)`; (2) 新しい `r` について `returns_g(a₁, …, aₙ, r)` と `ensures_g(a₁, …, aₙ, r)` を `Γ` に追加 |

複数の `requires` 句と `ensures` 句が結合されます。

**関数グラフと検証済み契約（E1–E5）。** 値を返す部分的algorithmにも
論理関数記号を与える。同じ完全入力x（構文、通常値、保持文脈、使用する
再構成C）について次を使う。

| 規則 | 論理式・採用条件 |
|---|---|
| E1 | returns_f(x,r) implies f(x)=r。導入前に結果の型、完全入力での実行単値性、未返却を含む **全** 型適合入力で断言する戻り型の値の存在を正当化する。Pの下だけで成立する依存型をPの外で断言しない。 |
| E2 | P(x) & returns_f(x,r) implies Q(x,r)。本体の部分正当性検証後に採用。構文では各環境のAdm_Γ(ρ) & InputOK(x,ρ) & P_ρ(x)を使う (§20.5.3 M8)。 |
| E3 | returns_f(x,r1) & returns_f(x,r2) implies r1=r2はE1と等式から導く。実行単値性はE1導入の前提でもあり、別公理で不一致を補わない。 |
| E4 | 検証済み正常返却保証P(x) implies ex r st returns_f(x,r)。構文ではM8の環境/InputOKガードを要する。E1/E2と合わせP(x) implies Q(x,f(x))を得て定義ラベルで引用する。明示・暗黙の失敗、子呼び出し、反復範囲も含む (§20.7.2)。 |
| E5 | 完全入力cでMVMが確認した有限な正常返却は、検証済み本体・入力・結果に対応した内部returns_f(c,v)を与える。失敗・資源切れは新返却証拠を与えず、正常返却の不存在も証明しない。 |

未返却入力のf(x)は未規定の値。f(x)=rは常に代入可能な通常の等式で、
returns_fやensuresを意味しない。voidはreturnsのrを省き値関数記号を持たない。
algorithm名の引用はなく、本体呼び出しの契約は既に後続文脈に入る。
昇格には宣言だけでなく検証済みE4を要する。複数結果を許すPick契約だけでは
関数記号を正当化できず、導入にはE1の実行単値性を要する。

呼び出しは、その引数についての `returns_f` の事実が得られるとき **戻ることが分かっている** といいます。そのような事実の出所は、次の 3 つに限られます。

1. 基底呼び出し `f(c₁, …, cₙ)` の MVM による評価が完了して `v` を返すと、その呼び出しについてだけ `returns_f(c₁, …, cₙ, v)` が得られます (§20.9.2)。失敗した評価からは何も得られません (§20.9.3)。
2. アルゴリズム本体の中では、`f` の呼び出しは、それに続く文の文脈で、新しい `r` について `returns_f(args, r)` を与えます。これは部分正当性です。後続の文は、呼び出しが戻った場合にだけ実行されます。再帰呼び出しにも適用されます (§20.13.4)。
3. その呼び出しの **正常返却の存在** を示す検証済み定理を引用するか文脈に持つ場合。単なる停止の証明では足りません。

`terminating` のアルゴリズムは、本体の中の部分的なアルゴリズムの各呼び出しが戻ることを、出所 1 または 3 によって示さなければなりません。出所 2 は戻ることを仮定しているため、この目的には使えません。

### 20.13.2 `terminating` のプロモーション公理

`terminating` が宣言され検証されると、アルゴリズムは `func` に昇格され、次の公理が Mizar kernelに出力されます。

|公理 | FOL スキーマ |
|---|---|
| **全体性** | `∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) → is_T(f(x₁,…,xₙ)))` |
| **契約** | `∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) → Q(x₁,…,xₙ, f(x₁,…,xₙ)))` |
| **定義式** | 定義的アルゴリズムのみ (§20.7.3)。`return` 文ごとに 1 つのガード付き等式 (§20.13.6) |

`requires` が存在しない場合、`P` はデフォルトで `⊤` になります。functorは宣言された型のすべての入力の合計です。複数の `ensures` 句が 1 つの `Q` に結合されます。

**例** — `factorial` (本体は §20.1.1 のとおり):

```
terminating algorithm FactorialDef: factorial(n) -> Nat
  ensures result >= 1
  decreasing n
```

生成された公理:

|公理 |式 |
|---|---|
|全体性 | `∀n. (is_Nat(n) → is_Nat(factorial(n)))` |
|契約 | `∀n. (is_Nat(n) → factorial(n) ≥ 1)` |
|定義式 | `∀n. (is_Nat(n) ∧ n = 0 → factorial(n) = 1)` |
|定義式 | `∀n. (is_Nat(n) ∧ ¬(n = 0) → factorial(n) = n * factorial(n - 1))` |

これらの公理は、`terminating` が検証されるとすぐに証明システムで使用できるようになります。本体が展開される形は定義式だけであり、定義式を受け取るのは定義的アルゴリズムだけです。それ以外の停止アルゴリズムでは、さらなる性質は契約から導かなければなりません。

### 20.13.3 検証条件スキーマ

検証器はアルゴリズム本体を走査し、標準的な Hoare 論理 スキーマによって VC を生成します。 `Γ` は、現在の論理コンテキスト (そのプログラム ポイントで蓄積されたファクト) を示します。

statement verification は `Normal`、`Return`、`Break(loop)`、`Continue(loop)`
の exit context を別々に返します。逐次合成は `Normal` からだけ継続します。
loop construct は自分に属する `Break` と `Continue` context を消費し、無関係な
exit はそのまま残します。loop の post-context は normal exit と break exit の
join です。`while C` の `¬C` のように通常終了だけで成り立つ fact は、break exit
には追加されません。

`assign(Γ, l, e)` は §20.1.4 の old-state assignment transformer を表します。
`e` を pre-state で評価し、`l` と alias し得る location を含む fact を forget
または rename し、alias しない fact を保存して、`l` の post-state equality を
追加します。`assign_field` は解決済み lvalue identity を通じた field update 用の
対応する transformer です。

loop head では cutpoint に同じ old-state discipline を適用します。`MayWrite(S)` は
loop body `S` が任意の path で代入し得る mutable location の集合で、解決済み
aliasing lvalue path について閉じています。`havoc(Γ, W)` は `W` 内の location と
alias し得る location を含む `Γ` の fact を forget または fresh 化し、alias しない
location や immutable な hidden value に関する fact を保存します。loop body `S`
について `Γ_loop = havoc(Γ, MayWrite(S))` と書きます。invariant と loop guard は
entry context `Γ` ではなく `Γ_loop` の上で仮定されます。そうしないと、`x` に代入する
任意回数の反復後にも `x = 0` のような entry fact が不健全に残ってしまいます。range
bound、range step、collection domain は `Γ_loop` を作る前に一度だけ評価され、下では
`a₀`、`b₀`、`s₀`、`S₀` のような hidden immutable value で表します。このような値を
導入する場合、`Γ_loop` はそれらの immutable binding を追加した `Γ` から計算します。

`V_after` は normal back edge または `continue` edge の post-state で評価された loop
measure、`V_before` は body 実行前の loop head で評価された同じ measure です。range
loop では `step` の default は `1` で、positive `Nat` でなければなりません。`next(i)`
は `to` loop では `i + s₀`、`downto` loop では `i - s₀` です。

| Statement | 生成される VC | 後続コンテキスト |
|---|---|---|

### 20.13.4 再帰的アルゴリズムのエンコーディング

再帰的 `terminating` アルゴリズムの終了は、**十分に根拠のある再帰引数**によって確立されます。基礎となる原則は次のとおりです。

> *`requires` を満たすすべての入力 `x` について、すべての再帰呼び出し `f(y)` が `measure(y) < measure(x)` (辞書編集的には `Nat`) を満たし、`measure` が `Nat` 値である場合、`f` は、`requires` を満たすすべての入力の合計になります。

これは、`Nat` (または `Nat × Nat × …`) の十分に根拠のある帰納スキーマに対応します。

```
∀x. (∀y. (measure(y) < measure(x) → P(y))) → P(x)
─────────────────────────────────────────────────────
∀x. P(x)
```

ここで、`P(x)` は、入力 `x` の全体性と契約性の積です。

**相互再帰**の場合、同じ原則が集合的に適用されます。検証器は、相互再帰グループを単一の帰納法として扱い、共有 `decreasing` 測定値がクロスアルゴリズム呼び出しごとに減少することを検証することによって、無限の呼び出しシーケンスが発生しないことを確認します。

すべての終了が確認されると、グループ内のアルゴリズムごとにプロモーション公理 (§20.13.2) が発行されます。

**アルゴリズム自身の検証における帰納法の仮定。** `terminating` アルゴリズムが見出しに `decreasing` 測度 `μ` を宣言している場合、その本体の初期文脈は、アルゴリズム自身と再帰グループの各メンバー `h` (型ガード `is_Bⱼ`、前提条件 `P_h`、事後条件 `Q_h`、測度 `μ_h`) について、次を含みます。

```
∀y₁,…,yₘ. (is_B₁(y₁) ∧ … ∧ P_h(y₁,…,yₘ) ∧ μ_h(y₁,…,yₘ) < μ(x₁,…,xₙ) → Q_h(y₁,…,yₘ, h(y₁,…,yₘ)))
```

ここで `<` は §20.5.2 の辞書式順序です。これは上記の整礎帰納法の仮定であり、アルゴリズム自身を適用する `ensures` 句 (§20.4.1) を正当化します。現在の引数 `x₁,…,xₙ` についての仮定はないため、現在の呼び出しの契約をそれ自身の証明に使うことはできません。同じ帰納法により、§20.13.2 の契約公理は許容されるすべての入力で成り立ちます。

測度が厳密に小さい引数への制限は不可欠です。他のすべての引数で仮定を許すと、`ensures result = f(n + 1) + 1` のような句から `f(n + 1) = f(n + 2) + 1 = f(n + 3) + 2 = …` という `Nat` 上の無限降下が得られ、検証器が矛盾を導いて、矛盾した契約を受理してしまいます。

**部分的なアルゴリズムの再帰。** 部分的なアルゴリズムは、`decreasing` の測度なしに、自分自身や同じ再帰グループの他のメンバーを呼び出せます。§20.13.1 の出所 2 は、これらの呼び出しにも他の呼び出しと同様に適用されます。再帰呼び出しが戻った後は、返された値についてその `ensures` が成り立ちます。これは部分正当性の再帰規則です。この規則は評価の長さについての帰納法により健全です。戻る評価は、その内側の呼び出しのより短い評価だけを含み、それぞれは戻って、帰納法の仮定により `ensures` を満たします。この規則は、どの評価も戻らない引数については何も与えないので、停止性を証明せず、上のような無限降下も生じません。

```mizar
definition
  let n be Nat;

  terminating algorithm collatz_step_algo(n) -> Nat
  do
    if n mod 2 = 0 do return n div 2; end;
    return 3 * n + 1;
  end;
end;

definition
  let n be Nat;

  :: Not terminating: termination for every n >= 1 is an open problem.
  algorithm collatz_steps_algo(n) -> Nat
    requires n >= 1
    ensures iterate[Nat, collatz_step_algo](result, n) = 1
  do
    if n = 1 do return 0; end;
    return collatz_steps_algo(collatz_step_algo(n)) + 1 by IterateShift;
  end;
end;

theorem Collatz27: collatz_steps_algo(27) = 111 by computation;
theorem Collatz27Reaches1: iterate[Nat, collatz_step_algo](111, 27) = 1
  by computation;
```

`collatz_step_algo` は定義的アルゴリズムなので、MVM で評価でき、functor の実引数としても使えます (§18.8.4)。`iterate` は §18.8.4 のテンプレートアルゴリズムで、ゼロ返却にはiterateの検証済みゼロ定義式を要し、`IterateShift` は補題 `iterate[T, F](k + 1, x) = iterate[T, F](k, F(x))` です。再帰的な `return` は、内側の呼び出しの `ensures` から検証されます (出所 2)。`Collatz27`は通常の値等式で、計算は内部で正常返却を確認する。`Collatz27Reaches1`も呼び出しを計算し検証済み契約を使う。等式だけでは返却証拠にならない。

### 20.13.5 ゴースト変数の消去

ゴースト変数は検証中に論理コンテキストに存在しますが、ランタイム プログラムからは消去されます。消去は次の意味で**健全**です。

> *ゴースト変数の存在下で検証された非ゴーストコントラクト (`requires`、`ensures`、`assert`) は、消去されたステートメントでゴースト変数について言及されていない限り、消去されたプログラムにも保持されます。

|プロパティ |声明 |
|---|---|
| **契約の保存** | `S'` を、`ghost var`、`ghost const`、および `ghost` の割り当てをすべて削除した `S` とします。 `S` が契約 `P`/`Q` を満たし、`P`、`Q` がゴースト変数について言及していない場合、`S'` は `P`/`Q` も満たします。 |
| **不変射影** |ゴースト変数 (`S_visited` など) に言及するループ不変式は、型チェック中にのみ検証されます。実行時の義務は発生しません。 |
| **ゴーストの隔離** |検証器は、ゴースト変数が非ゴースト代入の右側に表示されないこと、および非ゴースト アルゴリズム呼び出しに渡されないことを静的にチェックします (§20.1.3)。これは消去が健全であるための重要な条件です。 |

### 20.13.6 定義的アルゴリズムの定義式

パラメータ `x₁,…,xₙ`、パラメータの型ガード `is_A₁(x₁) ∧ …`、前提条件 `P` を持つ定義的アルゴリズム `f` (§20.7.3) について、`r₁,…,rₖ` をテキスト順に並べた `return` 文とし、それぞれが式 `e₁,…,eₖ` を返すものとします。

- `rᵢ` の**局所ガード** `gᵢ` は、`rᵢ` を囲む `if` の分岐の条件の連言です。`do` の分岐では `C`、`else` の分岐では `¬C` を使います。
- **経路条件**は `πᵢ = gᵢ ∧ ¬π₁ ∧ … ∧ ¬πᵢ₋₁` です。定義的断片にはループがないため、`rᵢ` より前に本体を抜ける方法はテキスト上で先にある `return` だけです。したがって `πᵢ` は、実行が `rᵢ` に到達するときに限り成り立ちます。
- `σ` は、`πᵢ` または `eᵢ` に現れる各 `const` を、`const` がなくなるまで繰り返しその定義項で置き換えます。論理式ではなく `boolean` 型の項 `t` である条件は、`t = true` として読みます。`f` が `boolean` を返し、`eᵢ` が論理式 `φ` である場合、下記の等式は `f(x₁,…,xₙ) = true ↔ φσ` の形になります。

昇格は、各 `i` について次を生成します。

```
∀x₁,…,xₙ. (is_A₁(x₁) ∧ … ∧ P(x₁,…,xₙ) ∧ πᵢσ → f(x₁,…,xₙ) = eᵢσ)
```

`ghost` 文、`assert`、スナップショット、claim ブロック、`return` の正当化は定義式に寄与しません。

**追加の義務はない。** 経路条件は構成上互いに素であり、すべての経路で戻るため (§20.2.6)、`P` の下で全体を覆います。重なりを持つ条件付き定義 (§10.12.2) と異なり、定義的アルゴリズムには整合性 (consistency) や網羅性の義務は不要です。

**健全性。** 停止性は §20.13.4 の測度の義務によって検証されます。再帰呼び出しを含まない本体は自明に停止します。定義的断片は本体の中の非決定性の源をすべて除外します。したがって、本体が呼び出す functor の解釈をどのように固定しても、測度に関する整礎再帰により、型ガードと `P` が許す入力の上で定義式を満たす関数はちょうど 1 つ存在します。昇格は保存的拡大です。定義式は来歴 (provenance) を持つ通常の公理であり、カーネルを変更しません。

相互再帰グループでは、すべてのメンバーが定義的である場合に限り定義式が生成され、グループ全体の停止性が検証された時点で全メンバーについて出力されます。テンプレートアルゴリズム (§20.1.1) は、スキーマパラメータを抽象のまま残した定義式を受け取ります。

**例** — `fibonacci` (§20.8.1):

| return | 生成される等式 |
|---|---|
| `return 0` | `∀n. (is_Nat(n) ∧ n = 0 → fibonacci(n) = 0)` |
| `return 1` | `∀n. (is_Nat(n) ∧ n = 1 ∧ ¬(n = 0) → fibonacci(n) = 1)` |
| `return fibonacci(n - 1) + fibonacci(n - 2)` | `∀n. (is_Nat(n) ∧ ¬(n = 0) ∧ ¬(n = 1 ∧ ¬(n = 0)) → fibonacci(n) = fibonacci(n - 1) + fibonacci(n - 2))` |

### 20.13.7 認定された計算事実の取り込み（T1–T8）

有限・有向・適用条件付きの手順であり、全数学式の完全変換器や任意順の
書き換え系ではない。完全入力、正常返却、Adm/InputOK、requiresを独立に
確認し、ensures **全体** を実例化する。同じ呼び出しの帰結で前提・返却を
循環的に正当化しない。内部returnsとAST引数の等式は公開事実から分け (T8)、
暗黙Cを落として別関数の等式を公開しない。通常値等式とensures実例全体を
候補とし、以下の手順を適用する。

変換前に有限な候補式、具体的非循環AST、局所ガード、元式との対応記録、
有限なKΓ条件記録を固定し、標準定義の解決済み対応と実例化証明を確認する
(§20.5.3)。分類・定義・証明不足時は拒否する。内部σは自由宣言UIDを出力先で
型付けした **終端的** 数学項へ対応付ける。同時に適用し、挿入項内部を再置換
せず、未知の宣言を同名変数・仮値で補わない。終端的とは、object拡大や
容器内部も含めAST内容・型・参照、内部UID/C、未変換の意味・構造操作がない
通常式をいう。通常関数の定義は展開しない。

| 規則 | 変換と固有の適用条件 |
|---|---|
| T1 | 解決済み通常funcは同じσで子の意味を型適合引数へ翻訳し同じ数学記号に渡す。pred/結合子はtrueの真理条件へ。暗黙値・署名・ガード・リテラル内容を含め、論理式を項位置へ入れず内部反射/評価記号を通常funcとして通さない。 |
| T2 | 有効な純R1対応はσ適用済み元項・論理式の真理条件を出力し、Var(κ)はσ(κ)へ。現在の木・UID・文脈と一致し、終端的出力が可能な記録を要する。混合R2構築を純R1とはしない。 |
| T3 | 不透明な葉は保存した項・論理式へ自由UIDを捕獲回避で代入 (§20.5.3 M6)。出力を再反射・束縛分解・定義展開しない。 |
| T4 | 外側σでA/Bを翻訳し、出力宣言・σ値・本体自由名を捕獲しない新束縛zを導入。σ[κ↦z]で本体を翻訳し元UID対応、全入力の型・適用・値域前提を保持。(z \|-> E) qua Function of A',B'を認定構成・一意性で関数化。空A'は空関数としκの現在値・本体環境を生成せず、未対応構文は拒否する。 |
| T5 | 更新値vを更新 **前** に終端的v'へ翻訳。xのUID対応だけを変えてtを翻訳。現在のAdm、変数/文脈対応、UIDに依存しない公開返値型、局所ガードでの更新適合証明を要する。依存する子は内部で合成し、未検査の子val_atを生成しない。 |
| T6 | T5と同様にvをσ更新前に翻訳してからvalid_atを更新後対応の有限な記録KΓへ一度展開し、現在のAdmと記録/Admの同値の証明を要する。元の型・属性・依存適用・view前提を保持。展開は条件記述であり証明ではない。制限量化・含意の帰結を変換する際もガードを保つ。 |
| T7 | 数学上の変数値がない開いたVarも含め、具体的構造/UIDのexpr_size、len expr_children、構造等式を正確に計算。FV={}は不要。近似サイズや意味等式で構造を比較しない。 |
| T8 | 内部証拠と、公開する通常等式・ensures実例全体を選別。ASTを含むensures部分式を消す規則にしない。 |

除去対象のboolean val/val_atを少なくとも一方に含む比較では、認定した
true≠falseと二値性により、B=true/B≠falseをTruth(B)、B=false/B≠trueを
not Truth(B)、B=CをTruth(B) iff Truth(C)、B≠Cをその否定へ変換する。
Truth(val p)はpの真理条件、val_atはT5を使う。終端boolean項bはb=trueで
終了し、この表を再適用しない。boolean引数やBinder返値には **項** の変換を
別途要し、比較規則だけで生成しない。未認定・未対応の形は拒否する。

処理順は(1)証拠/候補選別、(2)有限記録/認定、(3)束縛・ガードを保つ有限式走査
（T5/T6の更新値を先に処理しT6/T7は一度）、(4)終端対応が使えるT2/T3を優先し、
それ以外はT1/T4/UID対応でASTの意味を翻訳、(5)通常Binderの関数構成と
候補全体の残存検査とする。出力した数学式を反射・定義展開・同じ付値入口へ
戻さない。T1/T4は構造的な子への厳密な減少で再帰し、T2/T3は有限元式の
終端出力で終わる。T5は入力の真の部分式を先に処理してAST再帰へ進む。

自動決定可能性を説明しない。資源切れは実際の未完了操作を報告し公開しない。

最後に候補 **全体** の式、量化変数型、完全な引数/結果、注記、列・集合内部まで
検査する。AST値・型・構成子・参照、内部UID/C、未変換のval/val_at/valid_at/
expr操作が残れば候補全体を拒否し、ensuresの成功部分だけを黙って残さない。
綴りや宣言object型ではなく解決済み識別・値・型で検査する。候補種、残存項と
位置、最初に適用できなかった規則/不足条件/未完了段階を報告する。
後の取り込み失敗で確認済み内部正常返却を否定しない。正当化したASTのない
数・判定・通常boolean項は構文由来だけでは拒否しない。この境界検査だけで
内部公理・MVMの正しさを保証することはできない。
