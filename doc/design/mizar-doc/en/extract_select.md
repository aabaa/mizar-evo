# mizar-doc Extraction Selection — Definition Proposal
Canonical language: English; [Japanese companion](../ja/extract_select.md).
Status: non-normative proposal only. ES-Q1–ES-Q7 are unselected; no selection policy, API, diagnostic code or executable subset extension is adopted here.

## Authority And Fixed Boundaries
Doc16 refines architecture13 [verified subset](../../architecture/en/13.documentation_and_extraction.md#extraction-uses-verified-executable-subset) and [Step 1](../../architecture/en/13.documentation_and_extraction.md#step-1-select-extractable-items), under spec20 [code extraction](../../../spec/en/20.algorithm_and_verification.md#2010-code-extraction). Extraction consumes verified `terminating` algorithms; an exported signature or mathematical validity alone is insufficient. Target language, numeric representation and host-library bindings come from extractor configuration, not inline annotations. The first target remains Doc21's decision.
Phase16 consumes phase14 proof acceptance and phase15 artifact integrity. It does not rerun semantics, accept evidence, change proof validity or mutate published inputs. The [Doc2 reader](./artifact_reader.md#published-input-loading) establishes publication consistency, not current extraction-policy acceptance or executable readiness. Spec23 [exports](../../../spec/en/23.package_management_and_build_system.md#2351-mizirjson-artifact-format) contain signatures/contracts, not algorithm bodies; source parsing cannot fill that gap with newly inferred semantics.
Every selected item needs matching source/dependency artifacts, accepted required contract/termination obligations under the active extraction policy, erasable ghost/proof state, and target lowering for every runtime operation. External attestations must be absent or permitted by that policy; stored proof-status names or witness reachability alone are not acceptance. No policy default is inferred here.
The [internal05 reader](../../internal/en/05.documentation_extraction.md#artifact-documentation-reader) and [extraction pipeline](../../internal/en/05.documentation_extraction.md#extraction-pipeline) require verified executable projections and dependency summaries. Missing required source/maps block the affected items; source presence alone grants no readiness. Any implementation cache must satisfy architecture13's [consumer validation](../../architecture/en/13.documentation_and_extraction.md#phase-16-is-a-consumer-phase); unvalidated compiler IR is not an alternative authority. Doc2 does not yet supply these extraction-specific prerequisites.

## Selection And Classification
Inherited root origins are exported algorithms, explicit extraction configuration and CLI-selected items. They identify candidates, not extraction approval. Non-algorithms and non-terminating algorithms cannot become executable roots under spec20.10. Root-channel combination, private visibility and runtime dependency closure remain ES-Q1–ES-Q3; no implicit precedence or reachability algorithm is adopted.
The existing classifications retain their architecture13 meanings:

| Status | Existing meaning / refusal boundary |
|---|---|
| `Extractable` | All verification, computability and target constraints are satisfied; only this class may be emitted. |
| `SpecOnly` | Mathematically valid but not executable for the selected target; never emitted as a stub or guessed runtime value. |
| `BlockedByProof` | Required obligations are open or disallowed by policy; never recheck or reinterpret them in selection. |
| `BlockedByTarget` | Target lacks a lowering for a runtime construct; no partial code for that item. |
| `BlockedByDependency` | A dependency artifact or runtime mapping is missing; do not silently omit a runtime dependency. |

An unsupported runtime construct is explicitly rejected, including one reached through a required runtime call. An item with an unavailable required callee/mapping cannot satisfy all extraction constraints. Whether dependencies are added automatically or must be requested, and how reasons propagate, requires ES-Q3/ES-Q4. Proof-only dependencies do not thereby become runtime code.
The broad `SpecOnly` and target-blocked descriptions can overlap; neither row order nor the first observed failure defines precedence. Missing executable projection/source-map evidence is a refusal prerequisite, not permission to invent a sixth status, relabel a lower-reader error or treat absence as an empty body. ES-Q4/ES-Q5 must close representability and classification gaps before implementation.

## Executable Subset And Explicit Rejection
Spec20 [ghost isolation](../../../spec/en/20.algorithm_and_verification.md#2013-variable-declarations-var-const) forbids ghost-to-runtime flow. Ghost declarations/assignments, specification-only snapshots and proof-only structures may be erased only at their established boundary; runtime operations and required runtime checks cannot be erased to make a target appear supported. Ghost escape is an extraction error indicating an invalid projection or earlier checker bug, never repaired by inserting a value or reevaluating a proof.
Spec20 [Pick](../../../spec/en/20.algorithm_and_verification.md#203-non-determinism-pick) distinguishes non-ghost runtime sites, ghost-only sites and stable choices inside specification formulas. A non-ghost Pick requires executable support for the selected target or explicit rejection; no deterministic witness, finite enumeration or host choice routine is selected here. A ghost-only Pick is erased with ghost state but retains its required non-emptiness obligation before erasure. Specification-formula choices do not become runtime Pick sites. The existing partial/terminating verification rules are unchanged; this proposal does not admit partial algorithms for extraction.
Ordinary assignments, control flow, calls and numeric/data operations are eligible only when their verified executable data and target mappings exist. This is a constraint, not a claim that any current backend supports them. No new finite-type rule, numeric representation, dynamic-check policy or capability catalog is defined. RuntimeIr projection/erasure belongs to Doc18–20; backend support and runtime bindings belong to Doc21–22.
Unsupported items receive explicit refusal rather than degraded code, placeholders, skipped statements or a changed runtime meaning. Under internal05, unsupported constructs block affected items unless the selected profile requires all requested roots. This permits separate eligible items under an appropriate profile, never a partially generated refused item. Profile defaults, request failure and staged-output retention require ES-Q7 and the later publisher owner.

## Identity, Diagnostics And Adoption
Preserve artifact-bound module/FQN/item identity, source ranges when available and dependency provenance. For identical verified inputs, target, policy and configuration, selection and diagnostics must be deterministic; canonical module/FQN ordering follows architecture13. Root duplication/collision rules, reason multiplicity and absent-location representation need explicit definitions rather than arrival-order tie breaks. Target name mangling/reverse maps and output manifests remain later owners.
Integrity/staleness/schema errors remain lower-reader failures. Extraction refusals use the separate Extraction diagnostic family and existing ordering/profile boundaries from [internal05](../../internal/en/05.documentation_extraction.md#diagnostics); no code, severity table, descriptor or location is allocated here. Missing ranges must not be fabricated. Documentation warning promotion and approved comment Q1–Q8 option ① do not authorize extraction fallback or alter proof policy; Doc7 remains parked and Doc8 dependent.
Before Doc17 implementation, owner answers must be reflected in separately authorized owning definitions, with executable-projection producer/schema, current policy evidence, root/dependency identity, status/reason/location rules, target capabilities and extraction diagnostics specified. Later fixtures must cover eligible/refused roots, each unsupported runtime construct, dependency refusal, ghost/Pick separation and deterministic/profile behavior. Existing reader tests provide input validation evidence only; this proposal adds no executable coverage, allocation or audit credit.

## Owner Q-Decisions — All Unselected
Each alternative is a candidate tool definition constrained by the fixed boundaries above, not a new language rule or authorization. An owner may request another bounded definition. Adoption needs a separate authorized specification update; this proposal does not mark Doc16's normative definition or Doc17 readiness complete.

| Question / affected definition | Proposed ① | Proposed ② |
|---|---|---|
| ES-Q1 — root channels and duplicates | Union enabled export/config/CLI root sets, coalescing repeated full artifact-bound identities; conflicting bindings refuse selection. | Explicit config/CLI roots replace default exports when present; coalesce identical bound identities and refuse conflicting bindings. Define config/CLI combination in the adopting update. |
| ES-Q2 — private explicit roots | Permit explicitly selected private algorithms only when verified executable metadata and identity are available; export discovery remains public. | Limit all roots to exported algorithms; reject explicit private roots. Neither alternative changes language visibility or authorizes raw-source lookup. |
| ES-Q3 — runtime dependency closure | Add required executable callees transitively from validated dependency metadata; define cycles, policy propagation and refusal paths before adoption. | Require the request to enumerate runtime callees or configured external mappings; missing members block the caller. Define closure validation and cycles before adoption. Neither alternative erases required calls. |
| ES-Q4 — classification and reason reporting | Retain all applicable typed refusal reasons in deterministic order, deriving one of the five statuses from a separately approved precedence table. | Define mutually exclusive classification predicates and one primary reason, with deterministic related dependency reasons. Both require a construct catalog distinguishing SpecOnly/target refusal and mapping missing projection/maps without reclassifying lower errors. |
| ES-Q5 — executable and policy evidence | Define an artifact-bound per-item executable projection carrying references to lower-owned accepted-obligation/policy results and required source-map availability. | Define separate validated executable and policy views joined by full publication/item identity. Both require producer/schema/currentness contracts; neither invents proof acceptance, missing bodies or new public APIs here. |
| ES-Q6 — required source/map availability | Define required data per selected item and runtime operation, accepting source-less extraction only where all required projection/map data is present. | Require complete source/map coverage for each selected module in addition to executable projections. Both must state exact required data and refusal reasons; source availability never substitutes for verified executable data. |
| ES-Q7 — profile default and request outcome | Default to affected-item refusal with explicit failed-root results; a named strict profile requires all requested roots. | Default to all-requested-roots success; a named permissive profile permits independent eligible items with explicit refusals. Both preserve no code for refused items; request exit/output retention and publisher atomicity need subsequent definitions. |
