## Candidate Field Model
The following defines column ① of Q10–Q18 together, solely for owner review. `W` means ASCII space, tab, CR or LF; non-ASCII whitespace is not a field separator in this candidate. Strip only CommonMark container/paragraph indentation for recognition, retaining its map. A tag begins at a paragraph's first inline source position with literal `@` plus a maximal non-W token; only exact lowercase known names match. No escape/entity decoding or removal of inline markup may manufacture a tag name.
After the marker, skip W within that paragraph; for tags with a slot, consume the next maximal non-W source token as the name/ref/version, without decoding markup or imposing syntax. The body is the remaining source suffix after separator W, or everything after marker-separator W for slotless tags; its semantic boundaries exclude separator W, while the original full payload is retained. A missing slot stays missing, never borrowed from another paragraph. Soft/hard breaks continue fields/body within the paragraph; the next paragraph or block ends the tag.
Field extraction uses the logical paragraph stream without container prefixes, after display-block recognition and before inline-math recognition; required slots stay opaque to math. Map each derived segment through container removal, Q3 and the retained Artifact/loading maps to its real source; preserve segment provenance rather than inventing a contiguous range across removed text. For raw duplicate comparison, use the original Q3-extracted slice, including continuation-line container prefixes, ending before the final contributing line's terminator; internal line endings and trailing spaces/tabs remain significant.

| Known tag | Explicit slot | Body requirement already approved |
|---|---|---|
| `@param` | name | Optional explanation; one occurrence per same parameter name. |
| `@returns`, `@requires`, `@ensures` | none | Nonempty explanation required by Q8. |
| `@see` | ref | No explanatory-body requirement; unresolved ref passes to Doc9/10. |
| `@since` | version | No explanatory-body requirement or new version grammar. |
| `@deprecated` | version | Nonempty following message required by Q8. |

For candidate ①, nonempty means at least one non-W source character in the body; markup-only text counts, and no renderer is consulted. A slot such as backtick-delimited `x` remains its entire raw token, not an inferred parameter name. Slot absence, approved duplicates and established metadata mismatches retain all text and warn; complete/partial/unavailable parameter and return metadata retain the comments owner's limits. No warning is added merely for unknown tags, undocumented parameters, unresolved refs or absent metadata.
Candidate ① duplicate checks span all separate blocks attached to the same full-provenance module/item target in source order. `@param` compares exact raw name tokens; singleton tags compare the tag name regardless of payload. For repeatable Q7 tags compare the exact tag name plus the entire post-marker payload up to the paragraph end, including separator/trailing W and line breaks, after Q3 extraction only. No Unicode, whitespace, entity, markup or reference normalization; warn on each later matching occurrence and retain every occurrence, without replacement or merging blocks.

## Candidate Extension Interactions
Under Q17①, identify CommonMark fenced/indented code, HTML blocks and reference definitions first, then display math; none contains structured tags. Derive fields on the remaining paragraphs; identify code spans, inline HTML and link/image/autolink structure before inline math, protecting their non-label contents. Standard link structure outside display math is preserved. Backtick contents pass intact to later Mizar highlighting and exact label/FQN checking; never resolve expressions as labels. Doc9/10 receives link destinations and `@see` slot text with raw spelling/ranges; no reference resolution occurs here.
For remaining paragraph text, an unescaped single `$` pairs with the next unescaped single `$` in the same paragraph, with nonempty interior and no adjacent `$`; no currency heuristic is implied. Backslash parity determines escaping. Math takes precedence over emphasis, but cannot cross code/HTML or whole link/image/autolink boundaries; within a link label it can pair only within that label. Thus `$[text](ref)$` retains the CommonMark link and literal unmatched dollars (Q18① warns), whereas `[$x$](ref)` retains the link with math in its label. Accepted math content is opaque and passes with raw text/ranges to Doc11/12; this link-first choice is unselected Q17①, not an adopted restriction on spec24.3.
For display math, a logical line after container markers and up to three indentation spaces must contain only optional surrounding spaces/tabs and either `$$nonempty content$$` or `$$`. The latter searches for a subsequent `$$`-only logical line in the identical container stack/list item, stopping before any protected code/HTML/reference-definition block or container end. Both delimiter lines must themselves be outside protected blocks. If interrupted, the opener is unmatched and no display block consumes the intervening text; preserve its CommonMark parse. Thus `$$` / fenced code / `$$` never spans or consumes the code, and `$$` inside code cannot close math. Recognize accepted display blocks before paragraph/inline processing; their interiors must contain a non-W character and are opaque, retaining content/newlines/maps for Doc11/12. Other dollar runs are literal; unmatched eligible openers warn under Q18①.

Paired display delimiters with a W-only interior produce no math node: retain the entire spelling as literal text and warn under Q18①. A single-line `$$…$$` candidate uses the outermost pair only, with no internal unescaped `$$`; otherwise keep the line literal. These failure rules, like the delimiter grammar itself, remain unselected.

## Degradation And Adoption Boundary
CommonMark accepts every input string: unmatched emphasis/backticks and unclosed fences already have defined parses, so “malformed Markdown” cannot justify replacing CommonMark with a reduced validator. Under Q18① warn only for the proposed extension failures or an actual inability to derive/map a view; preserve the raw affected block as fallback without aborting the default documentation build. Lower-reader integrity refusals never become presentation success. Missing source maps never acquire fabricated ranges; use existing provenance location rules when applicable.
Before adoption, the Documentation diagnostic owner must define/adopt Markdown/tag warning meanings, descriptors and location/order/profile behavior; existing W0400–W0404 are attachment warnings, not codes to repurpose. This proposal allocates no codes and does not settle new diagnostic policy. Presentation warnings may fail documentation under the existing promotion profile, never proof validity or extraction acceptance.
Owner review witnesses include blank-separated and consecutive `@param` lines; `> @returns text` and tight-list `- @requires text`; escaped/entity/code/wrapped `@param`; slots containing backticks, links, NBSP or a line break; empty, markup-only and multiline bodies; identical versus whitespace-different repeatable tags in one/two blocks; `$x$`, `$$x$$`, multiline `$$`, code/HTML/link dollars and unmatched delimiters. Expected outcomes follow the selected column only after approval; these are proposal cases, not new executable fixtures or spec tests.
Doc8 parsing stays open until Q9–Q18 are answered, definitions are coherently adopted and diagnostic prerequisites are satisfied. Links/UsedBy, math/HTML rendering, extraction/publication and broader crate completion remain with their later owners; no coverage or trace credit changes here.
