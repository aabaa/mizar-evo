## Authority And Responsibility
Spec [2.9/2.10](../../../spec/en/02.lexical_structure.md#29-comments-and-annotations) and [24.1](../../../spec/en/24.documentation_generation.md#241-documentation-comments-syntax) own comment syntax, association, CommonMark and tags. Architecture [02](../../architecture/en/02.source_and_frontend.md#comments-and-doc-comments-are-source-metadata) preserves syntactic candidates; architecture [13](../../architecture/en/13.documentation_and_extraction.md#step-2-attach-doc-comments) and internal [05](../../internal/en/05.documentation_extraction.md#documentation-inputs) require verified identity plus source adjacency. These definitions refine that consumer boundary, not language semantics.
The comments module owns grouping, attachment candidates, Markdown/tag interpretation and their presentation diagnostics. Doc7 implements attachment only after approval and completed input definitions; Doc8 implements parsing after Doc7. Link/UsedBy resolution, math rendering, HTML/search output, extraction and publication retain their later owners.

## Inputs And Provenance
Consume the validated [Doc5 plan](./doc_build.md#full-build-and-index-inputs) without changing its publication, full ModuleSummaryIdentity, complete exports or optional summaries. Identify an item by its owning publication/module and original verified export identity (origin/FQN); label queries supply candidates, never a unique association by themselves. No FQN splitting, signature parsing, nearest-name match or semantic reanalysis may invent identity or labels.
The [optional native lexical reader](./artifact_reader.md#optional-native-lexical-source) returns normalized source text, Disk loading maps and complete identity-free Lexer preprocessing, including raw comment kinds/lexemes/spans and diagnostics. It supplies no grouped blocks, Markdown, tags, verified attachment or frontend dependency. The approved Q1 route is the [Artifact projection](../../mizar-artifact/en/comment_projection.md); this optional reader is not its comment fallback.
Use Artifact’s [availability/identity](../../mizar-artifact/en/comment_projection.md#availability-and-identity), [coordinate/maps](../../mizar-artifact/en/comment_projection.md#text-coordinates-and-adjacency) and [integrity rules](../../mizar-artifact/en/comment_projection.md#compatibility-hashes-and-refusals). Missing or incompatible mappings cannot establish Doc attachment; valid semantic metadata remains usable without optional source.

## Blocks And Attachment Targets
Spec24.1 defines a block as contiguous `:::` lines immediately preceding a named definition, theorem, registration or algorithm; a physical blank line ends item association. A blank `:::` line stays inside the block as a Markdown paragraph separator. Ordinary `::` and `::=…=::` comments are not documentation text. Do not concatenate separate blocks across intervening source content.
A top-of-file doc comment before any import or definition documents the module. Preserve spec2.9.2’s doc block → item-attached `@proof_hint` → theorem example; an attached annotation cannot sever that association. Approved Q2 makes a file-leading block module-only and ordinary trivia/standalone annotations stop item adjacency. Approved Q5/Q6 preserve module-prefix eligibility across whitespace, blank lines and ordinary comments; every eligible block remains separate, source ordered and module-only. Module association uses the verified module identity; item association requires the source-adjacent candidate and verifier-provided item identity/range to designate the same item. A range match alone is insufficient.
Definitions/theorems/registrations use stored exported label metadata; algorithms use their identifier per [24.2](../../../spec/en/24.documentation_generation.md#242-cross-referencing-and-hyperlinks). Missing labels, multiple candidates, conflicting ranges or unsupported target information remain unresolved and diagnosed, never resolved by enumeration order. Repeated names across packages/modules/versions retain their full provenance.
Public documentation uses verified exported targets. Non-exported comments may be omitted unless private-doc output is requested; that request grants no new verifier metadata or verified status. Comments on invalid/unverified items cannot appear as verified API documentation. Nested or other unnamed/unsupported targets gain no new documentability from proximity; their extension needs owner definitions. Unattached blocks remain diagnosable, not silently dropped.

### Residual Association Definitions
A block is a maximal run of consecutive documentation-comment lines; blank physical lines and ordinary line/block comments separate blocks. Keep each block's raw text, maps and source order separately. Horizontal indentation and the ordinary line break between consecutive lines are not intervening comments or blank lines. Do not attach one block to both module and item.
Module-leading eligibility is evaluated only in the file prefix before imports or any source item, including a standalone diagnostic annotation. An item-attached annotation belongs to its following item's boundary, not ordinary trivia; it preserves adjacency only for that same verified item, with no intervening blank line/comment/standalone annotation. No scan may skip an import, unrelated item or interruption to find a later target. Approved Q5/Q6 preserve that prefix across ordinary trivia and retain all its separate blocks; ordinary comment text is excluded.
Attachment outcomes use the shared [spec22 descriptors](../../../spec/en/22.error_handling_and_diagnostics.md#2268-documentation-attachment-warnings), without changing reader failures:

| Condition after valid input loading | Presentation outcome |
|---|---|
| No eligible module or adjacent named-item candidate, including trailing/interrupted blocks | Orphan warning; keep block text/range available without attaching to another target. |
| Adjacent syntax exists but verified identity/label/target boundary is missing or unsupported | Unresolved-target warning; no identity inferred from text, range or nearest name. |
| Multiple identities or contradictory candidate/range associations survive | Ambiguous-attachment warning; retain candidate provenance, choose none. |
| Target is invalid/unverified | Unverified-target warning; never present the block as verified API documentation. |
| Required association coordinates are absent or cannot be related to the verified target | Unresolved-attachment warning; never invent a map. A lower-reader integrity refusal remains an error, not this warning. |

Use the affected block's preserved source range; candidate locations may supply related ranges only when available. Non-exported verified targets retain the existing private-doc selection rule; deliberate public-output omission alone is not an orphan or missing-comment warning. These are diagnostic conditions, not a new code registry or a warning deduplication policy.

## Markdown And Structured Tags
Preserve the raw block and per-line mapping while deriving its Markdown body; approved Q3 removes `:::` and at most one following ASCII space per line, preserving the rest and its reverse map. Do not globally trim/deindent text or normalize Unicode, tabs or line endings a second time: such changes can alter CommonMark indentation, code and diagnostic positions.
The required surface is CommonMark, not an invented reduced language: paragraphs, headings, emphasis, lists, fenced/indented code, block quotes and standard links remain available. Paragraphs may be separated by blank `:::` lines. Doc8 must pin its parser/version and define extension interactions without silently reducing spec24.1; any observable ambiguity returns for owner clarification.
The [Doc8 CommonMark/tag-field proposal](./commonmark.md) records candidate definitions and unselected Q9–Q18; it adopts no new semantics and does not open the implementation gate.
Preserve Mizar inline-code contents and code-block text for later highlighting. Exact label/FQN code references, explicit `[text](ref)` and `@see` targets pass to Doc9/10; expressions stay code. Inline `$…$` and display `$$…$$` math on its own line pass with source ranges to Doc11/12 under [24.3](../../../spec/en/24.documentation_generation.md#243-mathematical-formula-rendering). Comments neither resolve links/anchors/UsedBy nor render/evaluate math, code examples or verifier annotations. HTML output policy belongs to Doc13–15.
Recognize tags only at the first token of a Markdown paragraph, retaining name, raw arguments/body and ranges. Spec24.1 supplies seven tags: `@param name` (one per parameter), `@returns` (return value, `result`), `@requires`/`@ensures` (prose supplement), `@see ref`, `@since version`, `@deprecated version` (following deprecation message). Preserve all seven meanings; no tag adds a formal contract, changes verification, evaluates code or imposes a new version grammar.
Unknown tags pass through verbatim under spec2.9.2, without becoming unknown statement annotations. Approved Q4 gives malformed/duplicate/available-metadata-mismatched known tags default presentation warnings retaining text; the residual rules below and approved Q7/Q8 apply; do not silently discard text, overwrite a tag or infer unavailable parameter metadata. Markdown parse products are derived views, not a new serialized schema or replacement semantic AST.

### Residual Tag Validation
Required explicit slots follow spec24.1: `@param` needs `name`, `@see` needs `ref`, and `@since`/`@deprecated` need `version`. An absent slot is malformed and warns with the entire original tag retained. No version syntax, reference resolution or parameter type grammar is introduced. Exact Markdown-to-tag field recognition remains part of Doc8's CommonMark definition; text in code examples is not validated as executable annotations.
Two `@param` occurrences naming the same parameter violate “one tag per parameter”; warn on the repeated occurrence and retain both in source order, without first/last-wins replacement. Approved Q7/Q8 below define other tag multiplicity and explanatory-body requirements; Doc8 owns their parsing. Unknown tags remain verbatim and acquire none of these known-tag warnings merely for being unknown.
Compare a parameter name only with available authoritative parameter metadata for the same verified target. A complete parameter list can establish an unknown name; a partial list cannot establish absence. Unavailable lists disable membership checks, not required-slot/duplicate checks; never parse signatures or infer a parameter list from tag text. Likewise warn about `@returns` only if available authoritative metadata explicitly establishes no return value; absent metadata is not a mismatch. No coverage warning is implied for undocumented parameters. Prose `@requires`/`@ensures` is not compared with formal formulas, and `@see` resolution remains Doc9/10 work.
Malformed, duplicate and established metadata-mismatch conditions produce default presentation warnings at the offending tag's preserved range, retaining all raw arguments/body and mapped ranges.

## Diagnostics And Determinism
Use the Documentation diagnostic family and existing ordering/profile rules from [internal05](../../internal/en/05.documentation_extraction.md#diagnostics). Preserve source ranges when available; never fabricate a range for unavailable source. Missing source is a warning by default; missing comments are an optional lint. Malformed Markdown warns and degrades rendering rather than aborting the default documentation build. Approved Q4 gives unattached/ambiguous blocks and malformed tags default presentation warnings retaining text; the definitions above and approved Q5–Q8 govern these cases.
Integrity/staleness/schema errors remain lower-reader errors, distinct from presentation warnings. A profile may promote documentation warnings to errors for that documentation build; proof validity, published verification inputs and extraction policy do not change. Preprocessing diagnostics retain their original meaning/ranges; Doc diagnostic adoption cannot reinterpret a failed read as successful input.
For identical validated publications, bound comment inputs and options, preserve source block/line/tag order and semantic import order. Use complete publication/module/item identities and mapped source positions for deterministic association and diagnostics, independent of worker/input enumeration; never use storage order as reference precedence. Degraded output retains the offending text/ranges, and regenerating documentation never mutates source or artifacts.

## Attachment Consumer
[`comments::attach_comments`](../../../../crates/mizar-doc/src/comments.rs) consumes one full-identity module of a validated DocBuildPlan. Its borrowed result retains original projection/maps, separate raw line rows, loaded block ranges and original landmark candidates; target identity refers to the original module or export. Unavailable and available-empty projection states remain distinct. No Markdown body or tags are parsed here.
An optional genuinely bound LoadedSource supplies real primary spans after identity/path/hash/text checks; otherwise warnings use the shared Documentation provenance location. The caller retains source/snapshot binding responsibility; attachment grants no new currentness. The result's documentation-failure query applies the retained warning-promotion profile without changing proof metadata. Unsupported or missing association information remains diagnosed and unbound.
