# mizar-doc Comment Definitions
Canonical language: English; [Japanese companion](../ja/comments.md).
Status: owner approved Q1–Q4 option ①; projection and remaining consumer definitions gate implementation.

## Authority And Responsibility
Spec [2.9/2.10](../../../spec/en/02.lexical_structure.md#29-comments-and-annotations) and [24.1](../../../spec/en/24.documentation_generation.md#241-documentation-comments-syntax) own comment syntax, association, CommonMark and tags. Architecture [02](../../architecture/en/02.source_and_frontend.md#comments-and-doc-comments-are-source-metadata) preserves syntactic candidates; architecture [13](../../architecture/en/13.documentation_and_extraction.md#step-2-attach-doc-comments) and internal [05](../../internal/en/05.documentation_extraction.md#documentation-inputs) require verified identity plus source adjacency. These definitions refine that consumer boundary, not language semantics.
The comments module owns grouping, attachment candidates, Markdown/tag interpretation and their presentation diagnostics. Doc7 implements attachment only after approval and completed input definitions; Doc8 implements parsing after Doc7. Link/UsedBy resolution, math rendering, HTML/search output, extraction and publication retain their later owners.

## Inputs And Provenance
Consume the validated [Doc5 plan](./doc_build.md#full-build-and-index-inputs) without changing its publication, full ModuleSummaryIdentity, complete exports or optional summaries. Identify an item by its owning publication/module and original verified export identity (origin/FQN); label queries supply candidates, never a unique association by themselves. No FQN splitting, signature parsing, nearest-name match or semantic reanalysis may invent identity or labels.
The [optional native lexical reader](./artifact_reader.md#optional-native-lexical-source) returns normalized source text, Disk loading maps and complete identity-free Lexer preprocessing, including raw comment kinds/lexemes/spans and diagnostics. It supplies no grouped blocks, Markdown, tags, verified attachment or frontend dependency. The approved Q1 route is the [Artifact projection](../../mizar-artifact/en/comment_projection.md); this optional reader is not its comment fallback.
Use Artifact’s [availability/identity](../../mizar-artifact/en/comment_projection.md#availability-and-identity), [coordinate/maps](../../mizar-artifact/en/comment_projection.md#text-coordinates-and-adjacency) and [integrity rules](../../mizar-artifact/en/comment_projection.md#compatibility-hashes-and-refusals). Missing or incompatible mappings cannot establish Doc attachment; valid semantic metadata remains usable without optional source.

## Blocks And Attachment Targets
Spec24.1 defines a block as contiguous `:::` lines immediately preceding a named definition, theorem, registration or algorithm; a physical blank line ends item association. A blank `:::` line stays inside the block as a Markdown paragraph separator. Ordinary `::` and `::=…=::` comments are not documentation text. Do not concatenate separate blocks across intervening source content.
A top-of-file doc comment before any import or definition documents the module. Preserve spec2.9.2’s doc block → item-attached `@proof_hint` → theorem example; an attached annotation cannot sever that association. Approved Q2 makes a file-leading block module-only and ordinary trivia/standalone annotations stop item adjacency. Module-leading trivia/multiple-block definitions remain open. Module association uses the verified module identity; item association requires the source-adjacent candidate and verifier-provided item identity/range to designate the same item. A range match alone is insufficient.
Definitions/theorems/registrations use stored exported label metadata; algorithms use their identifier per [24.2](../../../spec/en/24.documentation_generation.md#242-cross-referencing-and-hyperlinks). Missing labels, multiple candidates, conflicting ranges or unsupported target information remain unresolved and diagnosed, never resolved by enumeration order. Repeated names across packages/modules/versions retain their full provenance.
Public documentation uses verified exported targets. Non-exported comments may be omitted unless private-doc output is requested; that request grants no new verifier metadata or verified status. Comments on invalid/unverified items cannot appear as verified API documentation. Nested or other unnamed/unsupported targets gain no new documentability from proximity; their extension needs owner definitions. Unattached blocks remain diagnosable, not silently dropped.

## Markdown And Structured Tags
Preserve the raw block and per-line mapping while deriving its Markdown body; approved Q3 removes `:::` and at most one following ASCII space per line, preserving the rest and its reverse map. Do not globally trim/deindent text or normalize Unicode, tabs or line endings a second time: such changes can alter CommonMark indentation, code and diagnostic positions.
The required surface is CommonMark, not an invented reduced language: paragraphs, headings, emphasis, lists, fenced/indented code, block quotes and standard links remain available. Paragraphs may be separated by blank `:::` lines. Doc8 must pin its parser/version and define extension interactions without silently reducing spec24.1; any observable ambiguity returns for owner clarification.
Preserve Mizar inline-code contents and code-block text for later highlighting. Exact label/FQN code references, explicit `[text](ref)` and `@see` targets pass to Doc9/10; expressions stay code. Inline `$…$` and display `$$…$$` math on its own line pass with source ranges to Doc11/12 under [24.3](../../../spec/en/24.documentation_generation.md#243-mathematical-formula-rendering). Comments neither resolve links/anchors/UsedBy nor render/evaluate math, code examples or verifier annotations. HTML output policy belongs to Doc13–15.
Recognize tags only at the first token of a Markdown paragraph, retaining name, raw arguments/body and ranges. Spec24.1 supplies seven tags: `@param name` (one per parameter), `@returns` (return value, `result`), `@requires`/`@ensures` (prose supplement), `@see ref`, `@since version`, `@deprecated version` (following deprecation message). Preserve all seven meanings; no tag adds a formal contract, changes verification, evaluates code or imposes a new version grammar.
Unknown tags pass through verbatim under spec2.9.2, without becoming unknown statement annotations. Approved Q4 gives malformed/duplicate/available-metadata-mismatched known tags default presentation warnings retaining text; exact validation rules remain open; do not silently discard text, overwrite a tag or infer unavailable parameter metadata. Markdown parse products are derived views, not a new serialized schema or replacement semantic AST.

## Diagnostics And Determinism
Use the Documentation diagnostic family and existing ordering/profile rules from [internal05](../../internal/en/05.documentation_extraction.md#diagnostics). Preserve source ranges when available; never fabricate a range for unavailable source. Missing source is a warning by default; missing comments are an optional lint. Malformed Markdown warns and degrades rendering rather than aborting the default documentation build. Approved Q4 gives unattached/ambiguous blocks and malformed tags default presentation warnings retaining text; attachment-diagnostic and tag-validation definitions still gate implementation.
Integrity/staleness/schema errors remain lower-reader errors, distinct from presentation warnings. A profile may promote documentation warnings to errors for that documentation build; proof validity, published verification inputs and extraction policy do not change. Preprocessing diagnostics retain their original meaning/ranges; Doc diagnostic adoption cannot reinterpret a failed read as successful input.
For identical validated publications, bound comment inputs and options, preserve source block/line/tag order and semantic import order. Use complete publication/module/item identities and mapped source positions for deterministic association and diagnostics, independent of worker/input enumeration; never use storage order as reference precedence. Degraded output retains the offending text/ranges, and regenerating documentation never mutates source or artifacts.
