## Hash domains and inputs

A generic `Hash` value does not identify its domain. The validator needs the producing owner, domain/version and exact input association; matching digest bytes alone never suffice. Unknown domains, missing comparable inputs or incompatible versions keep the affected fix unavailable. Existing [fix fields](../../mizar-diagnostics/en/fix.md#data-model) are preserved; no new payload field or production API is introduced by this proposal.

| Input | Existing authority or proposed validation contract |
|---|---|
| Build source hash | Reuse Session's `hash_text` on the original **loaded** source text: [disk/open-buffer text is BOM/CRLF-normalized; generated text is preserved byte-for-byte](../../mizar-session/en/source.md#loaded-source). Use BLAKE3 over `b"mizar-session/source-text/v1" || u64_le(UTF8_length) || UTF8_bytes`; its manifest spelling is `mizar-session/hash-text/v1:<digest>`. Match the exact source entry and module's manifest source hash. Never substitute Driver's source-input fingerprint, build ID or raw editor bytes. |
| Artifact hash | Use the manifest/store owner's [hash domains](../../mizar-artifact/en/manifest.md#hash-string-domains) and [reader validation](../../mizar-artifact/en/manifest.md#reader-requirements): canonical JSON, schema-declared exclusions and artifact framing/class/family/version. Validate manifest reachability and the referenced module/content; no raw-file checksum or interface-hash substitution. |
| `required_text_hash` | **Q1:** proposed A reuses Session `hash_text` over the complete original loaded text of the sole edited source. It excludes ranges, replacement text, URI, version and publication identity; those are validated separately. Hashed multi-source fixes remain unavailable under A. No existing opaque value is reinterpreted without the producer's domain/input declaration. |
| Explanation hashes | `required_artifact_hash` binds the owning artifact; `Artifact.content_hash` binds backing content; `summary_hash` binds a canonical bounded summary/descriptor, never localized preview. **Q2** must specify the backing content/summary domains and comparable inputs; generic hash equality and a successful preview/store lookup alone cannot authorize an edit. |
| Missing facts | Require an authenticated enclosing artifact or a manifest-reachable development artifact, its owner-defined content hash/schema and the exact obligation/fact entry used by this fix. **Q2** must define that selector and source/VC association; filename `missing_facts.json`, path, title or candidate text alone proves nothing. |

Raw editor URI/version/incarnation, retained original text/maps, current publication and each expected-text/range check remain mandatory under [snapshot association](snapshot.md#source-association). Equal normalized source hashes or build IDs never restore a stale action. Every edited source needs its own original/current association and the applicable artifact provenance; one primary-source hash cannot validate other files.
**Q1 — text-hash scope:** recommend A above for a bounded first consumer using an existing domain. Alternative B defines a versioned aggregate edit-source digest, including deterministic ordering, source association, per-source bytes and framing, for multi-source hashed fixes; its exact encoding needs a separate approved owner definition before use. A retains more filtering; B needs a new producer/validator contract and must not settle parked SourceId serialization. Owner approval selects the meaning and the producer migration/registration boundary.
**Q2 — backing domains/selectors:** recommend A: artifact-backed `content_hash` reuses the exact existing store-framed artifact hash; for non-artifact bounded content/summary propose BLAKE3 over `b"mizar-lsp/action-backing/v1" || frame(role) || frame(encoding) || frame(bytes)`, where `frame(x) = u64_le(byte_length(x)) || x`, role is UTF-8 `content` or `summary`, encoding is the producer-owned versioned encoding key and bytes are its exact original bounded payload or canonical structured summary/descriptor (no localized preview). The producer supplies those bytes and encoding; unknown encodings stay unavailable. A missing-facts selector is the producer-authenticated obligation key and exact entry selector within the authenticated backing artifact; the producer validates source/VC correspondence, rather than LSP guessing a schema. Alternative B requires all backing and summaries to be published as existing schema-validated artifacts and uses their store hashes, retaining filtering when unavailable. A supports retained query data but needs new producer/validator registrations; B is narrower and may need upstream publication work. Approve the domain/roles, supported owner encodings and missing-facts selector semantics, or explicitly keep the affected consumer filtered. No missing-facts schema or parked producer decision is defined here; backend candidates stay distinct from kernel-verified `used_axioms`.

## Fix and handle provenance

**Proposed acceptance chain:** select one immutable current publication by its non-reused process-local identity; resolve its diagnostic handle in that exact build index; resolve the fix id within that record and compare the canonical [fix payload](../../mizar-diagnostics/en/fix.md#attachment-to-records); obtain owner-authenticated backing associated with that precise fix; validate every target source, manifest/module/artifact and relevant handle against it. IDs, matching subject strings or co-occurrence on a record do not establish the fix-to-handle relation.
**Q3 — binding carrier:** recommend A, a host-owned immutable association registered from the genuine producer alongside the selected publication, keyed by publication/diagnostic/canonical fix and exact existing explanation handle or missing-facts selector. Alternative B extends producer payloads with explicit typed references in a separately approved schema change. A needs no `FixSuggestion` field; B is durable but expands upstream scope. Neither can be populated by guessing from diagnostic titles, paths, array positions, a unique attached handle or client data. No producer binding means refusal, even with a single candidate.
The association must cover every backing dependency actually used by the fix, including cross-module inputs; validate all, not the first available match. Explanation resolution checks the original handle's kind/subject/source, snapshot and artifact/content/summary preconditions through its owning store/validator. An unrelated registered payload or a cache hit grants no authority; missing/ambiguous/unsupported/mismatched backing keeps the fix unavailable. Retained stale explanations remain readable under [explanation rules](explain.md#freshness-and-stale-handles), without edit authority.
This is an in-memory ownership proposal only: it does not settle OpenBuffer artifact provenance/storage, Session SourceId encoding or native producer completeness. If those owners cannot supply the required authenticated association, keep the affected actions filtered.

## Command resolution and execution

`FixCommandRef` stays an opaque producer reference under the [fix owner](../../mizar-diagnostics/en/fix.md#data-model). LSP must not treat it as a shell command, CLI string, URI, arbitrary method name or trusted client argument. Proposed resolution uses an explicit host allowlist mapping each exact producer reference and canonical fix binding to one supported operation and its retained owner inputs; unknown refs remain unavailable.
**Q4 — route and wire contract:** recommend A, one server command named `mizar.executeDiagnosticCommand`, advertised only with the execution host. Initial code actions remain title/kind/data locators; command-capable clients must support resolving `command`. Resolve reconstructs a command with that fixed name and a single opaque locator argument bound to publication/diagnostic/fix/original document association; no client-supplied operation, file path or command arguments are authority. Alternative B uses a dedicated custom request returning the existing bounded query/scheduling outcome, with separately negotiated capability and request schema; it needs client integration. Approve the route, name/argument shape and capability/error contract before either is exposed; retain existing edit-only client behavior.
Proposed operation ownership: explain delegates to the bounded [explanation host](explain.md#implementation-boundary); show-VC reads validated retained obligation data and returns display data to the client; reverify submits only through the existing Driver/build host after its currentness/admission checks. A missing operation owner means no offer or execution. This proposal adds no query semantics, VC schema, scheduler policy, proof acceptance, shell spawning or direct workspace mutation.
Proposed lifecycle: offer validates support and provenance; resolve reselects the current publication and reconstructs from server authority; execution ignores client edits/command contents, re-resolves the locator and revalidates canonical fix, snapshot/diagnostic/handle, backing hashes and all live source associations immediately before handing off. The owner must atomically guard effect admission against replacement/edit/close/reopen; an async read retains its original inputs and rechecks currentness before returning a current result. Cancellation before admission prevents work; cancellation after admission follows the existing operation owner's contract and promises no rollback. A scheduling operation validates admission, not continued equality after its own build replaces the snapshot. A later source edit requires separate explicit editor application and full edit validation.
**Q5 — outcomes and admission:** recommend A, malformed request/argument shape → InvalidParams; unsupported route → MethodNotFound; well-shaped unknown/stale/unbound locator, changed canonical fix or failed validation at resolve/execute → ContentModified with no effect; cancelled before admission → RequestCancelled; genuine host failure → InternalError; success → bounded operation-owned data or scheduling acknowledgement, never an implicit edit. Offer filters unavailable suggestions. Alternative B returns structured unavailable/stale outcomes like explanation queries for validated command failures. Owner must approve result shapes and confirm an atomic admission seam (or leave effectful commands filtered); no new error codes, budget or rollback policy are selected here.

## Conditional validation matrix

These are review obligations for the approved design and future implementation, not new executable tests or current positive-path claims; existing filtering/refusal tests remain unchanged.

| Case | Input shape and required outcome |
|---|---|
| 1 | BOM/CRLF/Unicode or version-only edit with equal build ID: loaded-source hash may match; raw/currentness/range checks still reject stale edits and retain original coordinates. |
| 2 | Several sources/edits, missing expected text or hash scope: validate every source and explicit text precondition; Q1-A refuses hashed multi-source fixes, while existing unhashed multi-source behavior stays intact. |
| 3 | Matching manifest/module/artifact versus wrong source/hash/class/schema or unreachable member: only the exact owner-validated chain can authorize an action; every mismatch refuses. |
| 4 | Two fixes/diagnostics sharing handles, absent/ambiguous binding, wrong summary/content/VC/fact selector: require the exact authenticated fix relation and all backing dependencies; no guessed association. |
| 5 | Known/unknown ref, missing host/capability, forged locator or supplied command contents: allow only the approved registered route/operation and server-reconstructed inputs; otherwise filter/refuse. |
| 6 | Edit/reopen/equal-id or cross-Server replacement/cancellation between offer/resolve/execute: old locators never revive; no stale effect admission; retained reads preserve original sources and cancellation uses the owner boundary. |

Owner approval must record Q1–Q5 selections and any deliberately still-filtered consumer. Task38 then needs a fresh implementation dispatch and owner-backed validation/admission seams; this proposal alone supplies neither.
