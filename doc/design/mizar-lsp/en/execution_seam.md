Current `CompilerDriver::submit_captured` enters synchronous `submit_inner`; scheduled dispatch completes, `session.finish(outcome)` executes, then `store_session` makes the record visible. `cancel` can reach only stored records and immediately terminalizes active ones. The bridge cannot process replacement/Shutdown while that exclusive mutable borrow is active. A background thread alone, a forged Running record, or cancellation after terminal return cannot establish the missing live execution/control boundary.

## Required observable boundary

For a supported genuine captured build with outstanding real scheduled work, acceptance must expose allocator-issued session/request ids together with the existing lane, generation and content-derived snapshot identity and authoritative nonterminal state before completion, retaining its original native capture and leases. Early capture/planning/dispatch failures may remain terminal structured failures; do not manufacture a live build for them. An owned execution record must exist before work can become externally cancellable. `Running` requires real scheduler-owned work that may still produce events, not a caller-set flag.
Expose a control path usable while execution is outstanding, plus a way to drive/await progress and retrieve authoritative state, existing ordered events and eventual terminal submission/results. Control cannot require reacquiring a Driver borrow held until completion. Rust API names and types follow the implementation contract; no new event/payload or diagnostic kind is required by this definition.
The seam must admit a replacement and expose its actual lane-current acceptance without waiting for the old execution to finish. Only then does the bridge request Superseded once for the old nonterminal session. Preserve monotonic generations, accepted-failure handling and equal-snapshot replacement; failed capture and rejected acceptance never masquerade as replacement. Mere edits/admission do not cancel. Quiet/cap timing, coalescing and capture-at-flush remain bridge-owned.
Shutdown/exit must leave control and cleanup usable after admission stops: discard the slot, request Shutdown once for a nonterminal owned session, never capture/submit afterward. Cancellation request, owner checkpoint observation, terminal outcome and execution drainage must be distinguishable evidence; a returned request acknowledgment alone proves no stopped work. Unknown/already-terminal cancellation remains idempotent and never revives work.

## Ownership and invariants

Driver owns in-flight records, lane-current transitions, event assembly and publication guards; Build owns graph readiness, resource admission and cancellation policy; phase services own real execution/checkpoints; Session/IR/Artifact retain capture, output and transaction authority. LSP only submits/controls its lane and retains original capture associations; it must not implement an alternate scheduler or compiler.
One authoritative record per execution must prevent completion/cancel races from overwriting a winning terminal result, duplicating SessionFinished or reactivating obsolete work. Define each control/acceptance transition's ordering point. A completion that wins before cancellation keeps its real terminal result; an accepted cancellation follows Q2/Q3. Existing canonical task/service order, structured errors and replay identity survive independent execution timing; event retrieval does not grant current publication rights.
Recheck existing lane/session plus snapshot/publisher guards at delayed result, diagnostic, coherent snapshot and artifact handoffs. Old work never becomes current because its snapshot id equals the replacement's. No partial accepted artifact or synthetic phase output is allowed. Cancellation does not roll back an already-started atomic artifact transaction; its owner boundary remains authoritative, and obsolete completion grants no current LSP publication.
Session-scoped controls must not cancel replacement or other-lane work sharing a snapshot id. Retain each execution's original capture, source maps, cancellation state, cached-output ownership and required leases until its real work can no longer access them, independently of lane selection or logical terminal status. Outstanding readers keep existing retained resources. Cleanup releases only that execution's ownership, once; no new global eviction/storage/SourceId policy is proposed.

## Approved owner decisions (original alternatives)

**Q1 — who advances execution and makes control usable?** A: split captured acceptance/start from host-driven progress/finish, storing resumable owner execution and returning control before completion. Preserve existing synchronous submit as a run-to-terminal adapter over the same core. B: Driver-owned worker execution with independently accessible session control and completion retrieval; synchronous callers wait on that same execution. Recommend A for explicit ordering/lifetime and deterministic host control; B offers progress during long owner calls but needs worker ownership, synchronization, shutdown/join and thread-safety contracts. A requires a real scheduler continuation/dispatch boundary: repeatedly rerunning completed work or polling an otherwise blocking whole submission is insufficient. Neither choice changes readiness/resource policy or permits LSP to recreate scheduler queues. A's host integration must continue serving protocol traffic and cancellation between progress calls; unsupported long non-cooperative calls gain no latency guarantee.
**Q2 — how does Shutdown reach actual work?** A: add an owner-supported per-execution cancellation signal composed with existing Build cancellation policy and passed to real phase checkpoints; Superseded/Shutdown retain their Driver reasons. B: extend Build's owner cancellation API with explicit/shutdown requests bound to the intended execution, then have Driver use it. Recommend A for a bounded control seam; B centralizes policy but needs a separate Build API definition. The existing documented snapshot-wide explicit/Shutdown propagation gap must be closed whichever route is approved: never encode Shutdown as false supersession, or merely set a terminal flag. For either option, specify checkpoint delivery to running work and prevention of further eligible dispatch, session isolation for equal snapshot ids, and compatibility with existing snapshot supersession. Any new scheduler policy/observable outcome beyond existing cancellation requires owner definition before implementation.
**Q3 — when is a cancelled session terminal?** A: accept cancellation into Cancelling, publish Cancelled/Superseded and one terminal event only when owner work has drained. B: preserve current immediate logical terminal outcome, but retain a separately observable execution-drain state/control lifetime and suppress every later current handoff. Recommend A for direct correspondence between terminal evidence and stopped work. A changes existing immediate terminal timing; B adds a second lifecycle and requires explicit rules for the bridge's nonterminal predicate versus work still draining. Both need approved adaptation of Driver's cancellation owner document, race/idempotence rules and resource retention; neither immediate terminality nor a delayed event is silently selected here. No forced termination or checkpoint/cleanup latency is promised.
**Q4 — how is the bridge connected?** A: add an explicit nonterminal captured-submission route for configured compiler hosts, preserving synchronous public callers via Q1's common execution core; adapt bridge control/progress and replay to it. B: make nonterminal acceptance the standard internal submission contract and migrate internal integrations, retaining synchronous compatibility wrappers for existing callers. Recommend A to bound caller migration and preserve batch/watch behavior. B unifies internal submission around nonterminal execution but broadens integration and owner review. Both require genuine native import-discovery/diagnostic-index behavior, original capture handoff and acceptance identity; a test-only Driver, artificial stored session or separate fake bridge backend is insufficient. No executable host installation, Watch integration or Task41 presentation choice is inferred; those remain separately dispatched boundaries.
**Q5 — how is live cancellation made deterministic in tests?** A: synchronize at an owner-supported dispatch/checkpoint boundary around a genuine native SourceFrontend invocation and its actual scheduler task; retain real outputs/status, allow cancel before its next checkpoint, then release/advance and observe drainage. B: use a real registered phase service with a controlled cooperative wait that delegates to the genuine producer, plus a native end-to-end control proving the same seam carries actual captured work. Recommend A for least auxiliary service surface; B can expose an in-call checkpoint under Q1-B but requires a carefully bounded test adapter. Neither may fabricate a positive PhaseResult, terminal outcome, currentness or events; timeout/sleep-based races, injected cancellation before submission and private state mutation cannot count as Task40 evidence. The chosen synchronization must prove outstanding owner work and cancellation observation, and include an uncancelled run with unchanged canonical results.
