## Required evidence boundary

An observation must originate in the genuine registered native Frontend invocation, binding its actual checkpoint receipt/result to the scheduler-selected task and owning Driver session. Neither a cancellation request/acknowledgment, a delivered token alone, scheduler cancellation, terminal outcome nor absence of published output is a receipt witness. Existing `pending_task` identifies admitted work before invocation; it does not prove the invocation subsequently happened.
Capture evidence after the native checkpoint is reached and before any Driver result normalization, stale-result clearing or current handoff can erase its provenance. Under a return-witness design, capture the unmodified return facts and expose positive receipt only after existing result validation succeeds, still before suppression. Later read-only retrieval of that already-captured evidence is sufficient; no callback during an exclusive Driver borrow is required. Suppression must not erase the observation or turn it into a current output. Record ordering follows actual dispatch/return, not a timestamp inference.
Required facts are authoritative session identity, actual graph TaskId and Frontend/service provenance, checkpoint kind, input snapshot, exact cancellation token delivered to that invocation (including its Build cancellation generation and reason), and the genuine result/receipt facts supporting the claim. Resolve request id, lane and request generation through the original session; do not confuse request generation with cancellation generation. Snapshot or TaskId alone is insufficient across equal-snapshot executions. Store a minimal immutable summary, never cloned phase payloads, diagnostics, outputs, captures or publication tokens.
For the present service-entry checkpoint, a return witness must establish native TypeId, matching input/token snapshot, genuine Cancelled return and the original empty-output/no-artifact result shape, with existing validation intact. Current native code returns Cancelled only from this matching-token branch; a future additional Cancelled return path must preserve an unambiguous checkpoint attribution or strengthen the witness. A non-native service claiming the same descriptor/status cannot supply native evidence. Unsupported paths and absent records mean no evidence, never inferred receipt.

## Ownership and invariants

Driver owns capture, association and retrieval. Build continues to own admission/checkpoint policy; the native service continues to own execution and receipt. Preserve the same native concrete TypeId, registry service, dispatch resources and execution route; no service wrapper, replacement producer, alternate scheduler, fabricated result or re-execution for observation. Observation must not affect scheduling, cancellation reasons, validation, canonical results/events, publication or acceptance. Exact API names/types belong to the approved implementation contract.
The approved first-reason, Cancelling-until-drained and terminal replay rules remain authoritative. Distinguish receipt from drainage and from one SessionFinished; observation grants no capture lease, artifact access, editor publication or currentness. Equal-snapshot replacements and Watch/LSP sessions retain separate evidence, controls and publishers. Completion that wins before cancellation remains completion, with no retrospectively invented receipt. No checkpoint, progress or cleanup latency guarantee is added.
Read access must work for obsolete sessions and after Shutdown/exit cleanup progress, including when terminal results are suppressed. Repeated reads/replay must not create observations, advance execution, consume cancellation or duplicate terminal events. Retention must be explicit, limited to actual observed invocations per retained execution, and released with its owner under Q4; no global log, independent capture retention or new session-eviction policy is implied.

## Approved owner decisions (all A; proposal alternatives retained)

**Q1 — how is evidence exposed?** A: a dedicated read-only Driver query keyed by session, with an explicit distinction between unknown session, known session with no observation, and recorded observations; retain the normal submission/event APIs. B: add a typed Driver observation event to existing replay, with the same distinctions and pre-suppression capture guarantee. **Recommend A**: it avoids changing canonical event schemas/order or downstream subscribers. B reuses replay but requires event-owner, compatibility and stale-publication classification changes; an observation event could never count as output/publication.
**Q2 — what proves native receipt?** A: capture a native-dispatch return witness at the existing registry boundary, using the facts above and the native matching-token Cancelled branch as its provenance invariant. B: add a Driver-owned receipt sink to execution resources and notify it directly inside the existing native checkpoint, retaining the native service TypeId and route; distinguish receipt from subsequent result validation/drainage. **Recommend A** for the current checkpoint: no new service/context callback is needed. B gives explicit checkpoint attribution if Cancelled gains other origins, but broadens context/lifetime ownership and needs a separately frozen notification contract. Neither option may infer receipt solely from a token or scheduler decision; B must not redirect or condition execution on observer behavior.
**Q3 — how broad is the identity/API surface?** A: cover the genuine native Frontend service-entry checkpoint only, pairing owning session with actual TaskId and native checkpoint discriminator; reuse existing session identity/token types. B: define a general per-service-span checkpoint observation API for all phases, retaining session/task plus phase/service/checkpoint discrimination. **Recommend A** for Task40's missing prerequisite. B permits other producers later but requires owner-defined provenance for each and a larger validation matrix; it does not grant cancellation evidence to uninstrumented services. Neither may collapse distinct sessions sharing snapshot/task identities or accept caller-authored receipt records.
**Q4 — when is evidence retained and released?** A: opt in when starting a captured execution, retain immutable summaries with that session's existing execution/replay record through drainage and stale replay, and release with that record. Reads are non-consuming; disabled observation is explicitly distinguishable from enabled with no receipt. B: opt in at start and offer an explicit consuming drain/acknowledgment after retrieval, with a documented consumed state and retention until acknowledgment or session-record release. **Recommend A**: no second cleanup protocol, and per-session storage is bounded by actual native invocations; this is not a new global capacity guarantee. B can release evidence earlier but needs lost-reader/repeat-read semantics. Neither silently drops evidence before its promised access window, retains compiler resources separately, or enables observation retroactively after the checkpoint.
**Q5 — what prerequisite validation is enough?** A: use existing admitted-task progress boundaries with genuine captured OpenBuffer native work: enable observation before start, confirm the real pending Frontend, request cancellation while Running, progress through its actual invocation, then inspect the retained witness after suppression/drainage. Add the six controls below and unchanged synchronous/native regression checks. B: validate a broader same-seam matrix across Disk/OpenBuffer and synchronous/nonterminal native routes, including additional native checkpoint kinds only after their owner contracts exist. **Recommend A** to bound this prerequisite; B offers broader reuse evidence but must not invent interior checkpoints or imply cancellation access during a blocking call. Both prohibit sleep/timeout races as positive evidence, pre-submission cancellation as the live-work proof, synthetic acceptance, private state mutation and native wrappers.
