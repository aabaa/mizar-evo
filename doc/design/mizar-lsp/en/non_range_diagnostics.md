## Required identity and ownership boundary

A source-load record identifies the requested package and normalized package-relative path even without SourceId, readable text or an editor document. Preserve that non-range variant, existing code/severity/message and canonical snapshot-scoped handle. Equal paths in different packages remain distinct; neither message text nor a filesystem-local absolute path determines identity. No EOF, insertion point, source span, line/column, underline, excerpt or invented document version may stand in for the failed request.
Never feed the non-range primary through a span-only converter. Real secondary anchors still require exact original-source validation and preserve order/multiplicity, shape, provenance and generated reasons through the retained record. Unknown variants, stale records or unrepresentable retained anchors fail explicitly; there is no dropping, renormalization, new deduplication or guessed provenance.
All presentation variants refer to one authentic immutable diagnostic selection and original association; a handle or wire token grants no currentness, edit, proof, artifact or acceptance authority. Retained reads must never remap old locations into live text. Existing CLI/artifact projection, overlay isolation, ranged delivery and other units' open questions remain outside this definition.

## Open owner decisions

The questions below are resolved as A throughout; references to proposed fields and recommendations describe the original proposal, now approved unchanged.

**Q1 — which wire carrier?** A: a dedicated server-to-client JSON-RPC notification, provisionally `mizar/publishNonRangeDiagnostics`, carrying a structured non-range replacement set alongside unchanged standard ranged notifications. B: a dedicated client pull request returning the same structured set, with an explicit unavailable/stale result and client polling/refresh lifecycle to be defined before implementation. **Recommend A**: it fits existing push delivery and permits active clearing. B avoids unsolicited payloads but needs an additional refresh/availability contract; Q4/Q5 below describe A, so choosing B requires owner approval of their adapted pull lifecycle before coding. Standard push/pull Diagnostic arrays, a fake URI with a zero range, and an information popup cannot provide this structured non-range carrier.

**Q2 — how is support negotiated?** A: opt in per initialized connection with `capabilities.experimental.mizarNonRangeDiagnostics: {version: 1}`; the server advertises the same supported version under `capabilities.experimental`. Missing, malformed or unsupported versions leave the extension disabled: a batch containing non-range records fails explicitly before any frame, while ranged-only behavior remains unchanged. No silent omission, popup fallback or claim of non-range delivery. B: require the extension at initialization and explicitly reject incompatible clients; this also prevents their ordinary ranged-only sessions. **Recommend A** for compatibility. Merely receiving an unknown custom notification is not acknowledgment or support. The named fields/version are proposed, not a change to current initialization.

**Q3 — how much structured payload?** A: the compact v1 envelope below, with exact package/path and primary-kind fields, existing display fields and handle, real secondary locations, and original record retention for all richer payload. B: a lossless full wire projection of every diagnostic field/anchor/note/detail/fix/explanation, with explicit codecs and unsupported-value rules frozen separately before implementation. **Recommend A**: it follows the current ranged handle model without inventing public record codecs. The handle retains semantic name, stable detail key/reason, notes (including absent versus empty), intent, anchor shape/provenance and attachments; it does not promise a new query or action route. B increases schema and compatibility obligations.

Conditional Q1-A/Q3-A envelope (field names and values are proposals):
```text
params = {version: 1, selection: <opaque connection-local publication token> | null,
          records: [<record>, ...]}
record = {location: {kind: "sourceLoad", package: <PackageId string>,
                    path: <NormalizedPath string>}, code: <existing public code>,
          severity: <existing LSP severity mapping>, message: <exact message>,
          data: {snapshot: <existing published BuildSnapshotId string>, id: <existing ordinal>},
          relatedInformation: [<validated real secondary locations/messages>, ...]}
```
The ordered array is the non-range subsequence of `BuildDiagnosticIndex::records`; it is not grouped by inferred URI or sorted by text. Strings use JSON escaping and the owners' underlying package/path values, not debug formatting, filesystem resolution or path concatenation. `data` uses the current ranged diagnostic encoding. Secondary conversion and note-span validation reuse the existing original-map rules; an empty secondary array needs no text for the primary. The token distinguishes equal-snapshot publications and is scoped to the live connection, not a persistent identity or handle substitute. Null selection is reserved for clearing with an empty array under Q4-A; records require a non-null selection and matching handle snapshots.

**Q4 — what is replaced and when cleared?** A: each extension notification replaces the entire non-range set for the selected diagnostic publication on that connection, including all represented packages. Emit an empty set for a genuine clean replacement; accepted invalidation/loss of selection emits `{selection: null, records: []}` while the connection can deliver. Keep original selection identity/currentness checks; identical snapshot ids do not revive old records. Shutdown/exit discard local selection/delivery state, with no promise of writes after terminal closure; clients discard connection-owned display on termination. B: package-scoped replacement sets and explicit per-package tombstones, retaining other packages independently. **Recommend A**: no additional cross-publication merge state. B requires owner-defined package removal, overlapping-publication and tombstone rules first. Neither may treat old retained records as current or alter snapshot admission; clearing conveys removal, not a new current diagnostic.

**Q5 — mixed batches and failure guarantees?** A: preflight capability, selection, every ranged/non-range record, anchor and JSON frame before any write; any unsupported/invalid record rejects the entire batch. For a valid supported selection, write unchanged ranged notifications in existing URI order, then one extension replacement frame (including empty), retaining canonical order within each carrier. Validate the same selected publication and currentness before each nonempty/current frame; a clearing frame instead validates that no replacement selection has superseded its removal. Propagate conversion/I/O errors; currentness loss stops further writes. Already written frames cannot be rolled back and no retry/acknowledgment or atomic client display is promised. B: one negotiated combined extension frame for both ranged and non-range records, requiring a new ranged carrier and client adoption; stream I/O can still fail partway through that frame. **Recommend A** to retain current ranged interoperability and whole-batch conversion failure. B reduces multi-frame display skew but expands the wire surface; its schema requires separate approval. No option promises atomic external writes.

## Conditional validation and implementation handoff

After owner decisions, freeze the chosen carrier/schema/capability/lifecycle in the presentation implementation contract(s); do not infer approval from the recommendations. A non-A choice with missing dependent rules returns to the owner before implementation. The original [ranged host admission](ranged_diagnostic_host.md#admission-and-ownership) excludes SourceLoad and the current converter requires captured native sources: approving a wire shape alone does not relax either gate. The separate [source-load prerequisite](../../mizar-driver/en/request.md#native-source-capture) defines genuine capture/retention/host admission, retaining package/path and the original native currentness guard without requiring a failed source's text or synthesizing a coherent full snapshot. Presentation work and then Task41 follow those prerequisites; arbitrary caller-built indexes are not positive host-delivery evidence.
The document-review cases below become executable obligations only after the corresponding owner approval. Cap six; extra cases need an authority clause or .miz test.
