Existing [metadata reads](metadata.md#published-inputs) consume published facts only. ## Products and ownership

Two products are needed: an outgoing dependency-facing [ModuleSummary](../../mizar-artifact/en/module_summary.md#scope), and an importer-local published view of the resolved visible surface. The former exports public declarations, lexical effects and reexports; it cannot stand for local private declarations, activation intervals or namespace alias bindings. The latter must bind those facts to the selected source and dependency inputs; Q3 chooses its carrier. These are logical requirements, not new Rust types or serialized fields.
Lexer owns exact written spelling pieces, syntactic arity, default/explicit operator metadata and activation events. Resolver owns correspondence to declarations, semantic relation targets, visibility, import/alias/conflict resolution and reexports. Artifact owns codecs, validating readers, canonical ordering and interface hashes. Existing Driver/build owners acquire and associate genuine phase outputs and publish through their established artifact/manifest boundary; LSP reads the result. No LSP AST/IR traversal, compiler replay, target guessing or invented producer registration may fill a gap.
Every supported fact needs the producer's canonical module/origin, written or qualified access spelling, role/kind, source provenance and visibility; local facts also need their owner-defined scope and activation boundary in the retained original source. Notation needs exact pieces/arity and available fixity/associativity/precedence; aliases need their own declaration provenance and exact target/relation; namespace bindings need local spelling and canonical target. Preserve published symbol/label signatures and statuses as supplied, without promoting a lexical candidate to a resolved symbol, alias equivalence or accepted theorem. Unsupported facts remain unavailable; keywords and completion ranking stay Task25 concerns.

## Notation publication proposal

Conditional on Q1/Q2 approval, extend the genuine same-frontend correspondence rather than merely deleting the rejection guards. Map declaration and operator/alias events through the existing source map; bind them to unique unrecovered owner declarations and complete source inventory. Preserve exact lexer spelling pieces and arity, not reconstructed resolver display strings. Multiple pieces may share an origin; never deduplicate by origin key alone. A standalone operator declaration adds no symbol or spelling.
The local view retains source-position events: imported metadata seeds the module body; local spelling and operator changes become active only at their completed declaration boundaries. Default metadata yields to the latest active explicit spelling-level event; later same-spelling overloads remain separate candidates, never an inferred winner. Private declarations remain locally visible according to resolver scope but cannot leak through exported rows. An outgoing summary is a dependency interface, not the history used to answer earlier local positions.
**Q1 — exported operator effects:** proposed A publishes the final publicly eligible spelling-level metadata on existing exported shapes; imported operator inputs and earlier local events remain in the local view. Require a matching exported functor/arity and owner-authenticated operator event. If private effects determine the final metadata, or a local event changes only an imported spelling without a local exported owner, withhold the outgoing lexical product until an export policy is approved. Alternative B defines a versioned exported operator-event projection, including effects on forwarded spellings, instead of flattening into shapes. Recommend A for existing-codec compatibility and a bounded first producer; B supports more cases but needs explicit scope/visibility/conflict semantics and schema work. Neither option changes the language activation or overload rules.
**Q2 — alias identity and admission:** proposed A gives each resolved public synonym/antonym its resolver-owned declaration origin and retains the original target module/origin plus relation kind separately; lexical shapes key to that alias's own exported row. Several spellings of that declaration share its origin. The producer must authenticate kind, ordered loci/arity correspondence and target under existing semantics, including imported originals; shallow lexical fallback is insufficient. Alternative B exports aliases as extra spellings of the original origin, with a separately specified relation/provenance carrier. Recommend A to preserve alias visibility, declaration ranges and antonym inversion independently; B avoids alias rows but cannot use current envelope binding unchanged for foreign targets. Existing supported relation profiles are not widened by this proposal: unsupported predicate/functor/mode/attribute/algorithm targets or chains need their owning resolver/checker work before publication. Neither choice equates an antonym with its target or decides overload applicability.

## Import and alias publication proposal

The producer consumes the complete source import/export inventory and semantically validated resolver outputs, not import-pre-scan success alone. Retain [alias binding](../../mizar-resolve/en/imports.md#alias-binding): `as` changes local namespace spelling, never canonical module/artifact identity; unaliased imports use the existing namespace rule. Preserve duplicate source declarations/provenance while canonical closure deduplicates graph edges. Unresolved, recovered or conflicting aliases stay explicit; import order never resolves a collision. Only public dependency surfaces are accessible. Local shadowing/ambiguity is supplied by resolver outcomes, not chosen by completion.
For each imported or forwarded fact, retain the canonical target module/origin and owner-resolved access path, the importing source binding, import/export provenance, and every consumed dependency summary's module/interface reference. A namespace alias is not an exported declaration merely because it appears in the import prelude. Ordinary imports do not automatically reexport their contents. Module paths and label access must come from the corresponding resolver facts; rendered text, filename and a lexical symbol id cannot manufacture them.
**Q3 — consumable carrier:** proposed A publishes an immutable owner-produced view alongside the selected publication, retaining the logical facts above, local scopes/events and dependency references under the existing snapshot association. It distinguishes available complete-empty scopes from unavailable/unsupported ones and carries resolved/ambiguous/unresolved outcomes without LSP resolution. No process-local identifier is serialized here. Alternative B adds a separately versioned artifact projection for this view. Recommend A to avoid pretending that ModuleSummary contains local scope/alias data; it requires a genuine producer handoff and lifecycle validation. B enables durable replay but needs an approved schema/encoding and storage owner. Until one carrier is implemented and bound, Task25 cannot assume these facts are available; this choice does not settle parked OpenBuffer provenance/storage or Session SourceId encoding.
**Q4 — reexport composition:** proposed A preserves canonical target summaries and explicit forwarding edges; resolver builds the visible view by validating the acyclic public forwarding closure and records all summary interfaces actually consumed. A facade's `reexports` records the forwarding relationship; it does not copy a foreign lexical shape under the facade's identity. Alternative B materializes forwarded rows in each facade, with an approved stable forwarding-origin mapping and matching payload codec. Recommend A to retain provenance without changing current envelope checks; B simplifies reads but needs new identity/hash rules. Missing targets, private forwarding, unsupported item-level forwarding or unresolved cycles cannot become a successful empty closure. Local `as` aliases never rename canonical reexport targets.

## Validation and publication boundary

Proposed acceptance chain: retain genuine frontend/source and resolver results from one coherent run; validate the complete covered declaration/import/export inventory and exact correspondence; read each dependency via its owner reader against the requested module/index/manifest binding; compose only authenticated facts; validate/canonicalize the summary and selected Q3 view; then expose their matching references through the existing publication owner. A caller-supplied identity or codec round trip alone proves no source/build authenticity. A source candidate, provider success or uncommitted summary is not a publication.
Reuse the [typed lexical envelope](../../mizar-resolve/en/module_summary_reuse.md#typed-lexical-payload-binding): kind/schema/key must select exactly one public exported row, with matching canonical module/origin payload identities. Current readers reject FQN-key substitution and mismatched envelopes, including foreign payload identities copied into a facade envelope; Q2/Q4 must supply representable rows or remain unavailable. Use existing shape validation and lexer canonical summary construction; preserve legal duplicate shapes. Artifact contribution order and lexer order/fingerprint are distinct owner contracts, never interchangeable hashes.
Canonical artifact writing and [interface hashing](../../mizar-artifact/en/module_summary.md#interface-hash) include exported notation/parse effects and affected dependency interfaces. Body/comment/range-only changes retain existing exclusions; a semantic exported spelling/operator/reexport change must affect the appropriate interface input. Reuse existing source, lexical and artifact hash domains without substituting one for another. The local view binds exact source/publication/dependency references; no new hash encoding is defined here.
**Q5 — incomplete/recovered input:** proposed A withholds each whole covered product when its required inventory, mapping, semantic relation, dependency or compatible encoding is missing/ambiguous/unsupported; never return a partial vector as complete. A genuinely complete empty product is valid. Alternative B publishes per-family/per-scope completeness with an approved unavailable marker, retaining valid families from recovered buffers. Recommend A for minimal failure handling; B improves IDE availability but needs exact partition/marker and cross-family dependency rules. This governs the new products only, not existing diagnostics or independent metadata readers; no new public diagnostic codes are selected. Completeness is for the declared product scope, not proof/native payload or whole-module acceptance credit.
Reads reuse [snapshot association](snapshot.md#source-association) through the metadata reader's [freshness rules](metadata.md#snapshot-association-and-freshness); the snapshot owner remains authoritative. Retain one original source/dependency set per read; never mix new local aliases with old summaries. Stale published facts remain explicitly stale and retain original coordinates; missing facts are unavailable, not an empty successful surface. Syntax recovery or an equal build id cannot create current semantic metadata. This proposal adds no SourceId/provenance encoding, source-loading or scheduling policy.

## Conditional validation and handoff

| Case | Input and required outcome after approval and implementation |
|---|---|
| 1 | Multi-piece notation, default then explicit operator, later overload: preserve pieces/arity and declaration-boundary events; no new symbol or overload winner; export follows Q1. |
| 2 | Synonym/antonym with local/imported original, several spellings and ambiguous target: exact alias/target relation under Q2 or unavailable, never shallow-fallback semantic authority. |
| 3 | Private, recovered or unsupported owner/event: preserve local visibility only where authenticated; no exported leakage or incomplete product called complete; Q5 governs refusal. |
| 4 | Ordinary/aliased/duplicate/conflicting imports and facade reexports: stable canonical target, correct access spelling/provenance, public closure only; Q3/Q4 govern delivery/composition. |
| 5 | Missing/wrong dependency module/hash/schema, unpaired lexical key or unsupported codec: existing reader rejection or unavailable publication; never fabricated empty dependency data. |
| 6 | Permuted input/repeated builds and edit/reopen/stale replacement: owner-canonical bytes and interface invalidation, one retained association, explicit stale/original coordinates; no equal-id revival. |

Owner approval must record Q1–Q5 choices and any semantic clarification before producer dispatches. Subsequent units separately implement notation correspondence/alias support and summary/view composition/publication, with genuine producer-to-validating-reader tests for this matrix. Task25 is redispatched only after those prerequisites are verified; this document neither implements nor completes it. Task39 native payloads, Task40 Driver execution, Task41 presentation and all other parked decisions remain untouched; existing §23.6/SCA-003 credit is unchanged.
