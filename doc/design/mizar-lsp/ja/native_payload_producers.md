## Producer profile と所有権

Parser は修正の根拠と正確な token 境界を所有し、Frontend は [診断 merge](../../mizar-frontend/en/orchestration.md#diagnostic-merge-order) を通して型付き根拠を保持します。Diagnostics は shared payload 構築、形状検証、canonical identity、集約を所有します。Driver の [実 frontend service](../../mizar-driver/en/frontend_adapter.md#disk-frontend-service) は元の loaded source を結び、実 phase 出力を転送し、message から edit を導きません。Publication host は不変の保持、store 設置、承認済み deferred registration を所有し、LSP は消費だけを行います。これは責任の定義で、新 public type や外部 schema ではありません。
**Q1 — 最初の実 producer:** 承認済み A は既存 parser の export 文の semicolon 欠落を次 item の直前で検出する site だけを対象にします。export path/list が構文的に完結し、次 item が認識され、parser が挿入境界を認証できる場合です。[Export 文法](../../../spec/en/12.modules_and_namespaces.md#124-export-statements) は `;` を要求し、`ModuleParser::diagnose_missing_semicolon` は既に `MissingSemicolon`（採用 code E0041）を出し、`module/tests/parser_diagnoses.rs::parser_diagnoses_missing_export_semicolon_before_next_item` が意図を保持します。助言的な `MaybeIncorrect`/`LocalTextEdit` の `;` 挿入を提案し、次 token は削除・置換しません。Edit は写像済み境界の空 native range、明示的 expected text は `""` とし、次 token の診断 span は別に保持します。他 site、EOF、不正 path、曖昧な recovery にこの profile の fix は出しません。Recovery message だけでは安全な挿入 site を証明できません。
承認済み A では同じ E0041 draft に `DiagnosticContext` handle を一つ付けます。Subject は包含診断の code と正確な stable detail key を持つ `Diagnostic` とし、`required_snapshot` は生成元 snapshot に束縛します。内容は欠落した終端記号と認証済み挿入境界を説明し、type/proof trace や修正後 module の検証成功を主張しません。Parser 内の型付き修正根拠を Frontend 変換で元 source 座標へ保存する必要があり、選択された実装がその受け渡しを拡張します。LSP での復元や E0041 だけからの推測は認めません。

## Backing content と identity

**Q2 — bounded backing profile:** 承認済み A は retained `CacheRecord` backing と producer 所有 encoding key `mizar-frontend/export-semicolon-context/v1` を使います。正確な content は、`category` = `syntax.missing_semicolon`、`site` = `export-before-item`、`expected` = `;`、`insertion_offset` = 元 loaded source の byte offset（非負整数）を持つ object の artifact 所有 canonical JSON UTF-8 です。Source id、URI、翻訳文言、任意 trace を bytes に入れず、source identity は認証済み診断/publication association に置きます。同じ bytes を `StructuredText` payload text として返し、同じ canonical object を bounded summary descriptor に用い、承認済みの異なる `content`/`summary` hash role を使います。Producer 検証は完全な object、正確な handle/source association、payload text/format/truncation、両 role の encoding を照合し、翻訳可能 preview は独立とします。A は retained query backing であり永続 cache format や新 hash domain ではありません。Parser/storage codec を拡張しません。
A は承認済み [backing domain](code_action_validators.md#hash-domains-and-inputs) に従い、`CacheRecord.content_hash` は正確な content bytes、`summary_hash` は正確な descriptor bytes を、それぞれ role と encoding で frame して hash します。Cache key は決定的な producer-local context key で、file path や proof identity ではなく、store は正確な canonical handle に登録します。この非 artifact profile に `required_artifact_hash` を捏造しません。後続 producer が artifact/missing facts を使う場合は既存 validator に従い全 manifest-reachable dependency と所有者認証済み obligation/entry selector を供給し、A はその対応を認めません。
挿入 fix、context handle、Q4 command の明示的で安定した producer key を集約前に割り当て、publication ordinal や表示文言ではなく決定的な producer-local occurrence identity を用います。反復 site と診断順変更でも Diagnostics の canonical fix/handle deduplication 規則を保ち、edit/source/subject/backing 前提が変われば古い association を権威として再利用できません。異なる診断の同 id は各 record 内で解決します。Bytes の一致や handle が一つあることは fix と handle の関係を証明しません。

## Publication と host への受け渡し

**Q3 — 承認済み B、host 適格性と受け渡し:** Driver は `BuildSessionOutcome::Succeeded`、完了出力、commit 済み manifest が揃った場合だけ coherent full snapshot を公開します。E0041 source-error 経路は別の [ranged diagnostic-publication/host-input adapter](ranged_diagnostic_host.md) を使い、実 original-source retention/backing 認証と既存 consumer 検証を保ちます。Error を格下げせず失敗 module を成功として公開しません。Q3-A は非アクティブです。
承認済み ranged adapter を通して、不変 producer 出力を正確な診断集約/publication とともに保持します。内容は元 source binding、canonical fixes/handles、bounded store payload、明示的 fix-to-backing association です。Producer draft identity を実 canonical aggregation record で join し、ordinal/title/code-span から推測しません。Full-snapshot host は正確な publication/diagnostic/canonical fix と全 consumed backing dependency を **既存の承認済み Q3-A** `register_deferred_fix` carrier に設定します。承認済み ranged adapter は別定義で同等の認証済み admission を定め、既存 full publication を装えません。ここで新 serialized phase product や代替 Task38 carrier を選びません。
既存 full 経路では [snapshot 所有者](snapshot.md#source-association) が元 capture/text/maps/URI/version/incarnation と再利用されない process-local publication identity を供給します。対応 store を publication とともに既存の [retained-read lifetime](snapshot.md#currentness-and-retention) で保持し、等しい build id の新 publication に古い store を付けません。Action を公開する前に完全で対応済みの association を揃え、backing 不足を host の捏造 content や LSP compiler replay で埋めません。Publication の破棄は既存 retention に従い、新 eviction budget や global mutable store policy を定めません。SourceId serialization、保留中の OpenBuffer provenance/storage は決めません。
**Q4 — native action surface:** 適格な Q3 経路を前提に、承認済み A は Q1 local edit と bounded `mizar/explain` query に加え、同じ診断に別の `MachineApplicable`/`CommandOnly` explain suggestion を固定の producer 所有 opaque reference で付けます。Host はその正確な reference をこの handle の読み出しだけに allowlist し、承認済み registration に content/summary/store/producer 検証を設定し、既存 capability/locator/revalidation/cancellation/error 規則で `mizar.executeDiagnosticCommand` を再構築します。この読み出し command に edit/text-hash 宣言/artifact dependency はありません。

## 失敗と freshness

**Q5 — 不完全な producer 入力:** 承認済み A は対応不能 payload を独立に抑止します。型付き修正根拠がなければ fix を省略し、完全で有効な backing がなければ handle を省略するか登録 store が既存 unavailable outcome を返し、正確な command binding がなければ command を省略/filter します。診断と独立して有効な local fix は保持します。不完全 object を認証済み完全 content として公開しません。これは payload availability のみで、recovery、severity/identity、phase status、proof acceptance を変えません。既存 preview fallback/cancellation を維持します。
Current host read は producer content と正確に写像した current action edit を届けます。Edit（version-only/normalized text が等しい変更も含む）、close/reopen、publication replacement 後に古い locator を current として resolve/execute できません。Editor 無効化後も同じ publication が選択されている間、retained explanation read は元 content/URI/version/元 source 座標と `stale_artifact` を保ちます。古い snapshot 要求や query 中の選択 publication 置換は `stale_handle` となり、置換では新 publication が選ばれ、新しいものを通じて旧 payload を返しません。古い offset を変更後 editor text に再写像しません。Native テストは同じ実 producer payload でこれらを合わせて検証し、診断だけの host 選択と別の typed range fixture では足りません。Build/source hash の一致は権威を復活させず、async command read は Task38 の既存規則で currentness/cancellation を再検査します。
