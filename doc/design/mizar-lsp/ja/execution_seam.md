# 非終端 Driver 実行 seam
正本は英語: [English companion](../en/execution_seam.md)。

## Status and authority

**提案のみ: Q1–Q5 は未決定で、承認済みの選択肢はない。** owner 承認後に実装を別 dispatch し、その後 Task40 Audit G5 を再 dispatch する。Task40 は保留のまま。本書は実行の前提条件を定義し、bridge scheduling や Task41 の presentation 判断は決めない。
根拠: [bridge lifecycle/deadlines](build_bridge.md)、Driver の [session states/capture](../../mizar-driver/ja/request.md#buildsession)、[supersession](../../mizar-driver/ja/request.md#supersession)、[scheduler boundary](../../mizar-driver/ja/driver.md#scheduler-boundary)、[cancellation](../../mizar-driver/ja/driver.md#cancellation)、[events](../../mizar-driver/ja/events.md)、internal01 の [協調キャンセル](../../internal/ja/01.compiler_driver_and_pipeline_scheduler.md#キャンセル)。言語・証明・診断の振る舞いと scheduler policy は既存 owner に属する。
現状の `CompilerDriver::submit_captured` は同期的な `submit_inner` に入り、scheduled dispatch 完了後に `session.finish(outcome)` を実行し、最後に `store_session` が record を公開する。`cancel` が届くのは保存済み record だけで、active なものは直ちに終端化する。その排他的可変借用中に bridge は replacement/Shutdown を処理できない。background thread だけ、捏造した Running record、終端 return 後の cancellation は、欠けている実行中の制御境界の証拠にはならない。

## Required observable boundary

本物の scheduled work が残る、対応対象の genuine captured build では、完了前に allocator 発行の session/request id と既存の lane・generation・content-derived snapshot identity と authoritative な非終端 state を公開し、元の native capture と lease を保持する。早期 capture/planning/dispatch failure は構造化された終端 failure のままでよく、live build を作り出さない。外部から cancellation 可能になる前に、所有された execution record が存在しなければならない。`Running` には今後 event を生成し得る本物の scheduler-owned work が必要で、caller が設定する flag では足りない。
実行が未完了でも使える control path と、進行を drive/await して authoritative state・既存の順序付き event・最終的な終端 submission/result を取得する手段を公開する。control は完了まで保持される Driver borrow の再取得を要求できない。Rust の具体的な名前・型は Q 承認後の実装判断とし、本定義は新しい event/payload や診断 kind を要求しない。
古い実行の完了を待たず replacement を受理し、実際の lane-current acceptance を公開できなければならない。その後に限り、bridge は古い非終端 session に Superseded を一度要求する。世代の単調性、受理後の failure、同一 snapshot replacement を維持し、capture failure や受理拒否を replacement と見なさない。編集・admission だけでは cancel しない。quiet/cap timing、coalescing、flush 時 capture は bridge が所有する。
Shutdown/exit 後、admission 停止後も control と cleanup を使用可能にする。slot を破棄し、所有する非終端 session に Shutdown を一度要求し、以後 capture/submit しない。cancellation request、owner checkpoint での観測、終端 outcome、実行の drainage は証拠として区別する。要求 acknowledgment だけでは work 停止を証明しない。不明・終端済み session への cancellation は冪等で、work を復活させない。

## Ownership and invariants

Driver は in-flight record・lane-current 遷移・event 組立・publication guard を、Build は graph readiness・resource admission・cancellation policy を、phase service は実実行・checkpoint を所有する。Session/IR/Artifact は capture・output・transaction authority を維持する。LSP は自 lane の submit/control と元の capture association 保持だけを行い、別 scheduler/compiler を実装しない。
実行ごとの単一 authoritative record により、completion/cancel race が確定した終端 result を上書きせず、SessionFinished を重複せず、obsolete work を再活性化しない。各 control/acceptance 遷移の順序確定点を定義する。cancellation より先に確定した completion は実際の終端 result を保ち、受理済み cancellation は Q2/Q3 に従う。実行 timing が異なっても既存の canonical task/service 順序・構造化 error・replay identity を保つ。event 取得は current publication 権限を与えない。
遅延 result・diagnostic・coherent snapshot・artifact handoff で、既存の lane/session と snapshot/publisher guard を再検査する。古い work は replacement と snapshot id が等しくても current にならない。partial accepted artifact や synthetic phase output を認めない。cancellation は開始済み atomic artifact transaction を rollback せず、その owner 境界が根拠であり続け、obsolete completion は current LSP publication を与えない。
session 単位の control は、snapshot id を共有する replacement や別 lane の work を cancel してはならない。各実行の元の capture・source map・cancellation state・cached-output ownership・必要 lease を、lane 選択や論理的終端 state と独立して、その実 work が参照不能になるまで保持する。進行中の reader は既存の retained resource を維持する。cleanup は当該実行の ownership だけを一度解放する。新しい global eviction/storage/SourceId policy は提案しない。

## Open owner decisions

**Q1 — 誰が実行を進め、control を使用可能にするか。** A: captured acceptance/start と host 駆動の progress/finish を分離し、再開可能な owner execution を保存して完了前に制御を返す。既存の同期 submit は同じ core を終端まで動かす adapter とする。B: Driver-owned worker execution と独立して使える session control/completion 取得を用意し、同期 caller は同じ実行を待つ。順序・lifetime・host 制御を明示しやすい A を推奨する。B は長い owner call 中も進行できるが、worker ownership・同期・shutdown/join・thread safety 契約が必要。A には本物の scheduler continuation/dispatch 境界が必要で、完了済み work の再実行や blocking submission 全体の polling では足りない。いずれも readiness/resource policy を変えず、LSP に scheduler queue の再構築を許さない。A の host 統合は progress call 間も protocol traffic/cancellation を処理し続ける必要があり、未対応の長い非協調 call に latency 保証は与えない。
**Q2 — Shutdown を実 work にどう届けるか。** A: owner-supported な実行ごとの cancellation signal を既存 Build cancellation policy と合成し、実 phase checkpoint に渡す。Superseded/Shutdown の Driver reason は維持する。B: Build owner の cancellation API を対象 execution に結び付く explicit/shutdown request で拡張し、Driver が使用する。限定した control seam となる A を推奨する。B は policy を集約するが、別の Build API 定義が必要。どちらを承認しても、既存文書の snapshot-wide explicit/Shutdown propagation gap を解消しなければならず、Shutdown を偽の supersession として表現したり、終端 flag だけ設定したりしてはならない。両案とも実行中 work への checkpoint delivery・以後の適格 dispatch の防止・同一 snapshot id での session 分離・既存 snapshot supersession との互換性を定義する。既存 cancellation を超える新しい scheduler policy/観測可能 outcome は、実装前に owner 定義を要する。
**Q3 — cancel した session はいつ終端になるか。** A: cancellation を Cancelling として受理し、owner work の drainage 後にのみ Cancelled/Superseded と一つの終端 event を公開する。B: 現状の即時の論理的終端 outcome を維持するが、別に観測可能な execution-drain state/control lifetime を保持し、以後の全 current handoff を抑止する。終端証拠と work 停止が直接対応する A を推奨する。A は既存の即時終端 timing を変え、B は第二の lifecycle を増やし、drain 中の work と bridge の非終端 predicate の関係を明示する必要がある。両案とも Driver cancellation owner 文書・race/冪等性・resource retention の承認された適応が必要で、即時終端も event 遅延もここでは選択しない。強制停止や checkpoint/cleanup latency は保証しない。
**Q4 — bridge をどう接続するか。** A: 設定済み compiler host に明示的な非終端 captured-submission route を追加し、Q1 の共通 execution core により同期 public caller を維持する。bridge の control/progress と replay をそこへ適応する。B: 非終端 acceptance を標準の内部 submission 契約にして内部統合を移行し、既存 caller には同期互換 wrapper を維持する。caller 移行を限定し batch/watch 動作を維持する A を推奨する。B は非終端実行へ内部 submission を統一するが、統合と owner review の範囲が広がる。両案とも本物の native import-discovery/diagnostic-index 動作・元の capture handoff・acceptance identity が必要で、test-only Driver・人工的な保存 session・別の偽 bridge backend では足りない。executable host の設置、Watch 統合、Task41 presentation 判断は導かず、別 dispatch の境界を保つ。
**Q5 — test で live cancellation をどう決定的にするか。** A: genuine native SourceFrontend invocation とその実 scheduler task の周囲にある owner-supported dispatch/checkpoint 境界で同期し、実 output/status を維持したまま次 checkpoint 前に cancel し、release/advance 後の drainage を観測する。B: genuine producer に委譲する制御可能な協調 wait を持つ実 registered phase service を使い、同じ seam が actual captured work を運ぶ native end-to-end control も用意する。補助 service の範囲が最小となる A を推奨する。B は Q1-B で call 内 checkpoint を公開できるが、慎重に限定した test adapter が必要。両案とも positive PhaseResult・終端 outcome・currentness・event を捏造しない。timeout/sleep race、submission 前の cancellation 注入、private state 改変を Task40 証拠と数えない。選ぶ同期方法は outstanding owner work と cancellation 観測を証明し、canonical result が変わらない uncancelled run も含める。

## Conditional validation and handoff

| Case | 承認・実装後に必要な証拠 |
|---|---|
| 1 | 実 OpenBuffer capture → native Driver submission → genuine selected task/checkpoint: 完了前の authoritative 非終端 session・元の association・独立した使用可能 control。uncancelled 実行の canonical result/status/event は同期実行と一致する。 |
| 2 | その live old session と同一 snapshot id を含む replacement acceptance: replacement が先に lane-current となり、bridge が一度 Superseded を要求し、old work が Q2/Q3 に従い cancellation を観測して drain する。old current output も replacement への cancellation/resource 影響もない。 |
| 3 | 実 live session と admitted slot がある Shutdown/exit: 一度の Shutdown、slot 破棄、以後 admission/capture/submission なし、実際の協調観測/drain、一つの終端 outcome/event。protocol 終端後も cleanup 可能。 |
| 4 | 単なる編集・capture failure・submission 拒否・受理後の failure・終端済み old session・completion/cancel race: 既存 acceptance/no-cancel/冪等性/error 規則、確定終端 result、厳密に一つの SessionFinished、以後の current handoff 禁止、世代単調性を維持し、live state を捏造しない。 |
| 5 | 別 watch/LSP lane、old/replacement 実行、同一 id snapshot: control/publisher 分離、安全に解放可能になるまで元 capture 保持、canonical replay、既存 suppression/publication guard を維持し、cross-lane cancel/stale acceptance を認めない。 |
| 6 | genuine producer work を伴う決定的 checkpoint/release と typed timing/cancellation fixture の区別: 実観測・終端/drain・publication 拒否を確認し、synthetic acceptance なしに同期互換性・cleanup/error path を検証する。 |

既存の test intent は Driver `tests/request.rs` の lifecycle/冪等性、`tests/driver.rs` の scheduler cancellation、および LSP `build_bridge_timing_tests.rs` / `build_bridge_event_tests.rs` の capture/failure/lane/terminal control に残る。running-deadline predicate と pre-cancelled scheduler policy 注入は control にすぎず、live bridge cancellation 証拠ではない。
Q1–Q5 承認後、Driver/Build owner の seam・cancellation propagation 作業（owner 契約改訂と同期互換性を含む）を dispatch し、別単位なら限定した bridge 適応を続ける。その契約は coding 前に選択 API・ownership・checkpoint・race・本 matrix を freeze する。Muse は actual bridge から genuine native 非終端 session に到達でき、両 cancellation reason が実 work に届き、lifecycle/resource/publication control が通過してから Task40 を再 dispatch する。前提 test は Task40 を完了せず、bridge 経由 supersede/Shutdown の組合せ証拠は Task40 が所有する。semantic coverage と §23.6/SCA-003 credit は与えず、Task41 と保留 OpenBuffer 判断は変更しない。
