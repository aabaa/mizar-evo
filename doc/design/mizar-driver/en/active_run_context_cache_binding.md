## Existing producers and missing association

[Native capture](request.md#native-source-capture) retains actual source/loader/input tuples and snapshot identity. [Build planning](../../mizar-build/en/planner.md) supplies typed package configuration, lock content and module/dependency indexes. Explicit [config/lock checks](frontend_adapter.md#native-config-content-association) bind their content hashes to capture; they do not authenticate active runtime selection. Recorded toolchain version/constraints and opaque `ToolchainInfo` agreement do not identify the executing compiler, selected backend or resolved pin.
[Native Disk preparation](frontend_adapter.md#native-disk-cache-preparation) receives `SourceLoadInputs` and an explicit `VerifierPolicy`; its compatibility fields carry supplied identities. `NativeCacheOptions` borrows policy/Store/mode independently of policies captured in configured services. No producer establishes that these are the actual effective configuration and policy used by this run. Genuine [persistent SourceLoad](driver.md#persistent-native-disk-sourceload-cache), [leaf persistence](driver.md#persistent-native-leaf-frontend-cache) and [retained Frontend lookup](frontend_adapter.md#retained-native-leaf-frontend-lookup) remain bounded explicit routes, not complete active-runtime provenance or cold Frontend expectations.
`design_gap`: the producer and binding contract below. `external_dependency_gap`: genuine running-toolchain/component identity and active configuration/policy association producers; cold Frontend expectations and later dependency/proof producers also remain missing. After approval, source/test work requires separate contracts. Another caller-authored digest, descriptor, success flag or generic published handle cannot close these gaps.

## Proposed route and ownership

Subject to Q1–Q6, Driver bootstrap assembles a submission-local association from actual protected capture, the produced plan/index, selected registry/services and effective invocation inputs, then supplies only the applicable validated data to the native cache path. It neither reconstructs lower semantic state nor treats the association as a transferable receipt. No representation, public type, constructor or hash/schema extension is frozen here.
Build owns config/lock projection, plan validation, graph and [cache scheduling](../../mizar-build/en/cache_seam.md#scope); Proof owns [policy interpretation/fingerprint](../../mizar-proof/en/policy.md#policy-fingerprint), selection/status and exported reuse metadata, with Kernel retaining evidence checking; Cache owns key construction, compatibility, [proof-reuse validation](../../mizar-cache/en/proof_reuse.md) and footprint/Store validation; Frontend owns independent expectations and phase footprints; IR owns sealing, physical retention and publication permission. Driver authenticates their same-run association and live session eligibility, without deriving their judgments or expanding accepted profiles.

| Required association | Genuine source and refusal boundary |
|---|---|
| Capture and task | Original native Disk source, package/module/path/edition/raw-map and source-key data; actual snapshot, task/work-unit, plan/index and sealed parents. Require unique exact correspondence; equal local IDs or normalized source hashes alone do not suffice. |
| Config and lock | Actual selected package verifier/build settings and typed lock inputs used by bootstrap; invoke existing content profiles and explicit capture comparisons. Preserve per-package settings/Store-root selection. Supplied aggregates/hash equality alone prove no current-file or resolved-dependency provenance. |
| Effective policy and invocation | The actual Proof policy supplied to each participating configured producer and cache validation, plus applicable resolved backend profiles/priorities, evidence priorities, recorded seeds and resource budgets from the execution configuration. Preserve policy/config as separate identities; missing active selection or conflicting associations withhold optimization. |
| Runtime producers and schemas | Actual selected service implementations and their registered/actual descriptors, owner output/key/storage/checker schemas, and genuine identity of the running compiler/components and selected backends where relevant. Concrete TypeId guards identify an in-process service only; copied descriptors, version strings, environment claims and opaque ToolchainInfo cannot establish portable runtime identity or compatibility. Q2 must supply the missing producer. |
| Dependencies and expectations | Actual artifact/index/summary identities and owner-complete phase footprints, with independent current payload bytes/side tables where required by [IR](../../mizar-ir/en/cache_adapter.md#producer-payload-expectations). SourceLoad's exhaustive zero-artifact footprint is not evidence of zero dependencies for Frontend/imports/proof. Unknown is not empty. |

The minimum is the entire applicable identity closure of the admitted phase, not every field of every future service. Cache retains compatibility decisions; no new equivalence between runtime versions or schemas is inferred. Session/request/lane/generation, cancellation, publisher and retention state authorize use but do not enter canonical keys. Preserve [key purity](registry.md#cache-key-purity-contract): worker/order/timing, undeclared environment/filesystem metadata and cache-root routing are not semantic key inputs; declared seeds/budgets and configuration identities remain as required by their owners. Resolve acquisition/root I/O outside the pure cache query.

## Lifetime, currentness and refusal

Use original immutable owner values through the invocation; never allow a context from another capture/plan/registry/policy selection to authorize this one merely because a hash or snapshot id agrees. Do not infer current disk-file freshness from a frozen capture. Actual source loading and existing dispatch validation retain their checks; changed configuration/registry/policy selection requires a new association, not mutation of a retained one.
Preserve both [lane/session and request-snapshot guards](request.md#current-session-publication-boundary), cancellation checks, publisher authorization and physical handle validity before lookup/materialization/persistence/handoff and final reporting at the route's existing checkpoints. Recheck after lower work where current routes do. A snapshot lease keeps snapshot resources alive; IR owners keep slots alive; neither makes a result current or permits publication. Scope cached-parent retention through actual scheduler consumption; release acquired owners on success, refusal, error, cancellation and supersession. Retained readers never revive execution/publication authority.
No atomic lifetime across Store I/O and lane/publisher changes is promised; earlier valid complete records need not be rolled back. Future reuse still passes normal Cache validation against the new run. Publication/currentness suppression must remain distinct from cache corruption or semantic rejection.
Absent, unsupported, ambiguous or mismatched context withholds cache preparation under Q6; genuine Store/lookup/decode/retention failure follows existing miss/error-as-miss handling. Existing invalid submit/dispatch/graph inputs and real producer errors keep their precedence and outcomes. Never silently weaken policy, repair input, reroute proof work or report a hit from metadata. Build alone accepts the validated skip, and only actual CacheHit tasks expose prepared cached outputs. Neither context nor hit establishes acceptance, a complete proof slice, witness/Artifact publication or a verified session.

## Owner Q-decisions

**Q1 — producer and binding boundary.** A: Driver's actual bootstrap assembles a private association from the values it installs/uses, and native cache consumes that same association; direct legacy APIs retain their limited claims. B: expose a reusable host-issued context accepted by later submissions. **Recommend A:** minimizes new authority and cross-run validation. B needs issuer authentication, exact capture/registry/config binding, revocation and consumer rules before freezing any API. Neither accepts arbitrary caller-authored context as a genuine producer.

**Q2 — running producer identity.** A: introduce an owner-produced deterministic identity for the actually running compiled components and selected service/backend implementations, bound at their real construction/selection sites; keep resolved release/pin authentication separate. B: require a genuine distribution/toolchain-selection attestation before this cache path becomes eligible. **Recommend A for a bounded native implementation:** it can identify execution without pretending that lock metadata selects/authenticates a release. The producer does not yet exist: freeze its authoritative build/selection source, reproducible versioned encoding and Cache-owned exact compatibility rule in a prerequisite; process-local TypeId, caller labels or a self-asserted digest are insufficient. B additionally needs the external selection/attestation owner. Unknown provenance remains unavailable under either option; neither approves new compatibility policy here.

**Q3 — effective configuration/policy association.** A: resolve the effective inputs once at bootstrap and pass the same Proof-owned policy values to configured services and cache validation, with per-phase policy roles explicit. B: leave independent construction and add complete owner-provided correspondence validation at admission. **Recommend A:** avoids post-hoc equality pretending to prove selection. The later contract must name actual configuration, invocation overrides and existing precedence, exact participating services and policy-consuming roles. Unspecified config-to-policy mappings or new precedence rules return as Q-decisions; neither option invents them or merges policy/config fingerprints.

**Q4 — lifetime.** A: submission-local borrowed/owned immutable association, existing point checks and scoped IR retention; reconstruct it for every new submission. B: retain a reusable per-session/registry context with explicit invalidation and per-use revalidation. **Recommend A:** reduces stale authority and release paths. B must define replacement/cancellation/reconfiguration invalidation. Neither includes volatile lifetime IDs in cache identity, promises atomic Store/currentness, or turns retention into currentness.

**Q5 — implementation staging.** A: first implement genuine active-run binding for the already supported native Disk SourceLoad profile, including required runtime identity prerequisites; separately freeze cold Frontend producer/consumer work. B: combine binding and genuine independent cold Frontend expectations/lookup in one implementation unit. **Recommend A:** exposes the missing association with a smaller oracle while preserving later footprint boundaries. B requires the whole Frontend footprint/expectation matrix and owner scopes. Neither permits an incomplete context, changes registered NoKey behavior by this definition, or completes full STEP6C; proof reuse/dependency-binding and other service gaps remain separate.

**Q6 — unavailable context.** A: withhold optimization only for tasks/profiles lacking their complete required association. B: withhold all optional cache preparation for this submission if any required association is unavailable. **Recommend A:** preserves independently eligible optimizations while following architecture-22 performance-only fallback; B is simpler but may rerun unrelated work. Both preserve ordinary execution, existing errors/publication suppression, disabled-cache behavior and invalid-input/producer-error precedence, with no new public diagnostic. Neither rejects a valid run for a cache miss or converts a real semantic failure into success.

## Conditional validation and handoff

The frozen definition contract's six review cases become implementation obligations only after the selected options are approved. Require genuine otherwise-viable positives and independent clean oracles: capture/bootstrap/actual registered execution and real Store records must produce cold/warm observations, not test-authored context/Hit/Complete evidence. Independently vary source/module/package/snapshot/plan/config/lock/policy associations and genuine runtime selections, cross-run swaps, service/schema/provenance and complete/incomplete footprints; equal labels or hashes cannot explain away a missing association. Refusal controls and unknown compatibility must withhold optimization without weakening effective policy or changing ordinary outputs/canonical diagnostics.
Exercise cancellation/supersession, current publisher replacement, collected slots and every owner-release return with deterministic checkpoints; retained-read controls must fail current use. Cover disabled cache, unsupported origin/profile, missing producers and actual Store/lookup/decode failures with viable ordinary execution. Reuse existing config/lock/toolchain, SourceLoad/retained-Frontend, Cache and IR matrices rather than cloning them. Frontend/proof/import cases remain refusal controls until separately admitted; context alone does not unlock them.
Owner records Q1–Q6 choices before Muse dispatches implementation. Its subsequent freeze must identify genuine producer APIs and identity sources, applicable phase closure, configuration/policy mapping and roles, purity/compatibility/validation order, exact owner write scopes, lifetime/release rules, test cases and focused/E2E gates. Missing prerequisites are explicit unavailable boundaries, not fabricated producers. New semantic or compatibility choices return to the owner; this definition changes no source, tests, spec, trace or coverage status.
