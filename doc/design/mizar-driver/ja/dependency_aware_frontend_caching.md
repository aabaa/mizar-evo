# 依存関係を扱う native Disk Frontend キャッシュ提案
正本: [English](../en/dependency_aware_frontend_caching.md)。

## 状態と権限

**2026-11-17 に owner が Q1–Q5 の A をすべて承認。** [Driver 計画](00.crate_plan.md#task-index) が索引する定義案であり、キャッシュ受入れを有効化しない。承認済み [active-run 決定](active_run_context_cache_binding.md#owner-q-decisions) と現在の [zero-import cold Frontend](driver.md#active-run-cold-frontend-binding) は既存 profile の権限を保持する。真正な全 Frontend 解析は parsing-avoidance や full STEP6C の達成ではない。
根拠: 仕様の [import](../../../spec/en/12.modules_and_namespaces.md#123-import-statements) と [build 再現性](../../../spec/en/23.package_management_and_build_system.md#234-build-lifecycle-and-reproducibility)、architecture 22 の [完全 footprint](../../architecture/en/22.incremental_verification_contract.md#dependency-slice-completeness)、[字句・parse 入力](../../architecture/en/22.incremental_verification_contract.md#frontend-lexicalparse-footprints)、[等価性](../../architecture/en/22.incremental_verification_contract.md#clean-build-equivalence)、[freshness](../../architecture/en/22.incremental_verification_contract.md#snapshot-scoped-results)、[fallback](../../architecture/en/22.incremental_verification_contract.md#cache-miss-fallback)。Cache の [fingerprint targets](../../mizar-cache/en/dependency_fingerprint.md#fingerprint-targets) と [lookup](../../mizar-cache/en/cache_store.md#lookup) が key/Store 権限を保持する。どの選択肢も言語、診断、proof 受入れ、互換性方針を変更しない。

## 既存 producer と不足する接続

実在する [supplied workspace-leaf 経路](frontend_adapter.md#supplied-workspace-leaf-summaries) は current な sealed leaf Frontend とその SourceLoad lineage を認証し、A13 local exports と正規 lexical contribution を構築して実際の provider に渡す。[scheduled prefix](driver.md#scheduled-sourceloadfrontend-prefix) は完全な import overlay を通して真正な leaf を引き渡せる。intermediate/artifact-summary producer も存在するが、キャッシュ適格性を証明しない。source lexical summary から完全な artifact ModuleSummary を捏造しない。
既存の [encoding](frontend_adapter.md#native-leaf-frontend-record-encoding)、[retained lookup](frontend_adapter.md#retained-native-leaf-frontend-lookup)、[cold expectations](frontend_adapter.md#cold-native-leaf-frontend-expectations) は zero-import 限定。import 入力の完全 closure/key projection、認証済み leaf summary による独立 importer 期待値、実 provider/runtime の結合、依存 readiness 時点の scheduler lookup/retention が不足する。これらは定義 gap であり、imported admission とテストは実装の前提として残る。
Driver は run/capture/provider の関連付けと orchestration を所有する。Build は plan/index/config/lock と scheduling、Frontend は preprocessing/key bundle/字句環境/parse/output storage、Resolver/Artifact は target resolution/A13 対応/summary identity を保持する。Cache は canonical key/互換性/Store validation、IR は payload 再構築/lineage/物理的有効性/retention、Proof は実効 policy と acceptance/reuse を所有する。本案で public context や下位 owner API を追加しない。

## 提案する限定 closure

Q1-A では診断なし・AST ありの Disk importer と、異なる direct workspace target 一つだけを扱う。target は clean・import なし・reexport なしの leaf。同一 target の重複 import は既存規則どおり ordinal/span/alias provenance を保持し、物理 parent を重複させない。private-only export の真正な完全 empty contribution は許容する。summary 不足/未対応、別 target、intermediate/transitive import、artifact 依存、cycle/self-import、reexport、Open/Generated、recovery/診断は最適化を見送る。通常 service の既存の広い動作は保持する。
既存 leaf 規則で protected native capture、snapshot/plan/index/task、target 自身の package version/edition/root/path/source metadata を認証する。current な own SourceLoad と解決された leaf Frontend の二 parent を kind/work-unit で特定し、不足・余剰・重複を拒否する。leaf 自身の current physical SourceLoad lineage、source key/map、AST、A13 export 対応を検証する。importer prescan と parsed imports を source/resolution に対応させ、各 summary がその leaf に由来し全 distinct target が存在することを確認する。index/overlay identity、fingerprint 一致、generic sealed publication だけでは足りない。source-summary の lockfile_identity None を維持し、captured lock/config identity は別物で release 認証を与えない。
実際の Frontend service/provider は、この検証済み immutable summary 集合そのものを消費する。選択済み parser/provider 実装、登録/実 descriptor、owner codec を真正 bootstrap association に結び付ける。既存 executing-image residency closure を、新たに参加する Resolver/Artifact/export/lexical-provider code へ拡張する。descriptor コピー、TypeId、caller root、digest 一致では選択を認証できない。未対応 linkage や association 不足は caching を拒否する。実 installed Proof policy、package ごとの設定/Store routing、既存互換性を保持する。

## 完全 key と独立期待値

Q2-A は既存 owner の完全 Frontend key bundle に加え、versioned な import 入力 projection を要求する。source semantic/raw-storage identity、preprocessing lexical/import-prescan hash、各解決 summary の完全 module identity と lexical fingerprint、順序付き import provenance、active lexical environment、notation/synonym/antonym 効果、predicate/functor metadata、source-position operator view、parser lexing plan/filter/context、token key/content、parser input hash/schema/version、edition を網羅する。own/leaf parent の content/side-table commitment、target source/key association、実 config/lock/policy/runtime/schema、完全な canonical named input を維持する。multiset/順序付き provenance を set に置換せず、token-key hash から token content を推定せず、semantic proof DependencySlice を字句完全性の代用にしない。
後続実装 freeze では、既存 composite hash による網羅も含め、必要な各要素を真正 owner 値、厳密な versioned canonical encoding/order、Cache key field に対応させる。operator/notation/filter 根拠の不足は unavailable であり zero ではない。owner codec と Cache の exact compatibility を再利用し、投機的な新 upstream hash/schema は本案で承認しない。SourceId/session/lane/task/worker/order/retention、cache-root routing は semantic key に含めない。元の ordinal/source-position は owner semantics が必要とする箇所に残す。
Q3-A では current bound SourceUnit と同じ認証済み provider summary から真正な全 Frontend 解析を行い、Store data と retained importer Frontend に依存しない。clean AST/key と厳密な source/preprocess/dependency 対応を要求する。lookup 前に完全 key bundle、semantic canonical bytes、全 raw Disk storage/map/side table、named-input/parent 期待値を生成する。decode 前に全 incoming raw storage を比較し、IR の expected semantic/side 検証と Cache key/produced-by 検証を維持し、owner codec で current SourceId/map と lineage を再構築する。等価性検査のため未検証 bytes を publish しない。miss では解析を再実行し得るため parsing-avoidance を主張しない。

## Scheduler の時点、寿命、拒否

Q4-A では実 importer の graph readiness、すなわち PackageResolve と真正な own SourceLoad/leaf Frontend 依存を scheduler が受理した後にだけ lookup を準備する。leaf は真正実行または既存 zero-import cache 経路で受入れた出力でよい。graph/overlay/task の厳密な対応を検証し、root/SourceLoad/leaf を scheduler より先に実行せず、Complete を捏造せず、Store metadata から readiness を推論しない。Q3 解析は期待値準備であり scheduler task の完了ではない。Build が実 rehydrated skip を受理するまで通常実行を残し、最終的にその task が CacheHit の場合だけ準備済み出力を報告する。
利用前に leaf SourceLoad lineage を含む全 consumed physical parent の scoped IR owner を取得し、期待値生成・lookup/decode・scheduler consumer・最終検証まで保持する。rehydrated importer も同様に保持する。利用前と下位処理後の既存 handoff で lane/request/snapshot/cancellation/publisher authorization と physical parent を検証する。success/miss/refusal/scheduler error/cancellation/supersession 全経路で取得 owner を解放する。borrowed reader/snapshot lease は currentness や publication 権限を与えない。Store I/O をまたぐ atomic lifetime は約束せず、frozen capture は後の disk freshness を保証しない。
Q5-A は、同じ検証済み closure にある実際に受理済み Completed/CacheHit 依存と真正 clean importer 出力だけから best-effort PersistentPrefix write を拡張する。insert 前に output/parent 対応、physical/current authorization、完全な期待 payload を再検証する。guard 喪失後の write を抑止し、先に有効だった write の rollback は不要。承認済み Q6-A に従い context 不足/未対応では該当最適化だけを見送る。disabled cache、lookup/decode/retention/Store failure は通常結果を保持する。invalid input/実 producer error の優先順位を保持し、新診断や semantic success を捏造しない。登録 cache query は pure NoKey のまま、direct/retained/zero-import の既存契約を保持する。

## Owner Q-decisions

**Q1 — 最初の import profile。** A: distinct direct workspace import-free leaf 一つと既存重複 import provenance。B: 複数 target/intermediate/artifact も今回含める。**推奨 A:** transitive 認証や外部 summary provenance を追加せず真正な限定 producer を使える。B は実装前に大きな closure/ownership/test 案が必要。どちらも semantic import/export acceptance を与えない。
**Q2 — closure 表現。** A: owner の完全 key bundle と versioned canonical dependency/parent association projection を上記対応表で再利用する。B: Frontend-owned 完全 lexical/parse footprint producer を先に追加する。**限定 profile では A を推奨:** public surface を抑え、対応不明な入力を拒否する。真正 owner 値で網羅できなければ prerequisite 判断に戻し、不完全 A を黙って実装しない。B は別途 frozen owner seam が必要で、並行 AST/summary 構造の複製ではない。
**Q3 — 独立期待値。** A: lookup 前に認証済み current summary を使う真正な全 importer Frontend 解析。B: parse を避ける独立期待値 producer を先に作る。**推奨 A:** 承認済み cold-profile staging に従い完全 oracle を得る。B は新 producer/footprint 証明と明示的 parsing-avoidance 基準が必要。どちらも Store record/retained importer 出力を current 期待値に使えない。
**Q4 — scheduler 上の位置。** A: 実 importer の ready 時点で受理済み parent に範囲を限定して準備。B: 別の準備 stage で全 parent を事前計算する。**推奨 A:** graph 実行の所有を維持し投機的 phase work を避ける。B は明示的 staging/retention/対応規則が必要。どちらも Build readiness/current-use guard を迂回しない。
**Q5 — persistence 導入。** A: 後続実装で guarded imported write と dependency-ready lookup を一緒に扱う。B: read-only lookup を先行し真正 write を延期する。**推奨 A:** テスト作成 positive に頼らず実 cold/warm record と fallback を観測できる。B は positive lookup credit の前に別途真正 producer を特定する必要がある。両方とも best-effort Store semantics と既存 zero-import 動作を保持する。

## 条件付き検証と引継ぎ

承認後の freeze は最大六 case family: (1) 真正 importer/leaf の cold write、warm/fresh-capture lookup、resident/blob、SourceId rebinding を独立 clean の全 key/bytes/map/side/lineage/診断/outcome と比較。(2) viable な source/raw/import-prelude/target/alias/lexical/notation/operator/parser/edition/leaf-summary/config/lock/policy/runtime 変更で miss/refuse、worker/order/local-ID 変更で canonical identity 維持。(3) stale/foreign/collected/swapped/missing/surplus parent、wrong summary/provider、self-hash も書換えた整合 corruption を未検証 publication 前に拒否。(4) 決定的 readiness/cancellation/supersession/publisher replacement と全 owner-release 経路。(5) disabled/failing Store、未対応/不完全/transitive/artifact/診断 profile でも viable な通常実行と error 優先順位を維持。(6) zero-import/retained/persistent/NoKey と later-service deferral を維持。各拒否 control は他条件が viable な cache record/clean run から始め、不足データを complete-empty にしない。
Driver の `source_load/supplied.rs`、`misc.rs` scheduled-overlay、`native_disk.rs` と Frontend/Cache/IR owner テストを再利用する。positive 根拠は実 bootstrap/scheduler event/真正 producer/Store record から得る。実 CacheHit と importer TaskStarted 不在は scheduler skip の証拠に限り、期待値解析の回避ではない。owner の Q1–Q5 承認後、Muse が実装 dispatch と契約 freeze を行い、厳密な producer API/encoding、scheduler hook、owner write scope、retention/error 経路、focused/E2E gate を指定する。新 semantic/compatibility 判断は owner に戻す。本単位で code/test/spec/coverage/proof/publication/reuse/full STEP6C 状態を変更しない。
